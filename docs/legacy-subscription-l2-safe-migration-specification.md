## 1 — هدف L2 (وما ليس هدفها)

### الهدف
نقل أي سجل وصول حقيقي وفعّال ما زال موجودًا **فقط** بالنظام القديم (`app_subscriptions`) إلى النظام الجديد (`subscriptions`/`access_assignments`)، **بشرط واحد لا استثناء له:** لا يمس هذا النقل أي قرار مستخدم صريح مسجَّل بالنظام الجديد بأي حال — لا إنشاء، لا تعديل، لا "تصحيح".

### ما ليس هدف L2 (صريح، لمنع الانزلاق)
- **ليست L3** — لا إزالة قراءة من `app_subscriptions` (Dashboard يبقى يقرأ منه كما هو).
- **ليست L4** — لا حذف للجدول أو البيانات القديمة.
- **ليست إصلاحًا شاملًا للتناقضات** — لو وُجد مستخدم بحالة لا تحتمل قرارًا آليًا آمنًا (نادر، موثَّق بقسم 3)، **لا يُرحَّل، يُترَك ويُسجَّل**، لا يُخترَع له قرار.
- **ليست مزامنة مستمرة** — أداة تُشغَّل يدويًا، بإذن، مرة أو عدة مرات منفصلة — ليست Job/Listener تلقائي دائم (يُبقي على قرار "لا Synchronization" من L1 قائمًا).

## 2 — نطاق البيانات (فحص فعلي، لا افتراض)

**الجداول المفحوصة مباشرة أثناء كتابة هذي الوثيقة (بيئة التطوير المحلية، مؤكَّد `APP_ENV=local`/SQLite، لا علاقة بـhw.sa الحقيقي):**

### `app_subscriptions` (Legacy — 4 صفوف، لن يزيد العدد أبدًا بعد L1)
```
user_id=5  app_key=marefa  status=active  subscribed_at=2026-08-06
user_id=6  app_key=marefa  status=active  subscribed_at=2026-08-08
user_id=7  app_key=marefa  status=active  subscribed_at=2026-08-09
user_id=8  app_key=marefa  status=active  subscribed_at=2026-08-09
```
**ملاحظة بنيوية مهمة:** `AppSubscriptionResource` بلوحة الإدارة يسمح فقط بحالتين (`active`/`cancelled`) — لا حالة ثالثة ممكنة بالـSchema أو بالواجهة. `app_key` بكل الصفوف الأربعة = `marefa` حصرًا — لا تطبيق آخر كان "متاح ومجاني" وقت أي كتابة قديمة. **بعد L1 (إيقاف الكتابة الجديدة)، هذي المجموعة مُجمَّدة نهائيًا** — لن يُضاف صف خامس أبدًا عبر أي Flow طبيعي، فقط عبر فعل يدوي إداري متعمَّد بلوحة `/admin` (خارج نطاق L2، مقصود، AD-006).

## 3 — تصنيف المستخدمين (كل الحالات الممكنة فعليًا، لا نظرية)

| # | التصنيف | Legacy (`app_subscriptions`) | New (`subscriptions`) | مثال حقيقي من القاعدة | قابل للحدوث؟ |
|---|---|---|---|---|---|
| A | لا Legacy، لا New | لا سجل | لا سجل | مستخدمون 1، 2، 3، 4 | ✅ نعم — لا فعل له علاقة بـL2 |
| B | Legacy فقط (Active) | Active | لا سجل إطلاقًا | **لا يوجد حاليًا بالقاعدة** (كل من عنده Legacy عنده أيضًا سجل New بحالة ما، راجع قسم 2) | ✅ نعم نظريًا — **هذا هو التصنيف الوحيد المؤهَّل فعليًا للترحيل** |
| C | Legacy + New متطابقان (كلاهما فعّال) | Active | Active | مستخدمون 5، 7، 8 | ✅ نعم — لا فعل مطلوب (مُرحَّل بالفعل ضمنيًا أو أُنشئ مباشرة بالنظام الجديد) |
| D | Legacy Active + New Cancelled | Active | **Cancelled** | **مستخدم 6 تحديدًا** | ✅ نعم — **الحالة الحرجة، AD-014 يحكمها حرفيًا: لا فعل، لا استثناء** |
| E | New فقط (بلا Legacy إطلاقًا) | لا سجل | Active أو Cancelled | لا مثال شخصي مباشر اليوم (الأقرب: اشتراك المؤسسة org:3 نفسه، لكنه Subscriber من نوع organization لا user — Legacy أصلًا لا يعرف مفهوم مؤسسة) | ✅ نعم — خارج نطاق L2 كليًا، لا علاقة لـLegacy به |
| F | Legacy Cancelled (بأي حالة New) | **Cancelled** | أي حالة أو لا شيء | لا مثال اليوم (لا صف Legacy واحد بحالة cancelled فعليًا) | ✅ ممكن نظريًا عبر تعديل يدوي بلوحة الإدارة — **لو حدث: لا فعل، Legacy نفسه يقول "لا وصول"، لا شيء يُرحَّل** |
| G | Legacy مُحذوف يدويًا (كان له صف، حُذف من لوحة الإدارة) | لا أثر إطلاقًا | حالته أيًا كانت | لا مثال اليوم | ✅ ممكن (زر Delete موجود بـ`AppSubscriptionResource`) — **يُعامَل مطابقًا للتصنيف A/E (لا سجل Legacy = لا شيء يُرحَّل)، بصرف النظر عن كونه محذوفًا أو لم يوجد أصلًا — Migration لا يملك ولا يحتاج يملك ذاكرة عن حذف سابق** |
| H | مستخدم له وصول شخصي + مؤسسي معًا بالنظام الجديد | Active أو لا شيء | Active (شخصي) + Access منفصل عبر مؤسسة | مستخدمون 7، 8 (Access عبر org:3 بالإضافة لاشتراكهم الشخصي) | ✅ نعم — **بلا أثر على قرار الترحيل الشخصي** — L2 يرحّل فقط البُعد الشخصي (Legacy لا يعرف مؤسسات أصلًا)، البُعد المؤسسي غير ذي صلة بمدخلات L2 أو مخرجاته إطلاقًا |

**حالات ذُكرت بطلبك واتضح أنها غير قابلة للحدوث فعليًا بالـSchema الحالي (تُوثَّق لا تُخترَع):**
- **"Legacy Inactive"** — Schema الحالي لا يملك حالة "Inactive" منفصلة عن "Cancelled" أصلًا لـ`AppSubscription` (خياران فقط: `active`/`cancelled`، مؤكَّد من `AppSubscriptionResource::form()`). أي إشارة لـ"Legacy Inactive" بأي وثيقة سابقة تُقرَأ كمرادف لـ"Legacy Cancelled" (الصف F أعلاه)، لا حالة ثالثة مستقلة.
- **صف كان مذكورًا سابقًا بـ`legacy-subscription-l1-spec.md` قسم E ("Active/None لكن تاريخ إلغاء موجود")** — أُكِّد سابقًا هناك، وأُعيد تأكيده هنا بفحص مباشر: **غير قابل للحدوث** لأن `Subscription` لا يُحذَف فعليًا أبدًا بأي كود موجود (فقط `status` يتغيّر) — لا "تاريخ إلغاء بلا سجل" ممكن بنيويًا.

## 4 — Migration Eligibility Rules (صريحة، لا `active()->exists()`)

**القاعدة الوحيدة، بلا استثناء:**

```text
مؤهَّل للترحيل  ⟺  Legacy.status = 'active'  AND  لا يوجد أي سجل New بأي حالة إطلاقًا لنفس (user, item)

غير مؤهَّل، بلا فعل، بصرف النظر عن حالة Legacy  ⟺  يوجد أي سجل New بأي حالة إطلاقًا (active أو cancelled)
```

**الفحص الإلزامي بالكود (Pseudocode تنفيذي، لا نثري):**
```php
// خطوة ١ — هل يوجد أي سجل New إطلاقًا؟ (بصرف النظر عن الحالة)
$existingAny = $user->marketplaceSubscriptions()
    ->where('marketplace_item_id', $item->id)
    ->exists();               // ← exists() الخام، بلا ->active()

if ($existingAny) {
    // توقف هنا. لا قراءة لحالته حتى. وجوده كافٍ لمنع أي فعل.
    return MigrationOutcome::Skipped(reason: 'سجل جديد موجود بأي حالة — قرار مستخدم مسجَّل، لا يُمَس');
}

// خطوة ٢ — فقط الآن، تحقق من Legacy
if ($legacyRecord->status !== 'active') {
    return MigrationOutcome::Skipped(reason: 'Legacy نفسه غير فعّال');
}

// خطوة ٣ — المؤهَّل الوحيد
return MigrationOutcome::Eligible;
```

**الفرق الحاسم عن الكود الحالي بـ`MarketplaceBackfillFreeAccess`:** الفحص الحالي (`->active()->exists()`) يسأل "هل يوجد سجل *فعّال* الآن؟" — لو الجواب لا (سواء لأنه لا يوجد سجل إطلاقًا، أو لأنه موجود لكن `cancelled`)، يُنشئ سجلًا جديدًا في الحالتين. الفحص المصحَّح أعلاه يسأل سؤالًا مختلفًا تمامًا: "هل يوجد سجل **بأي حالة**؟" — لو الجواب نعم (بصرف النظر عن كونه فعّال أو ملغى)، **لا فعل إطلاقًا**. هذا يحوّل تصنيف D (قسم 3) من "مؤهَّل خطأً" إلى "غير مؤهَّل بشكل صريح وآمن".

**تطبيق على البيانات الفعلية اليوم (قسم 2):**

| المستخدم | مؤهَّل؟ | السبب |
|---|---|---|
| 5 | ❌ لا (سجل New موجود، Active) | تصنيف C |
| 6 | ❌ لا (سجل New موجود، Cancelled) | **تصنيف D — بالضبط الحالة اللي AD-014 صُمِّمت لمنعها** |
| 7 | ❌ لا (سجل New موجود، Active) | تصنيف C |
| 8 | ❌ لا (سجل New موجود، Active) | تصنيف C |
| 1، 2، 3، 4 | ❌ لا (لا Legacy إطلاقًا) | تصنيف A |

**النتيجة الفعلية لو شُغِّل L2 اليوم على قاعدة البيانات الحالية: صفر سجل مؤهَّل للترحيل.** كل مستخدم Legacy-active إما مُرحَّل بالفعل ضمنيًا (C) أو محميًا صراحة بـAD-014 (D). **هذا ليس فراغًا بالتصميم — هذا دليل إن منطق الأهلية المصحَّح يعمل صح على البيانات الحقيقية الوحيدة المتاحة للاختبار.** أي بيانات إنتاج حقيقية مستقبلية (لو رُبِطت هذي الأداة يومًا بـhw.sa الفعلية) قد تحتوي فعليًا حالات تصنيف B — الأداة مصمَّمة لتلك اللحظة، لا لبيانات التطوير الحالية.

## 5 — Explicit User Intent — كيف يستحيل بنيويًا انتهاك قرار المستخدم

أربعة ضمانات، كل واحدة مستقلة عن الأخرى (Defense in Depth):

1. **فحص `exists()` الخام (قسم 4)** — خط الدفاع الأول، يمنع أي فعل لو وُجد أي سجل New مهما كانت حالته.
2. **لا استدعاء لـ`SubscriptionService::subscribeUserToFreeItem()` مباشرة من أداة الترحيل بلا فحص مسبق مستقل.** هذا اكتشاف تقني مهم أثناء إعداد هذي الوثيقة: **`subscribeUserToFreeItem()` نفسها تحتوي فرعًا (`$wasInactive`) يُعيد تفعيل أي اشتراك موجود غير فعّال تلقائيًا** — هذا سلوك **صحيح ومقصود** لسياق استخدامها الأصلي (مستخدم يضغط زر "فعّل" مرة أخرى بنفسه، فعل واعٍ صريح منه هو شخصيًا). **لو استُدعيت هذي التابع من أداة Migration بلا فحص `exists()` مستقل قبلها، ستُعيد تفعيل اشتراكات ملغاة تلقائيًا — بالضبط نفس خطر AD-014، لكن بمصدر مختلف (الخدمة نفسها لا الأداة).** لذلك: **قاعدة معمارية إلزامية لهذي المرحلة تحديدًا** — أداة الترحيل تستدعي `subscribeUserToFreeItem()` فقط بعد تأكيد صريح ومستقل إن لا سجل New موجود إطلاقًا (تصنيف B فقط) — لا تعتمد على أن التابع "آمن بذاته"، لأنه ليس مصمَّمًا ليكون آمنًا لسياق Migration، بل لسياق فعل مستخدم مباشر.
3. **AuditLog كخط دفاع ثانٍ اكتشافي** (لا وقائي) — أي إعادة تفعيل تحدث رغم الضمانات أعلاه (خطأ برمجي مستقبلي مثلًا) تترك أثرًا بمصدر مميَّز (قسم 8) يمكن اكتشافه بمراجعة لاحقة، لا تمر بصمت.
4. **Idempotency (قسم 6)** — حتى لو أُعيد تشغيل الأداة عن طريق الخطأ عدة مرات، لا تراكم أفعال يمكن أن "يتسلل" منها انتهاك.

## 6 — Idempotency

**المطلوب:** تشغيل الأمر مرتين متتاليتين (بلا أي تغيير بالبيانات بينهما) يُنتج **نفس النتيجة بالضبط** بالمرة الثانية — صفر أثر إضافي.

**كيف يتحقق هذا تلقائيًا من تصميم قسم 4 نفسه (لا آلية إضافية منفصلة مطلوبة):**
- أي مستخدم رُحِّل بالتشغيلة الأولى (تصنيف B → أصبح C بعدها) **لن يُعاد فحصه كمؤهَّل بالتشغيلة الثانية** — فحص `exists()` يجده الآن ضمن "يوجد سجل New" فيتوقف فورًا (نفس منطق تصنيف C).
- لا حاجة لجدول "تتبع تشغيلات سابقة" منفصل — حالة قاعدة البيانات نفسها (وجود/غياب سجل New) هي مصدر الحقيقة الوحيد لتحديد "هل رُحِّل هذا سابقًا؟"، بلا حالة خفية إضافية يمكن أن تنحرف عن الواقع.

**الضمان الصريح المطلوب اختباره (قسم 13):** تشغيلتان متتاليتان على نفس البيانات → نفس العدد بالضبط بالتشغيلة الأولى فقط، صفر بالثانية، صفر Duplicate Subscription، صفر Duplicate AccessAssignment.

## 7 — Migration Decision Matrix

| # | Current State (Legacy → New) | Migration Action | Expected Result | Audit Event المسجَّل |
|---|---|---|---|---|
| 1 | Active → لا سجل (تصنيف B) | ترحيل عبر `SubscriptionService::subscribeUserToFreeItem()` بعد فحص `exists()` مستقل مسبق | `Subscription` جديد (status=active) + `AccessAssignment` جديد (status=active) | `subscription_created` + `subscription_activated` + `access_granted` (بنفس آلية الخدمة الحالية، بلا تعديل عليها) |
| 2 | Active → Active (تصنيف C) | لا فعل | بلا تغيير | لا حدث جديد (الحدث الأصلي مسجَّل مسبقًا وقت الإنشاء الحقيقي) |
| 3 | Active → **Cancelled** (تصنيف D) | **لا فعل — ممنوع بنيويًا (قسم 4/5)** | بلا تغيير، الإلغاء يبقى قائمًا | لا حدث — **لكن يُسجَّل بتقرير Dry Run/تنفيذ الأداة كـ"Explicitly Skipped — User Cancelled"، ليكون مرئيًا لا صامتًا** |
| 4 | لا سجل → أي شيء (تصنيف A/E) | لا فعل — خارج نطاق L2 | بلا تغيير | لا حدث |
| 5 | Cancelled → أي شيء (تصنيف F) | لا فعل — Legacy نفسه لا يدّعي وصولًا فعّالًا | بلا تغيير | لا حدث |
| 6 | صف Legacy محذوف يدويًا سابقًا (تصنيف G) | يُعامَل مطابقًا للصف 4 — لا فرق بالفعل عن "لا سجل من الأساس" | بلا تغيير | لا حدث |

## 8 — Auditability

**كل عملية ترحيل ناجحة (الصف 1 فقط بالجدول أعلاه) تُسجِّل بالضبط نفس الأحداث الثلاثة التي تُسجِّلها `SubscriptionService::subscribeUserToFreeItem()` أصلًا اليوم لأي فعل مستخدم مباشر — بلا حدث جديد يُضاف لقائمة AD-001 المغلقة (ثمانية أحداث، لا تاسع).**

**التمييز المطلوب بين "فعل مستخدم مباشر" و"فعل ترحيل آلي" (توصية L1 Spec قسم D، تُطبَّق هنا فعليًا):**
`audit_logs.metadata` (عمود `json` موجود بالفعل بالـSchema، غير مُستغَل بالكامل اليوم) يحمل بكل صف ناتج عن L2 تحديدًا (عكس الغياب الافتراضي لهذي المفاتيح بأي فعل مستخدم مباشر) — **هذا لا يضيف عمودًا جديدًا للجدول ولا يغيّر Schema، يستخدم العمود الموجود أصلًا بالطريقة المصمَّم لها:**

```json
{
  "source": "legacy_migration_l2",
  "migration_run_id": "l2-2026-08-10-run-1",
  "legacy_record_id": 12,
  "legacy_app_key": "marefa",
  "reason": "legacy_active_no_new_record"
}
```

**هذا التركيب هو أساس Migration Provenance (§11 المُحدَّث بعد ملاحظتك الأخيرة):** `migration_run_id` واحد لكل تشغيلة فعلية (يُولَّد مرة واحدة أول ما يبدأ الأمر، يُستخدَم لكل الصفوف الناتجة عن نفس التشغيلة)، `legacy_record_id` يربط صراحة بسجل `app_subscriptions` المصدر (لا استنتاج لاحق بالتخمين من `user_id`/`app_key`).

**السجلات "المتخطّاة" (تصنيف D تحديدًا) لا تُسجَّل بـ`audit_logs`** — الجدول مخصَّص لأفعال حدثت فعليًا (AD-001)، لا لقرارات "عدم الفعل". بدلًا من ذلك، **تقرير تنفيذ الأمر نفسه** (المطبوع بالـConsole + محفوظ كملف Log منفصل خارج قاعدة البيانات، قسم 9) هو مكان توثيق "مين تخطّيناه ولماذا" — تمييز متعمَّد بين "ماذا حدث بالنظام" (audit_logs) و"ماذا قرر الأمر نفسه ولماذا" (تقرير التنفيذ).

**ما يُسجَّل لكل عملية فعلية (بالضبط كما هو اليوم، بلا تغيير على `SubscriptionService`):** الحدث، الفاعل (`actor_user_id` = المستخدم نفسه صاحب الاشتراك المُرحَّل — **ليس** حساب إداري أو نظامي، لأن الترحيل يمثّل حقه الفعلي الموجود مسبقًا لا فعلًا إداريًا جديدًا)، الموضوع (`subject_type`/`subject_id` = السجل الجديد)، الوقت (`created_at` تلقائي).

### 8-1 — هل L2 يعتمد على تاريخ `audit_logs` السابق؟ (مُضاف بعد حادثة فقدان 30 سجل)

**ثلاث طبقات منفصلة تمامًا يجب عدم خلطها — لكل واحدة اعتماديتها الخاصة على التاريخ:**

| الطبقة | تعتمد على تاريخ `audit_logs` **قبل** L2؟ | الأثر الفعلي لفقدان الـ30 سجلًا |
|---|---|---|
| **١. Migration Eligibility (§4)** | ❌ **لا إطلاقًا** — يعتمد فقط على عمود `subscriptions.status` الحالي (`exists()`/قيمته) و`app_subscriptions.status` — كلاهما بيانات حالة حيّة بجداول أخرى، لا علاقة لهما بـ`audit_logs` | **صفر أثر** — منطق الأهلية سليم بمعزل كامل عن أي فجوة بتاريخ Audit |
| **٢. Rollback Provenance (§11)** | ❌ **لا** — يبحث فقط عن أحداث بـ`metadata.source=legacy_migration_l2`، وهي أحداث **ستُنشئها L2 نفسها من الآن فصاعدًا**، لا شيء بالتاريخ القديم يحمل هذا الوسم أصلًا (المفهوم نفسه لم يكن موجودًا وقت الـ30 سجلًا المفقودة) | **صفر أثر** — أي Rollback مستقبلي يعتمد فقط على أحداث وُلِدت بعد التصحيح، بجدول محمي الآن (`audit-log-integrity-hardening.md`) |
| **٣. Parity Check — `Cancelled users incorrectly reactivated` (§9)** | ✅ **جزئيًا نعم** — هذا الفحص تحديدًا يبحث عن زوج (`SubscriptionCancelled` قديم ← `SubscriptionCreated/Activated` لاحق بمصدر L2) بتاريخ `audit_logs`. لو كان حدث الإلغاء **الأصلي** لمستخدم معيّن ضمن الـ30 المفقودة، هذا الفحص **لن يستطيع اكتشاف** إعادة تفعيل لذاك المستخدم تحديدًا عبر أثر Audit — **لكن** فحص الأهلية بالطبقة ١ (`exists()` على `subscriptions.status` الحالي) **يبقى يمنع الترحيل أصلًا بغض النظر عن أي فجوة Audit**، لأنه لا يقرأ `audit_logs` إطلاقًا | **محدود، غير حرج** — خط الدفاع الأول (الأهلية) سليم دائمًا؛ هذا الفحص خط دفاع **ثانٍ اكتشافي** فقط (كما وُصِف أصلًا بقسم ٥.٣)، فقدان قدرته الرجعية لا يعني فقدان الحماية الفعلية |

**الخلاصة العملية:** **L2 صحيحة ومكتملة الأمان حتى ببيئة بدأ فيها تاريخ Audit ناقصًا** — لأن قرار "هل أرحّل هذا المستخدم؟" لا يُبنى على `audit_logs` إطلاقًا (يُبنى على حالة `subscriptions` الحيّة، وهي سليمة 100%، مؤكَّدة بـ`audit-log-integrity-incident-report.md`). الفجوة الوحيدة الحقيقية: تدقيق رجعي لحوادث *قبل* هذا التاريخ (2026-08-12) عبر أثر Audit تحديدًا — لا تُصلَح، ولا تُختلَق بيانات لتعويضها (بقرارك الصريح)، فقط تُوثَّق كحد معروف.

## 9 — Subscription/Access Parity Check

أداة جديدة، بنفس فلسفة `MarketplaceCatalogParityCheck` (Phase 1a) لكن لبيانات الاشتراك:

**الاسم المقترح:** `php artisan marketplace:subscription-parity-check`

**المخرجات المطلوبة (كما طلبت حرفيًا، محسوبة من الحالة الفعلية للبيانات):**
```text

  → Already synced (New Active):       3   (تصنيف C: users 5, 7, 8)

Duplicate subscriptions:                0   (فحص: أي (subscriber, item) بأكثر من صف — لا حالة كهذي، UNIQUE constraint موجود أصلًا بـSchema)
```

## 10 — Dry Run

**إلزامي قبل أي تنفيذ فعلي — لا استثناء.**

```bash
php artisan marketplace:migrate-legacy-subscriptions --dry-run
```

**المخرجات (بلا أي تعديل على قاعدة البيانات، مؤكَّد بأنه Read-only عبر عدم فتح أي `DB::transaction` بمسار Dry Run إطلاقًا — لا `--dry-run` كعلم يُمرَّر لنفس الكود الكاتب، بل مسار كود منفصل تمامًا لا يستدعي أي دالة كتابة):**
```text
سيُرحَّل (Eligible):
  [لا أحد اليوم]

لن يُرحَّل — سجل New موجود (Skipped: Existing Record):
  user 5  (New status: active)
  user 6  (New status: cancelled)  ← AD-014
  user 7  (New status: active)
  user 8  (New status: active)

لا علاقة بـL2 (لا سجل Legacy):
  users 1, 2, 3, 4
```

**الفحص المطلوب بالاختبارات (قسم 13):** مقارنة `COUNT(*)` على `subscriptions`/`access_assignments`/`audit_logs` قبل وبعد تشغيل `--dry-run` — يجب يكون **متطابقًا تمامًا (صفر فرق)** بلا استثناء واحد.

## 11 — Rollback

**لا افتراض إن الحذف تراجع آمن — كما طلبت صراحة.** وبعد ملاحظتك الأخيرة، إضافة إلزامية: **Rollback لا يجوز يُلغي حالة تغيّرت بفعل المستخدم أو أي عملية تشغيلية لاحقة بعد الترحيل — حتى لو كان الإلغاء (لا الحذف) هو الأسلوب المُستخدَم.** "أسلوب آمن للتراجع" و"هل يجوز التراجع أصلًا الآن" سؤالان منفصلان — القسم السابق أجاب الأول فقط، هذا التحديث يضيف الثاني.

### Migration Provenance — كيف نعرف "هذا من L2 تحديدًا" ومتى لا يزال آمنًا لمسه

**المبدأ:** كل `Subscription` أنشأته L2 له سجل `AuditLog` مصدر (`event=SubscriptionCreated`, `metadata.source=legacy_migration_l2`, راجع §8 المُحدَّث). **Rollback لسجل معيّن مسموح فقط لو لم يحدث أي `AuditLog` آخر على نفس الموضوع (`subject_type`+`subject_id`) بعد سجل المصدر هذا.** أي حدث لاحق — إلغاء بفعل المستخدم، إعادة تفعيل، أي فعل مُسجَّل — يعني الحالة الحالية **لم تعد** الحالة التي تركتها L2، فتصبح خارج نطاق Rollback تمامًا.

**الفحص الإلزامي (Pseudocode تنفيذي — مُصحَّح أثناء التنفيذ الفعلي، راجع الملاحظة تحته):**
```php
// نجمع كل أحداث L2 نفسها على هذا الموضوع (قد تكون أكثر من حدث واحد —
// SubscriptionCreated ثم SubscriptionActivated، كلاهما بنفس metadata.source)
$migrationEvents = AuditLog::where('subject_type', Subscription::class)
    ->where('subject_id', $subscription->id)
    ->where('metadata->source', 'legacy_migration_l2')
    ->get();

if ($migrationEvents->isEmpty()) {
    return RollbackOutcome::Refused('هذا السجل لم يُنشأ بواسطة L2 أصلًا — Rollback لا يخصّه');
}

// نأخذ آخر حدث بينها (id الأكبر)، لا أولها — الاعتماد على ترتيب id
// التصاعدي (Append-only، auto-increment) كـ"خط زمني" موثوق.
$lastMigrationEventId = $migrationEvents->max('id');

$laterActivity = AuditLog::where('subject_type', Subscription::class)
    ->where('subject_id', $subscription->id)
    ->where('id', '>', $lastMigrationEventId)
    ->exists();

if ($laterActivity) {
    return RollbackOutcome::Refused('يوجد نشاط لاحق على هذا الاشتراك بعد L2 — قد يكون قرار مستخدم، لا يُلمَس');
}

// آمن — الحالة الحالية لا تزال بالضبط كما تركتها L2
$subscriptionService->cancel($subscription);
```

**خطأ حقيقي اكتُشف وأُصلِح أثناء كتابة اختبار §13 رقم 11b (Control):** النسخة الأولى من هذا الفحص قارنت بأول حدث L2 (`SubscriptionCreated`) فقط. بما إن `subscribeUserToFreeItem()` تكتب حدثين متتاليين على نفس موضوع `Subscription` بعملية الإنشاء الواحدة (`SubscriptionCreated` ثم `SubscriptionActivated`)، كانت النسخة الأولى تعتبر الحدث الثاني (**من نفس عملية L2 نفسها**) "نشاطًا لاحقًا" فترفض Rollback **دائمًا**، حتى باختبار Control بلا أي تدخل مستخدم إطلاقًا. اكتُشف عبر فشل اختبار حقيقي (`test_rollback_succeeds_when_no_later_activity_exists`)، أُصلِح بأخذ **آخر** حدث L2 (`max('id')`) كنقطة البداية، لا أولها.

**افتراض يجب توثيقه صراحة (لا إخفاؤه):** هذا الفحص يعتمد إن `AccessAssignment` الخاص باشتراك شخصي **لا يتغيّر أبدًا إلا عبر فعل مسجَّل على `Subscription` نفسه** (عبر `SubscriptionService::subscribe`/`cancel`، مؤكَّد بـgrep اليوم — لا Filament Resource أو مسار آخر يعدّل `AccessAssignment` مباشرة لاشتراك شخصي). لو استُحدث مستقبلًا مسار كتابة مستقل لـ`AccessAssignment` بمعزل عن `Subscription`، هذا الفحص يجب يُمدَّد ليغطي `subject_type=AccessAssignment` أيضًا — غير مطلوب اليوم لأن المسار غير موجود، لكنه ليس افتراضًا دائمًا.

### جدول السيناريوهات الكامل

| السيناريو | إجراء التراجع الآمن |
|---|---|
| سجل `Subscription` أُنشئ خطأً بواسطة L2، **ولا نشاط لاحق مسجَّل عليه** | **لا حذف.** `SubscriptionService::cancel()` — يمر فحص Provenance أعلاه بنجاح |
| سجل `Subscription` أنشأته L2، **لكن يوجد نشاط لاحق** (المستخدم فعّله بنفسه/ألغاه بنفسه/أي حدث Audit لاحق) | **Rollback مرفوض بنيويًا** — الحالة الحالية نتيجة قرار لاحق، لا نتيجة خطأ L2. لا Cancel، لا أي تعديل. يُبلَّغ فقط، لا يُنفَّذ |
| اكتُشف خطأ جماعي (عدة سجلات، لا سجل واحد) | نفس الفحص، مُطبَّق فرديًا على كل سجل — **لا Rollback جماعي بأمر واحد** (كل سجل مستقل، إلغاؤه الجماعي بأمر واحد يخاطر بإلغاء سجلات صحيحة أو سجلات لها نشاط لاحق ضمن نفس الدفعة) |
| اكتُشف خطأ بأداة الترحيل نفسها (Bug بالكود) قبل أي تشغيل فعلي | لا حاجة Rollback بيانات — Dry Run لم يكتب شيئًا أصلًا. الإصلاح كود فقط |
| فشل جزئي أثناء التنفيذ (انقطاع بمنتصف تشغيلة تضم عدة مستخدمين) | كل مستخدم يُعالَج ضمن `DB::transaction()` مستقلة خاصة به (لا Transaction واحدة ضخمة لكامل الدفعة) — فشل بمنتصف مستخدم واحد لا يترك سجلًا جزئيًا (Subscription بلا AccessAssignment مثلًا)، ولا يمنع باقي المستخدمين من إكمال معالجتهم بنفس التشغيلة |

**لماذا لا حذف مطلقًا:** حذف `Subscription` مُنشأ بالخطأ يُخالف AD-001 (يفقد الأثر التاريخي لحدوث الخطأ نفسه) ويُعيد فتح احتمال تصنيف B لنفس المستخدم بتشغيلة مستقبلية (لأن `exists()` سيعود `false` بعد الحذف) — **الإلغاء لا الحذف يضمن الاستقرار وعدم التكرار معًا.**

## 12 — Production Safety

**افتراض ملزم كما طلبت: بيانات `hw.sa` الحقيقية (لو رُبِطت هذي الأداة بها يومًا) أهم من أي بيانات تطوير محلية.**

| المرحلة | المتطلب |
|---|---|
| **Preconditions** | (أ) L1 مُفعَّلة ومؤكَّدة (لا كتابة جديدة لـLegacy) — محقَّق بالفعل محليًا. (ب) `MarketplaceBackfillFreeAccess` القديم إما مُعطَّل بالكامل أو مُستبدَل رسميًا بأداة L2 المصحَّحة — لا يجوز تعايش الأداتين (Blocking Issue #1 من Integration Readiness Review يجب يُغلَق أولًا). (ج) نسخة احتياطية كاملة من قاعدة البيانات قبل أي تشغيل فعلي |
| **تسلسل التنفيذ الإلزامي (سبع خطوات، بالترتيب، بلا تخطي أو دمج خطوتين)** | **Step 0** — تعطيل/استبدال `MarketplaceBackfillFreeAccess` القديم أولًا (لا تعايش ولو ليوم واحد) → **Step 1** — نشر أداة L2 المصحَّحة → **Step 2** — تشغيل `--dry-run` → **Step 3** — مراجعة بشرية للمخرجات (أنت تحديدًا) → **Step 4** — تنفيذ فعلي (بإذن صريح منفصل لهذي التشغيلة تحديدًا) → **Step 5** — `marketplace:subscription-parity-check` → **Step 6** — تشغيل كامل مجموعة الاختبارات (109+ اختبار قائم + اختبارات L2 الجديدة، §13) |
| **Backup requirements** | نسخة احتياطية لقاعدة البيانات كاملة (لا الجداول المعنية فقط — الفشل قد يمتد لسبب غير متوقَّع) قبل أي تشغيل بدون `--dry-run`، بغض النظر عن حجم البيانات المتوقَّع |
| **Dry Run** | إلزامي، ونتائجه تُراجَع بشريًا (أنت تحديدًا، بناءً على نمط هذا المشروع) قبل أي تشغيل فعلي — لا تشغيل تلقائي متسلسل (`--dry-run` ثم فورًا تشغيل حقيقي بلا مراجعة بينهما) |
| **Approval Gate** | تشغيل فعلي (بلا `--dry-run`) يتطلب تصريحًا صريحًا منفصلًا **لكل تشغيلة**، ليس إذنًا عامًا دائمًا — يطابق نمط الموافقة الصريحة المتكرر بكل مرحلة سابقة بهذا المشروع |
| **Execution** | تشغيل يدوي مباشر (Artisan Command)، لا Job مجدوَل، لا تشغيل تلقائي عند Deploy — قرار بشري واعٍ في كل مرة |
| **Verification** | تشغيل `marketplace:subscription-parity-check` (قسم 9) فورًا بعد أي تنفيذ فعلي — النتيجة المتوقَّعة: `Residual migration gap = 0`، `Cancelled users incorrectly reactivated = 0` |
| **Rollback** | كما بقسم 11 — جاهز وموثَّق **قبل** أي تشغيل فعلي، لا يُرتجَل بعده |

## 14 — لا نخلط L2 مع L3

**مؤكَّد صراحة، مطبَّق حرفيًا بهذي الوثيقة بأكملها:**
- ❌ لا إزالة قراءة من `app_subscriptions` — `DashboardController` يبقى يقرأ منه كما هو تمامًا
- ❌ لا حذف للجدول `app_subscriptions`
- ❌ لا بدء لأي عمل Legacy Retirement (L4)
- ✅ L2 تنتهي بمجرد استقرار `Residual migration gap = 0` عبر أداة Parity Check — لا خطوة إضافية بعدها ضمن هذي الوثيقة

---

## 15 — لا نلمس Core Platform

**فُحِص صراحة أثناء إعداد هذي الوثيقة: هل يوجد اعتماد تقني مباشر يمنع تنفيذ L2 بدون لمس Header/Navigation/Dashboard/بوابة معرفة/Authentication؟**

**الجواب: لا يوجد أي اعتماد كهذا.** كل عمليات L2 (القراءة من `app_subscriptions`، الكتابة عبر `SubscriptionService` الموجود أصلًا، أداة Parity Check الجديدة) مُحتواة بالكامل ضمن طبقة Marketplace (`app/Console/Commands`, `app/Services`) — **صفر ملف بأي من `Http/Controllers` غير Marketplace، `resources/views/layouts`, أو `resources/views/platform/dashboard.blade.php` يحتاج لمسًا لتنفيذ L2.** لا Architecture Conflict يُسجَّل هنا لعدم وجود واحد فعليًا.

# READY FOR L2 IMPLEMENTATION

**بشرط تنفيذي واحد صريح غير قابل للتفاوض، يجب يكون الخطوة العملية الأولى من التنفيذ نفسه (Step 0)، لا خطوة لاحقة:** استبدال/تعطيل `MarketplaceBackfillFreeAccess` الحالي (بالمنطق الخاطئ) بأداة L2 الجديدة المصمَّمة بهذي الوثيقة — **لا تعايش بين الأداتين ولو ليوم واحد.**
