# Hukm w Rakam — Marketplace UI Design System

**الحالة:** مسودة للمراجعة — بدون أي تنفيذ. لا كود، لا Components فعلية، لا Pages، لا تعديل على أي ملف تشغيلي، لا تغيير على Core Platform.
**المرجعان الملزمان:** `docs/marketplace-architecture-blueprint.md` (Target Architecture معتمدة) و`docs/marketplace-product-ux-architecture.md` (Product/UX Architecture معتمدة بقراراتها الستة الأخيرة). هذي الوثيقة لا تُعيد فتح أي قرار منتجي/معماري سابق — فقط تترجم القرارات المعتمدة (آلة حالة CTA، حالات Access، Rules-based Recommendations، عدم وجود Premium حقيقي، إلخ) إلى نظام بصري.

**قاعدة التصميم الحاكمة (كما طُلب):**
> النظام **Data-driven**، لا Hardcoded حول الثمانية عناصر الحالية. كل مكوّن يُعرَّف بمدخلاته (`type`, `status`, `availability`, `billing_model`, `subscription state`, `access state`, `organization context`, `user role`, `entitlements`) — لا بأي اسم/محتوى تطبيق محدد. إضافة تطبيق رقم 9 أو أول Integration حقيقي **لا تتطلب مكوّنًا جديدًا**، فقط بيانات جديدة تُغذّي نفس المكوّنات.

**قاعدة المحتوى الحاكمة:** أي حالة بصرية لا تخصّ بيانات حقيقية موجودة اليوم (Reviews, Ratings, Pricing حقيقي, Checkout, أرقام استخدام) **تُصمَّم كـ Empty State أو تُترك غير مُفعَّلة بصريًا** — لا حشو بصري وهمي بأي شكل، ولا حتى بصورة "مثال توضيحي". هذا امتداد مباشر لقرارك الثالث بالرسالة الأخيرة (Premium بلا محتوى وهمي).

**التموضع البصري المطلوب:** *Professional Platform Ecosystem*، لا *Application Store*. الفرق هنا ليس شعارًا — هو قرارات ملموسة تتكرر بكل قسم أدناه: كثافة معلومات تخدم قرارًا (لا شبكة أيقونات ملوّنة للتصفح السريع)، استخدام الذهبي كلون تمييز نادر لا كخلفية متكررة، غياب كامل لعناصر App Store التقليدية (نجوم/تقييمات/عداد تنزيلات) — وهذا الغياب هنا ليس قرار تصميم فقط، هو **انعكاس صادق لغياب البيانات نفسها**.

## 0. User-Facing Simplicity — طبقة الترجمة الإلزامية

**القاعدة:** Complex Architecture ≠ Complex UX. المعمارية معقّدة بما يكفي لحماية النظام وتوسيعه — لكن أي مصطلح داخلي بالمعمارية **ممنوع يظهر حرفيًا بأي نص واجهة**، بلا استثناء واحد، بأي شاشة موثّقة بهذي الوثيقة أو أي وثيقة لاحقة.

**المصطلحات الممنوعة حرفيًا بالواجهة:** `MarketplaceItem` · `Subscription` · `AccessAssignment` · `Entitlement` · `SubscriptionSeat` · `Tenant` · `Polymorphic Subscriber` · `Billing Model` · `Active Organization Context`.

### جدول الترجمة الإلزامي (يُستخدم حرفيًا بكل نص واجهة بهذا المشروع)
| المصطلح التقني | الترجمة البشرية بالواجهة |
|---|---|
| Subscription (شخصي) | "اشتراكك" |
| Subscription (مؤسسي) | "اشتراك المؤسسة" |
| AccessAssignment (نشط) | "لديك وصول" |
| AccessAssignment (غير نشط) | "ليس لديك وصول" / "بانتظار الوصول" |
| Entitlement | "المزايا المتاحة لك" |
| SubscriptionSeat | "مقعد مستخدم" |
| Active Organization Context | "المؤسسة الحالية" |
| Request Access | "طلب الوصول" |
| Ask Admin | "طلب من مدير المؤسسة" |
| Tenant / Polymorphic Subscriber | لا يظهران كمفهوم إطلاقًا — الواجهة تقول "أنت" أو تسمي المؤسسة بالاسم مباشرة |
| Billing Model | لا يظهر كمصطلح — ينعكس ضمنيًا فقط بتصنيف ظاهر مثل "شخصي"/"للمؤسسة" |

**قاعدة تحقق لأي مكوّن جديد لاحقًا:** قبل اعتماد أي نص واجهة جديد، يُفحَص مقابل هذا الجدول — لو المصطلح التقني يظهر حرفيًا (حتى بتلميح، مثال: "Access Assignment معلَّق")، النص مرفوض ويُعاد صياغته.

## 1. Design Principles

خمسة مبادئ، كل واحد يُختبر ضد قرار تصميم فعلي لاحقًا بالوثيقة، لا شعارات عامة:

1. **الوضوح قبل الجمال (Clarity over Decoration).** أي عنصر بصري يجب يخدم قرارًا (هل أشترك؟ هل أربط؟ هل أطلب؟) — لا عنصر زخرفي بلا وظيفة.
2. **الصدق البصري (Visual Honesty).** حالة "قريبًا" تبدو مختلفة بصريًا عن حالة "متاحة" بوضوح كافٍ يمنع أي التباس، لا فرق شكلي طفيف مموَّه بلون قريب.
3. **الكثافة المدروسة (Deliberate Density).** منصة Enterprise لمهنيين (محامين/محاسبين) تتحمّل كثافة معلومات أعلى من تطبيق استهلاكي — لكن الكثافة تُدار بتسلسل هرمي واضح (Typography Hierarchy)، لا ازدحام.
4. **الاتساق عبر الأنواع (Consistency across Types).** Application وIntegration وService لهم هوية بصرية فرعية مختلفة (قسم ٣٧) لكن ضمن نفس اللغة البصرية الأم — المستخدم يتعرّف فورًا إنه "بنفس المنصة" حتى وهو بشاشة نوع مختلف تمامًا.
5. **البيانات تقود الحالة، لا العكس (Data-driven States).** أي حالة بصرية (لون Badge، نص CTA، ظهور/إخفاء قسم) نتيجة مباشرة لحقل بيانات حقيقي — لا حالة "افتراضية جميلة" بلا مصدر بيانات وراءها.

## 2. Visual Direction

**الاتجاه:** Enterprise حديث بهوية عربية أصيلة — أقرب لـ Linear/Notion بالانضباط والمساحات البيضاء، وأقرب لمنصات Enterprise SaaS خليجية جادة (لا Consumer Apps) بكثافة المعلومات والجدية البصرية. **ليس** أسلوب App Store (بطاقات ملونة متساوية بلا تراتبية، أيقونات كبيرة بلا سياق نصي كافٍ، شارات تقييم/تنزيل بارزة).

**كيف يظهر هذا عمليًا (مقارنة مباشرة بالكود الحالي كنقطة انطلاق موثّقة، لا افتراض):**

| عنصر | نمط App Store (مرفوض) | نمط Hukm w Rakam (معتمد، ويطابق الاتجاه الحالي فعليًا بالكود) |
|---|---|---|
| البطاقة | أيقونة كبيرة + اسم فقط، بلا سياق قرار | أيقونة + اسم + Tagline + وصف + حالة — قرار كامل بمساحة واحدة (مطابق لـ`service-card.blade.php` الحالي) |
| الألوان | ألوان متعددة زاهية لكل تطبيق (تمييز بصري تسويقي) | لوحة موحّدة (Brand Green محوري، Gold للتمييز النادر فقط) — كل العناصر بنفس الهوية، الفرق بالمحتوى لا باللون |
| الحالة | نجوم/تقييم بارز أعلى البطاقة | Badge نصي صريح بحالة حقيقية فقط (متاحة/قريبًا/مفعّل لديك) |
| الحركة | Bounce/Scale احتفالية | `hover:-translate-y-1`, `transition-all duration-200` — حركة هادئة تدل على تفاعلية، لا احتفال |

## 3. Brand Application

الالتزام الكامل بالهوية الرسمية المرفقة (Hokm w Rakam Brand Guidelines) وبما هو مطبَّق فعليًا بالكود اليوم (`tailwind.config.js`) — لا هوية جديدة تُخترع بهذي الوثيقة. Marketplace **جزء من** حكم ورقم بصريًا، لا علامة فرعية بهوية مستقلة (متسق مع "Marketplace طبقة داخل حكم ورقم، لا كيان منفصل").

**قواعد تطبيق ملموسة للـ Marketplace تحديدًا:**
- شعار حكم ورقم فقط — لا شعار "Marketplace" منفصل، لا أيقونة متجر عامة (سلة تسوق، إلخ) كهوية للقسم.
- الأخضر (`brand`) هو اللون المحوري لكل عناصر التفاعل الإيجابي (CTA أساسي، حالة "متاحة/مفعّل لديك"). الذهبي (`gold`) **حصريًا** لعناصر تمييز نادرة (Badge "مجاني"، لمسات محدودة) — لا يُستخدم كخلفية واسعة أو لون متكرر، حفاظًا على طابعه كإشارة، لا كديكور (هذا موثّق فعليًا كسلوك حالي بالكود: `bg-forest` للـ"مجاني" لا `gold` بمعظم الأماكن، و`gold` محجوز لحالات "قريبًا" فقط).
- الأسود/الرمادي الغامق (Forest/Maroon) لخلفيات الأقسام التعريفية الكبيرة (Hero) — كما هو مطبَّق فعليًا (`bg-gradient-to-b from-forest to-brand-800`).

## 4. Color System

اللوحة **موجودة فعليًا** بـ`tailwind.config.js` — هذي الوثيقة تُقنِّن استخدامها الدلالي (Semantic Mapping) للـ Marketplace تحديدًا، لا تضيف ألوانًا جديدة.

### اللوحة الأساسية (Source of Truth: `tailwind.config.js`)
| الاسم | القيم | الاستخدام الدلالي بالـ Marketplace |
|---|---|---|
| `brand` (أخضر) | 50→900، محوره `brand-500 #198754` | الفعل الإيجابي، الحالة "متاحة/نشطة"، الروابط، الحدود التفاعلية |
| `gold` | 50→700، محوره `gold-500 #F6B41B` | تمييز نادر فقط: Badge "قريبًا" (خلفية فاتحة `gold-50`/نص `gold-700`)، لا استخدام واسع |
| `forest` | لون واحد `#00793A` | خلفيات Hero غامقة، Badge "مجاني" (خلفية صلبة) |
| `maroon` | 50→800، محوره `maroon-700 #53190D` | **غير مستخدم حاليًا بالـ Marketplace** — محجوز لحالات تحذير/خطورة عالية إن احتاجتها المؤسسة لاحقًا (مثال مستقبلي: حالة اتصال Integration معطوبة) — لا استخدام قبل حاجة حقيقية |
| `cream` | لون واحد `#FBF3EA` | خلفيات أقسام تعريفية هادئة (مطابق لاستخدام قسم "التكامل الذكي" الحالي) |
| Gray scale (Tailwind الافتراضي) | `gray-50`→`gray-900` | النصوص الثانوية، الحدود، الخلفيات المحايدة — أغلب المساحة البصرية فعليًا |

### خريطة دلالية إلزامية (Semantic Roles) — تُستخدم بكل مكوّن بدل الإشارة المباشرة للون
هذا الجدول هو العقد الفعلي — أي مكوّن لاحق يُبنى يُشير لهذي الأدوار، لا لاسم اللون مباشرة، لتفادي تشتت القرار البصري لاحقًا:

| الدور الدلالي | اللون | يُستخدم لـ |
|---|---|---|
| `state-active` | `brand-600` خلفية / `brand-700` نص | مفعّل لديك، متصل (Integration)، Access نشط |
| `state-available` | `brand-50` خلفية / `brand-700` نص، حدّ `brand-500` | متاح لكن غير مشترك بعد |
| `state-pending` | `gold-50` خلفية / `gold-700` نص | قريبًا، قيد المراجعة (Lifecycle)، قيد الطلب (Service) |
| `state-free` | `forest` خلفية صلبة / أبيض نص | Badge "مجاني" فقط |
| `state-attention` | `maroon` نطاق (محجوز) | خطأ اتصال/تعليق وصول — **لا استخدام قبل وجود حالة حقيقية تتطلبه** |
| `state-neutral-disabled` | `gray-100` خلفية / `gray-400` نص | غير متاح للسياق الحالي (دور/صلاحية لا تدعمه) |

## 5. Typography

**موجودة فعليًا:** `Tajawal` (نص عربي أساسي) + `Poppins` (خط عرض/Display، للأرقام والعناوين اللاتينية) عبر `fontFamily.sans` و`fontFamily.display` — لا خط جديد.

| المستوى | الحجم (Tailwind) | الاستخدام |
|---|---|---|
| Display | `text-4xl` (36px) | عنوان Hero رئيسي فقط (صفحة رئيسية Marketplace) |
| H1 | `text-2xl` (24px) | عنوان صفحة (Browse, تفاصيل عنصر) |
| H2 | `text-lg` (18px) بـ`font-bold` | عناوين أقسام داخل الصفحة ("تطبيقاتي"، "مكتبي") |
| Body | `text-sm` (14px) | نص الوصف الأساسي بكل مكان — الحجم المهيمن فعليًا بالكود الحالي |
| Caption/Meta | `text-xs` (12px) | Tagline، تواريخ، نصوص ثانوية |
| Badge/Micro | `text-[11px]`–`text-[10px]` | نص داخل Badges فقط — تحت الحد الأدنى المعتاد لكن مقبول لأنه مساحة محدودة جدًا ومُدعَّم بلون خلفية واضح |

**قاعدة وزن الخط:** `font-bold` للعناوين وأسماء العناصر فقط، `font-medium` لأي نص تفاعلي (روابط/أزرار)، `font-normal` (افتراضي) للوصف. لا استخدام `font-black`/أوزان إضافية — غير موجودة أصلًا بإعداد الخط الحالي.

## 6. Spacing System

مبني على مقياس Tailwind الافتراضي (4px base) — **مُلاحَظ فعليًا بالكود** بأنماط متكررة تُقنَّن هنا كمعيار Marketplace:

| الاستخدام | القيمة الملاحَظة فعليًا | القاعدة |
|---|---|---|
| تباعد داخلي لبطاقة | `p-5`–`p-7` | البطاقات الأكثر أهمية (متاحة) تاخذ `p-7`، الثانوية `p-5` |
| تباعد بين عناصر شبكة | `gap-5`–`gap-6` | شبكات البطاقات |
| تباعد رأسي بين أقسام صفحة | `py-12`–`py-20` (يزيد مع أهمية القسم واتساعه) | Hero أعرض من قسم فرعي |
| تباعد أفقي حاوية | `px-4 sm:px-6 lg:px-8` | ثابت بكل الصفحات — لا تغيير |
| عرض حاوية أقصى | `max-w-4xl` (نص/Hero مضغوط) / `max-w-6xl` (شبكات) / `max-w-7xl` (تخطيطات عريضة كالفوتر) | حسب كثافة المحتوى |

**قاعدة جديدة تُضاف هنا (لم تكن موثّقة سابقًا):** أي مكوّن جديد بالـ Marketplace (Integration/Service Cards، Subscription Table، إلخ) **يلتزم بنفس القيم أعلاه حرفيًا** — لا مقياس تباعد موازٍ يُخترع لمكوّن جديد.

## 7. Grid

- **شبكة البطاقات (Application/Integration/Service):** `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` — موجودة فعليًا، تبقى المعيار لكل أنواع البطاقات الثلاثة دون استثناء (اتساق عبر الأنواع، مبدأ ٤).
- **شبكة تفاصيل عنصر:** عمود واحد رئيسي (المحتوى) + عمود جانبي ثانوي على الشاشات الكبيرة فقط (`lg:grid-cols-[1fr_320px]` تصوريًا) للمعلومات السياقية (الحالة، CTA، "لمن يخدم") — يتحول لعمود واحد مكدَّس على الموبايل (قسم ٣٣).
- **شبكة الجداول (اشتراكات/مقاعد):** لا Grid حقيقي — Table دلالي (قسم ٣٢)، يتحول لبطاقات مكدَّسة بالموبايل لا Grid.

## 8. Responsive Breakpoints

مقياس Tailwind الافتراضي **بلا تعديل** — مستخدَم فعليًا بكل الكود الحالي (`sm:`, `lg:`):

| Breakpoint | العرض | الاستخدام الأساسي بالـ Marketplace |
|---|---|---|
| Base (بلا بادئة) | < 640px | موبايل — عمود واحد، فلاتر بـ Bottom Sheet |
| `sm` | ≥ 640px | عمودين ببعض الشبكات، حاويات تبدأ تتوسّع |
| `md` | ≥ 768px | غير مستخدم بشكل حرج حاليًا — نقطة انتقال ثانوية فقط |
| `lg` | ≥ 1024px | 3 أعمدة، ظهور الأعمدة الجانبية بصفحات التفاصيل، مبدّل السياق الكامل بالهيدر |
| `xl`/`2xl` | ≥ 1280px/1536px | لا حاجة فعلية اليوم — الحاويات محدودة بـ`max-w-7xl` أصلًا فما فوقها لا فرق بصري |

## 9. Elevation

**مُلاحَظ فعليًا:** نظام ظلال بسيط بمستويين واضحين، لا مقياس Material Design معقّد (Enterprise هادئ، لا ظلال درامية):

| المستوى | القيمة | الاستخدام |
|---|---|---|
| مستوى 0 | بلا ظل، `border` فقط | عناصر ثابتة غير تفاعلية (صفوف جدول، خلفيات أقسام) |
| مستوى 1 | `shadow-sm` | بطاقات بحالة غير مميّزة (قريبًا)، حاويات فلاتر |
| مستوى 2 | `shadow-lg shadow-brand-900/5` | بطاقة العنصر "المتاح" — ظل ملوّن خفيف جدًا بلون البراند لا رمادي عام، توقيع بصري مميّز لحكم ورقم |
| مستوى 3 (Hover فقط) | `hover:shadow-xl` + `hover:-translate-y-1` | تفاعل مباشر عند المرور، لا حالة ثابتة |

لا مستوى ظل رابع أعلى — القرار المتعمَّد إن التسلسل الهرمي البصري يُبنى بالحدود واللون أولًا (قسم ٤)، الظل عنصر مساند لا محوري.

## 10. Border Radius

مقياس واحد **موجود فعليًا وثابت** بكل الكود:

| العنصر | القيمة |
|---|---|
| بطاقات، حاويات كبيرة | `rounded-2xl` (16px) |
| أزرار، حقول إدخال، Badges | `rounded-full` (Pill) |
| أيقونات بخلفية | `rounded-2xl` (16px) — نفس مقياس البطاقات، لا مقياس منفصل |

**لا زوايا حادة (`rounded-none`) بأي مكوّن تفاعلي** — يتماشى مع الطابع "الفاخر الهادئ" المطلوب، لا صرامة زوايا حادة توحي بأداة تقنية باردة.

## 11. Iconography

**موجود فعليًا:** مكوّن `x-service-icon` بنظام `name` مفتاح (`legal`, `bankruptcy`, `articles`, إلخ) — أيقونات SVG خطية بسيطة (Line Icons)، لا أيقونات مملوءة ثقيلة، لا Emoji، لا صور فوتوغرافية للأيقونات.

**قاعدة توسّع إلزامية (Data-driven):** أي `MarketplaceItem` جديد **يجب** يصرّح عن مفتاح أيقونة ضمن نفس نظام `x-service-icon` — لا أيقونة مضمَّنة (Inline SVG) خاصة بعنصر واحد داخل مكوّن البطاقة نفسه. هذا يضمن إضافة تطبيق رقم 9 لا تتطلب تعديل مكوّن البطاقة، فقط إضافة حالة أيقونة جديدة للمكوّن المركزي.

**أيقونات الحالة (منفصلة عن أيقونة العنصر):** أيقونات وظيفية صغيرة (اتصال/قطع اتصال لـIntegration، حالة طلب لـService) — نمط خطي موحّد بنفس سماكة خط أيقونات `x-service-icon` الحالية، لا نمط بصري مختلف يكسر الاتساق.

## 12. Buttons

ثلاثة أنماط فقط — لا نظام أزرار موسّع بلا داعٍ:

| النمط | الاستخدام | مطابقة الكود الحالي |
|---|---|---|
| **Primary** | فعل إيجابي رئيسي واحد بالشاشة (فتح، اشترك، اربط) | `bg-brand-600 text-white rounded-full` — مطابق لزر "دخول" الحالي بمنطق مشابه |
| **Secondary** | فعل ثانوي (تصفّح الكل، إلغاء) | `bg-gray-50 text-gray-600 border` أو `bg-white border-gray-200` — مطابق لأزرار "روابط سريعة" بالـ Dashboard |
| **Dark/Contrast** | فعل على خلفية غامقة (زر البحث بشريط الفلاتر) | `bg-gray-900 text-white` — مطابق لزر "بحث" الحالي فعليًا |

**زر مفقود بالكود الحالي، مطلوب هنا كنمط رابع (Destructive/Caution):** لفعل "Disconnect" (قسم ١٨) — نمط بصري منفصل عن Primary لتفادي ضغط عرضي على فعل له عواقب (قطع اتصال تكامل). يُبنى بحدود لونية من نطاق `maroon` (قسم ٤) لا تعبئة صلبة، حفاظًا على الهدوء العام مع إشارة تحذير كافية.

**قاعدة حالة الزر (Data-driven، امتداد لآلة حالة CTA بالوثيقة السابقة):** نص/نمط الزر **لا يُثبَّت بالمكوّن** — يُمرَّر كمُدخَل من الحالة المحسوبة فعليًا (`AccessAssignment`, `Subscription`, `role`) لا كنص افتراضي بالمكوّن نفسه. المكوّن نفسه لا "يعرف" اسم التطبيق، فقط يعرض الحالة المُمرَّرة له.

## 13. Inputs

نمط واحد موحّد **موجود فعليًا** (`rounded-full`, `border-gray-200`, `focus:ring-brand-500 focus:border-brand-500`) — يبقى كما هو لحقول النص. إضافات مطلوبة هنا لدعم الشاشات الجديدة (اشتراكات/مقاعد):

- **حقل اختيار (Select) لتحديد Subscriber (شخصي/مؤسسة):** نفس نمط الحدود والتركيز، لكن بصريًا مصمَّم كـ Toggle واضح لا Dropdown عادي — لأن هذا قرار محوري (شخصي مقابل مؤسسة) يستحق وضوحًا بصريًا أعلى من حقل عادي.
- **حقول Integration (بيانات اتصال):** تُصمَّم بصريًا كـ "منطقة ثقة" (Trust Zone) — حدود أوضح قليلًا، أيقونة قفل بجانب أي حقل بيانات حساسة (رمزي فقط هنا، التنفيذ الفعلي للتشفير خارج نطاق تصميم واجهة).

## 14. Search

مبني فوق البحث النصي الحقيقي الموجود فعليًا (`platform.marketplace` بحقل `q`) — لا إعادة بناء، فقط توسيع بصري:

```
[ 🔍 نص حر .......................... ] [بحث]
[ فلتر: الكل | مجاني | قريبًا | الجديد ]  ← Pills أفقية (موجودة فعليًا لثلاثة، الرابع Data-driven جديد)
[ + فلاتر متقدمة (النوع/التصنيف/الجمهور) ]  ← 🔒 تظهر فقط بعد وجود بيانات type/category حقيقية (Phase 1 بالوثيقة التقنية)
```

**قاعدة الفلاتر المتقدمة:** لا تظهر كصف فلاتر فارغ اليوم — تظهر **فقط** لحظة توفر الحقل الحقيقي وراءها (`type` مثلًا)، بالضبط كما وثّقت وثيقة الـ UX (لا قسم لمجرد أنه يبدو جميلًا). حتى ذاك الحين، شريط البحث يبقى بحالته الحالية بالضبط.

**AI-powered discovery:** لا عنصر بصري له اليوم — لا حقل بحث "ذكي" منفصل، لا أيقونة AI بجانب شريط البحث. يُضاف بصريًا فقط لحظة وجود الطبقة الفعلية (خارج نطاق هذي الوثيقة بالكامل).

## 15. Filters

نمط الـ Pills الأفقي الحالي (`rounded-full`, حالة نشطة `bg-brand-600 text-white`) **يبقى المعيار الوحيد** لأي فلتر أساسي (حالة/سعر). للفلاتر متعددة القيم لاحقًا (تصنيف، توافق/جمهور) — نمط `Chip Multi-select` بنفس لغة الـ Pills لكن بإمكانية اختيار أكثر من واحد، **لا Dropdown منفصل بصريًا** يكسر الاتساق مع الفلاتر البسيطة الحالية.

**فلتر "مدفوع/Premium":** موجود بنيويًا بالتصفح الكامل (Browse) **فقط**، بنفس نمط الـ Pills — **غير موجود إطلاقًا** بشريط الفلاتر المختصر بالصفحة الرئيسية (اتساق مباشر مع قرارك الثالث: مدعوم معماريًا وتصميميًا، غير مروَّج بالواجهة الرئيسية).

## 16. Badges

أهم مكوّن بالنظام كامل لأنه الناقل الأساسي لحالة حقيقية (مبدأ ٢: الصدق البصري). **موجود فعليًا** بثلاث حالات، يُنظَّم هنا كنظام Data-driven كامل:

| النوع | القيمة (Data-driven) | الشكل |
|---|---|---|
| Lifecycle/Availability Badge | `متاحة الآن` / `قريبًا` / `مفعّل لديك` — من `status` + `AccessAssignment` | ألوان `state-available`/`state-pending`/`state-active` (قسم ٤) |
| Pricing Badge | `مجاني` — فقط لو `pricing_model=free` حقيقي | `state-free` — **لا يظهر بديل "مدفوع" كـ Badge إيجابي**، غياب Badge المجاني يعني ضمنيًا "غير مجاني"، لا حاجة لـBadge "مدفوع" منفصل يوحي بتفعيل نظام تسعير غير موجود |
| Type Badge 🔒 | `تطبيق` / `تكامل` / `خدمة` — من `type` | نص محايد رمادي، **يظهر فقط لحظة وجود أكثر من نوع واحد فعليًا بالكتالوج** (اليوم كل شيء "تطبيق" ضمنيًا، Badge نوع لعنصر وحيد بلا تنويع = ضوضاء بصرية بلا فائدة قرار) |
| New Badge 🔒 | من `created_at` (نافذة زمنية تُحدَّد لاحقًا، مثال 30 يوم) | نمط نصي بسيط، لا لون Badge جديد — **قرار تصميم غير حاسم بعد** (منقول لقسم الأسئلة المفتوحة ضمنيًا، ليس Badge لونيّ صارخ لتفادي منافسة بصرية مع Badge الحالة الأهم) |

**قاعدة صارمة:** لا أكثر من Badge حالة واحد (Lifecycle) + Badge سعر واحد (اختياري) بنفس البطاقة بأي وقت — أي Badge إضافي (Type/New) لاحقًا يجب يُصمَّم بوزن بصري أقل صراحة، لتفادي الازدحام المذكور كخطر بوثيقة الـ UX (قسم W هناك).

```
┌─────────────────────────────┐
│ [Badge حالة]      [Badge سعر]│  ← أعلى يمين (RTL: يسار بصريًا)
│                               │
```

## 21. Subscription Components

مكوّنان أساسيان جديدان (لا يوجدان بالكود الحالي):

**جدول "اشتراكاتي"** (قسم ٣٢ يفصّل نمط الجدول العام) بعمود "وصولي الفعلي" منفصل بصريًا عن عمود "حالة الاشتراك" — تجسيد بصري مباشر لـ"Subscription ≠ Access": لونان مختلفان محتملان لنفس الصف (اشتراك أخضر نشط + وصول Badge منفصل "بانتظار تفعيل" بلون `state-pending`) بدل عمود حالة واحد مضلِّل.

**مؤشر Subscriber (شخصي/مؤسسة):** Badge/Tag صغير يرافق كل صف اشتراك يوضّح "شخصي" أو "باسم [اسم المؤسسة]" — نص واضح دائمًا، لا رمز/أيقونة فقط (لأن الالتباس هنا له كلفة عالية جدًا حسب قسم D بوثيقة الـUX).

## 22. Access States

هذا القسم يترجم آلة حالة CTA الكاملة (7+ حالة، من وثيقة الـUX قسم H) لنظام بصري موحّد — **جدول تحويل حالة→تصميم، لا نص جديد**:

| الحالة المنطقية | لون Badge/CTA | نمط الزر |
|---|---|---|
| Access نشط | `state-active` (أخضر صلب) | Primary — "فتح" |
| متاح، بلا اشتراك، مجاني | `state-available` (أخضر فاتح) | Primary — "ابدأ الآن" |
| متاح، بلا اشتراك، مدفوع 🔒 | `state-available` | Primary — "اشترك" (🔒 معطَّل فعليًا بلا Billing، لا يُعرض قبل وجود عنصر مدفوع حقيقي) |
| مشترك، Access معلَّق/غير مُخصَّص | `state-pending` (ذهبي) | Secondary — "اطلب وصول" |
| Organization-only، المستخدم بلا صلاحية اشتراك | `state-neutral-disabled` (رمادي) | Secondary — "اطلب من المدير" |
| قريبًا | `state-pending` | Secondary — "أنا مهتم" (موجود فعليًا) |

**قاعدة إلزامية:** لون الـ Badge ولون/نمط الـ CTA **مشتقّان من نفس متغيّر الحالة المصدر** — لا تحرير مستقل لكل واحد، لتفادي تناقض بصري (مثال يُمنَع: Badge أخضر "متاح" بجانب زر رمادي معطَّل بلا سبب ظاهر).

## 23. CTA States

توسيع مباشر لقسم ٢٢ من منظور الزر تحديدًا — **كل نص CTA مُدخَل، لا خيار تصميم حر لكل شاشة:**

```
Open · ابدأ الآن · اشترك (🔒) · ترقية (🔒) · اطلب وصول · اطلب من المدير · أنا مهتم · ربط (Integration) · طلب/حجز/تواصل (Service)
```

**قاعدة تصميم CTA واحدة إلزامية:** زر واحد أساسي (Primary) ظاهر بأي وقت لكل عنصر — لا يظهر زران Primary متنافسان بنفس البطاقة/الشاشة. أي فعل ثانٍ (مثال: "عرض التفاصيل" + "اطلب من المدير" معًا) يكون أحدهما Secondary دائمًا.

**تبويبات النوع (Integrations/Services) 🚫 غير معروضة بصريًا اليوم** — تمامًا كما بقسم F بوثيقة الـUX، لا نمط بصري "معطَّل" لها حتى (لا Tab رمادي بعلامة "قريبًا") — غياب كامل، لا تلميح بوجودها.

```
└─────────────────────────────────┘
```

خلفية `bg-white`، حدود `border-gray-100`، `rounded-2xl`، نص مركزي — **مطابق حرفيًا لنمط Empty State الموجود فعليًا بـ`dashboard.blade.php` اليوم** ("ما عندك أي تطبيق مفعّل بعد")، يُعمَّم كمعيار رسمي لكل empty state جديد بدل إعادة اختراعه.

---

## 28. Loading States

**Skeleton Screens** تطابق شكل المحتوى الفعلي (بطاقة/جدول)، لا Spinner مركزي لمحتوى متعدد العناصر (كما حُسم بقسم R بوثيقة الـUX). لون Skeleton: `bg-gray-100` بحركة نبض هادئة (`animate-pulse`، متاحة أصلًا بـTailwind الافتراضي، لا مكتبة إضافية). Spinner بسيط (دائرة دوّارة) **يُقبَل فقط** لأفعال نقطية سريعة (إرسال نموذج "أنا مهتم"، تأكيد اتصال) — لا لتحميل صفحة كاملة.

---

## 29. Error States

نمط بصري منفصل بوضوح عن Empty State (خطأ ≠ غياب بيانات طبيعي): إطار/أيقونة بلون `state-attention` (نطاق `maroon`، أول استخدام فعلي له بالنظام) بدل الرمادي المحايد لـEmpty State، مع نص عربي واضح لسبب الخطأ (لا رسالة تقنية خام مطلقًا) وزر "إعادة محاولة" دائمًا.

---

## 30. Confirmation States

مطلوبة لأي فعل له عواقب حقيقية — أبرزها **Disconnect (Integration)** وإلغاء اشتراك مستقبلًا: نافذة تأكيد مضغوطة (Modal)، لا صفحة منفصلة، بزر Destructive (قسم ١٢) واضح ومنفصل عن زر الإلغاء (ترتيب ثابت: الفعل الآمن "تراجع" دائمًا هو الافتراضي بصريًا — Focus/تمييز أعلى — والفعل الحاسم أقل تمييزًا، لتفادي ضغط عرضي).

---

## 31. Notifications

🔒 **لا نظام Notifications حقيقي بالمنصة اليوم (موثّق كفجوة صريحة بالوثيقة التقنية، قسم ٨).** هذا القسم تصوّر بصري مبدئي فقط للـPattern يوم يُبنى — Toast علوي مؤقت لأفعال فورية (تم التسجيل بنجاح)، لا نظام إشعارات دائم (جرس/مركز إشعارات) يُصمَّم هنا قبل وجود الخدمة الخلفية له فعليًا.

---

## 32. Tables

نمط جدول واحد موحّد لكل الاستخدامات (اشتراكات، مقاعد لاحقًا): رؤوس أعمدة رمادية خفيفة (`text-xs text-gray-500`)، صفوف بحدود سفلية رفيعة فقط (لا خطوط شبكة كاملة — أنظف بصريًا)، تباعد صف مريح (`py-4`) يراعي أن مستخدمي هذي الجداول (مدراء مكاتب) يقرؤون بتمعّن لا يتصفحون سريعًا. على الموبايل: يتحول كل صف لبطاقة مصغّرة مكدَّسة (قسم ٣٣) — لا Scroll أفقي كحل افتراضي.

---

## 33. Mobile Behavior

| العنصر | سلوك الموبايل |
|---|---|
| شبكة البطاقات | عمود واحد كامل العرض |
| الفلاتر | تنهار لزر "فلترة" واحد يفتح Bottom Sheet — لا تظهر Pills كاملة مكدَّسة رأسيًا (تشغل مساحة كبيرة جدًا) |
| مبدّل السياق | يتقلّص لعنصر بقائمة الهيدر (☰) — **يبقى ظاهرًا دومًا**، لا يختفي داخل قائمة ثانوية عميقة (خطورة خلط السياقات تبرر أولويته) |
| الجداول | تتحول لبطاقات مكدَّسة، عمود "وصولي الفعلي" (قسم ٢١) يبقى بارزًا حتى بالنسخة المصغَّرة |
| صفحة التفاصيل (عمودان على Desktop) | تنهار لعمود واحد، القسم الجانبي (الحالة/CTA) ينتقل لأعلى الصفحة مباشرة تحت العنوان — ليس أسفلها، لأن القرار (CTA) أولوية أعلى من الوصف الكامل بالموبايل |

---

## 34. Accessibility

امتداد تنفيذي مباشر لقسم T بوثيقة الـUX:
- كل Badge حالة (قسم ١٦) يحمل نصًا، لا اعتماد على اللون وحده — مُلتَزم به فعليًا بالتصميم أعلاه بالكامل (كل Badge بالجداول أعلاه له نص محدَّد، لا لون فقط).
- تباين `gold-700` على `gold-50` وتباين `state-attention` (`maroon`) على أبيض **يحتاجان قياس WCAG AA فعلي وقت تنفيذ High-Fidelity** — مُسجَّل هنا كبند تحقق إلزامي بالمرحلة القادمة، ليس قرارًا نهائيًا بهذي الوثيقة.
- كل زر بحالة "معطَّل سياقيًا" (`state-neutral-disabled`) يحمل `aria-label`/نص مرافق يوضّح *لماذا* (قسم T بوثيقة الـUX) — لا `disabled` بصري بلا تفسير نصي مرافق دائمًا.
- تسلسل Tab منطقي: فلاتر ← شبكة بطاقات ← Pagination — لا ترتيب DOM يخالف الترتيب البصري بسبب RTL (خطر شائع بمشاريع RTL، يُذكَر صراحة كبند تحقق).

---

## 35. RTL/LTR Behavior

المشروع عربي RTL بالكامل فعليًا وبشكل صحيح — لا تغيير مطلوب على الاتجاه العام. بنود خاصة بمكوّنات Marketplace الجديدة:

- **الأرقام** (أسعار مستقبلية، عدد مقاعد، تواريخ): تُعرض بخط `Poppins` (Display) كما هو معتمد فعليًا لغرض العرض الرقمي، مع اتجاه أرقام LTR داخل جملة RTL (سلوك متصفح افتراضي صحيح، لا تدخّل إضافي مطلوب).
- **أيقونات الاتجاه** (سهم "عرض التفاصيل ←")، السهم يشير فعليًا لليسار بصريًا لأنه RTL — **مطابق للكود الحالي بالفعل** (`←` بالنص العربي يعني "التالي" باتجاه القراءة الصحيح)، يُثبَّت كقاعدة لأي سهم توجيه جديد.
- **Bottom Sheet/Modal (فلاتر، تأكيد):** حركة الدخول/الخروج تبقى رأسية (لا فرق RTL/LTR)، لكن ترتيب الأزرار الداخلية (تأكيد/إلغاء) يتبع اتجاه القراءة العربي (الفعل الأساسي يمين، لا يسار كما بتصاميم LTR افتراضية).

---

## 36. Component States

كل مكوّن تفاعلي (بطاقة، زر، Badge، صف جدول) يلتزم بنفس أربع حالات تفاعل قياسية، بلا استثناء:

| الحالة | السلوك |
|---|---|
| Default | كما مُصمَّم بالجداول أعلاه |
| Hover | `-translate-y-0.5` إلى `-translate-y-1` (حسب حجم العنصر) + ترقية مستوى ظل واحد (قسم ٩) — لا تغيير لون خلفية كامل مفاجئ |
| Focus (لوحة مفاتيح) | `ring-2 ring-brand-500` — حلقة تركيز واضحة، إلزامية لأي عنصر تفاعلي (قسم ٣٤) |
| Disabled/Restricted | `opacity` مخفَّضة + مؤشر `not-allowed` + نص توضيحي مرافق دائمًا (لا حالة "معطَّل" صامتة) |

---

## 37. Component Variants

كل مكوّن بطاقة (١٧-١٩) و Badge (١٦) **متغيّر واحد بمعاملات (Props)**، لا نسخ منفصلة لكل نوع — هذا تطبيق مباشر للقاعدة الإلزامية بأعلى الوثيقة:

```
<ItemCard
  type="application | integration | service"
  status="available | soon | connected | disconnected | ..."
  billingModel="free | paid | organization_only | ..."
  accessState="active | pending | none"
  role="lawyer | firm | finance | student | client"
/>
```

الفروق البصرية بين الأنواع الثلاثة (قسم ١٨/١٩) تُنتَج **داخليًا بالمكوّن** بناءً على `type`، لا بثلاثة مكوّنات منفصلة يُعاد كتابة نفس الهيكل بها — هذا ما يضمن أن إضافة Integration/Service حقيقي لاحقًا لا يتطلب "بناء مكوّن جديد"، فقط تفعيل فرع الحالة الموجود أصلًا بالتصميم.

---

## 38. Do / Don't

| افعل | لا تفعل |
|---|---|
| اعرض Badge حالة نصي دقيق مصدره بيانات حقيقية | تخترع Badge "الأكثر مبيعًا"/"موصى به من الفريق" بلا معيار حقيقي وراءه |
| اترك فلتر "مدفوع" فارغًا بصدق لو فارغ | تعرض أسعارًا/خططًا تجريبية "كمثال" على عنصر مجاني فعليًا |
| استخدم سطر تفسير لكل توصية | تعرض "مقترح لك" بلا أي سبب مرئي |
| اجعل Integration Card بمفردات "اتصال" مختلفة | تعيد استخدام مفردات "اشترك/افتح" لعنصر Integration |
| اعرض فرقًا بصريًا واضحًا بين Subscription وAccess | تدمج الاثنين بلون Badge واحد موحّد |
| استخدم الذهبي كإشارة نادرة | تجعل الذهبي لون خلفية متكرر لكل مكان "مميّز" |
| اخفِ تبويب نوع غير موجود بالكتالوج تمامًا | تعرض تبويب "Integrations (٠)" رماديًا كتلميح لوجود مستقبلي |

## 40. Future Scalability Rules

قواعد تحكم أي إضافة مستقبلية للنظام — بدون هذي القواعد، Data-driven design يتآكل تدريجيًا لكل ميزة جديدة تُضاف بضغط الوقت:

1. **لا حقل بيانات بلا حالة بصرية معرَّفة مسبقًا.** أي عمود جديد يُضاف لـ`MarketplaceItem` أو الكيانات المرتبطة يجب يُربَط فورًا بأحد الأدوار الدلالية بقسم ٤، لا لون مُختار عشوائيًا وقت التنفيذ.
2. **مكوّن واحد لكل عائلة (Card/Badge/Button)، متغيّرات لا نسخ.** أي حاجة "شكل مختلف قليلًا" تُحل بمعامل جديد على نفس المكوّن (قسم ٣٧)، لا مكوّن مواز.
3. **100+ عنصر مستقبلًا = نفس المكوّنات، بيانات أكثر فقط.** أي اختبار تصميم لمكوّن جديد يجب يُختبَر ذهنيًا ضد سيناريو كتالوج كبير (تصفح، فلترة، أداء بصري) لا ضد الثمانية عناصر الحالية فقط.
4. **لا Badge/قسم جديد يُفعَّل بصريًا قبل وجود البيانات الحقيقية وراءه** — نفس قاعدة "لا تبني ميزة لمجرد وجودها بالمعمارية المستهدفة" (Future-ready ≠ Future-built) مطبَّقة هنا كقاعدة تصميم دائمة، لا استثناء مرحلي فقط.
5. **أي نمط بصري جديد لنوع Integration/Service إضافي (لو ظهرت أنواع أبعد من الثلاثة الحالية مستقبلًا) يُوسِّع نفس Props الموجودة (قسم ٣٧)، لا يعيد فتح بنية المكوّن من الصفر.**
