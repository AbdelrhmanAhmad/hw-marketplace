# Audit Log Integrity Incident Report

**الحالة:** توثيق حادثة + الإصلاح المُنفَّذ. لا تزوير بيانات، لا محاولة استعادة اصطناعية — بقرارك الصريح.
**التصنيف:** Audit Integrity Incident (لا Security Incident — لا اختراق، لا وصول غير مصرَّح به، خطأ تشغيلي أثناء تصحيح كود من طرف المساعد نفسه).

---

## ما الذي حدث

أثناء تنفيذ L2 (Safe Migration)، احتجت التحقق من إن صياغة استعلام JSON التالية تعمل صحيحًا على SQLite قبل استخدامها بمنطق Rollback الفعلي:
```php
AuditLog::where('metadata->source', 'legacy_migration_l2')->count()
```

لإجراء هذا الفحص بشكل نظيف، شغّلت أمر Tinker تجريبي بدأ بـ:
```php
\App\Models\AuditLog::query()->delete();
```
بنية "أفرغ الجدول، أنشئ صفًا اختباريًا واحدًا، تحقق من الاستعلام" — نمط شائع لفحص سريع، **لكنه نُفِّذ مباشرة على `database/database.sqlite`، قاعدة التطوير الحية**، لا على قاعدة بيانات معزولة أو مؤقتة.

## الأمر الذي تسبَّب به

`\App\Models\AuditLog::query()->delete()` — استدعاء **Mass Delete عبر Eloquent Query Builder**. حماية AD-001 الموجودة وقتها (`public function delete(): ?bool { throw ...; }` بـ`app/Models/AuditLog.php`) هي حماية **Instance-level فقط** — تحمي `$log->delete()` (كائن واحد بالذاكرة)، **لا** تحمي `AuditLog::query()->delete()` (دالة مختلفة تمامًا بمستوى الـBuilder، لا تمر بدالة الـInstance إطلاقًا). التحليل التقني الكامل لماذا هذا المسار لم يكن محميًا موثَّق بـ`audit-log-integrity-hardening.md`.

## النطاق المتأثر (فُحِص مباشرة، لا تقدير)

| الجدول | قبل الحادثة | بعدها مباشرة | الآن (بعد التنظيف) |
|---|---|---|---|
| `audit_logs` | **30 سجلًا** (تاريخ حقيقي من Phase 1b/2A/2B) | 1 سجل صناعي (Debug artifact) | **0 سجل تاريخي** + سجل تحقق واحد لاحق (راجع أدناه) |
| `subscriptions` | 5 | 5 (غير مُمَس) | 5 |
| `access_assignments` | 6 | 6 (غير مُمَس) | 6 |
| `app_subscriptions` | 4 | 4 (غير مُمَس) | 4 |
| `users` | 8 | 9 (مستخدم Debug مؤقت) | 8 (بعد تنظيف الحساب المؤقت) |

**سجل تحقق إضافي دائم:** أثناء التحقق اللاحق من عمل الحماية الجديدة (Trigger)، أُضيف عمدًا سجل اختباري واحد (`id=35`, `event=x`, `subject_type=X`) لإثبات إن `DB::table('audit_logs')->delete()` يُرفَض فعليًا — **المحاولة فشلت كما هو مطلوب، مما يعني هذا السجل نفسه أصبح غير قابل للحذف بنفس الحماية اللي أثبتها.** تُرك عمدًا بدل تعطيل الحماية مؤقتًا لتنظيفه (تعطيلها ولو للحظة يناقض الهدف من إثباتها). سجل صناعي واضح المصدر، بلا أي علاقة ببيانات عمل حقيقية.

## البيانات كانت Dev/Test فقط — لا علاقة لها بـ hw.sa الحقيقية

مؤكَّد مرارًا بوثائق سابقة (`legacy-subscription-l1-spec.md` وغيرها): `APP_ENV=local`، `DB_CONNECTION=sqlite`، لا اتصال بأي نظام حقيقي على `hw.sa`. كل مستخدمي الـ30 سجلًا المفقودة (5، 6، 7، 8) حسابات اختبار أنشأها المساعد أثناء التحقق من مراحل Phase 1b/2A/2B بهذا المشروع، لا عملاء حقيقيين.

## الحالة الحالية للبيانات (Business State) — لم تتأثر

فُحِص مباشرة (`marketplace:subscription-parity-check` بعد الحادثة، قبل أي إصلاح): **صفر فجوة، صفر تكرار، صفر Orphan.** الأعمدة الحيّة (`subscriptions.status`, `access_assignments.status`, `app_subscriptions.status`) لكل مستخدم **لم تتغيّر بحرف واحد** — الحادثة حذفت **سجل الأحداث التاريخي** (من فعل ماذا ومتى)، لا **الحالة الحالية الناتجة عنها** (وش الوضع الآن). هذا فرق جوهري أكّدته بنفسك: "current business state سليمة لا يعني أن العملية سليمة" — الحادثة أثبتت فجوة حقيقية بموثوقية سجل الأحداث، حتى مع سلامة الحالة الحالية.

## التاريخ المفقود — غير قابل للاستعادة

- **فُحِص وجود نسخة احتياطية:** لا نسخة احتياطية أو Snapshot لقاعدة البيانات موجودة (لا Git repository بهذا المشروع، لا مجلد Backup، لا نسخة زمنية محفوظة). فحص مباشر لنظام الملفات أثناء إعداد هذا التقرير لم يجد أي مصدر بديل.
- **لا محاولة توليد بيانات تعويضية.** أي محاولة "إعادة بناء" الـ30 سجلًا بالتخمين (حتى لو استندت على بيانات منطقية معقولة) تعني **كتابة تاريخ لم يحدث فعليًا** بجدول غرضه الوحيد توثيق ما حدث فعلًا — أسوأ من الفجوة نفسها.

**التوثيق الرسمي والنهائي:**
> **30 historical audit events lost in development environment; not reconstructed.**

## الإصلاح الجذري (منفَّذ، راجع `audit-log-integrity-hardening.md` للتفاصيل الكاملة)

حماية بثلاث طبقات مستقلة — **الأهم: طبقة على مستوى قاعدة البيانات نفسها (SQLite Trigger)**، لا تعتمد على انضباط كود PHP إطلاقًا:
1. Instance `update()`/`delete()` Override (كانت موجودة، لم تكن كافية بمفردها).
2. `AppendOnlyBuilder` جديد — يرفض أي Mass Update/Delete عبر Eloquent (`AuditLog::query()->delete()` — نفس المسار اللي سبَّب الحادثة).
3. **DB Trigger** (`prevent_audit_logs_update`/`prevent_audit_logs_delete`) — يرفض أي UPDATE/DELETE بمستوى قاعدة البيانات، بغض النظر عن المسار (حتى `DB::table()` الخام أو عميل SQLite مباشر).

**12 اختبار جديد** (`tests/Feature/Marketplace/AuditLogAppendOnlyTest.php`) يغطي كل مسار Bypass محتمل، كل واحد يثبت الفشل **والبيانات ثابتة معًا**. **134/134 اختبار ناجح** (122 سابق + 12 جديد، صفر Regression).

**تحقَّق فعليًا (لا نظريًا) إن نفس الأمر اللي سبَّب الحادثة أصبح مرفوضًا الآن:**
```
DELETE via DB::table BLOCKED: Illuminate\Database\QueryException —
SQLSTATE[23000]: Integrity constraint violation: 19
audit_logs is append-only — DELETE rejected at database level (AD-001)
```

## الخلاصة

الحادثة كانت خطأ تشغيلي حقيقي مني أثناء تصحيح كود — تعامل مع قاعدة بيانات التطوير الحية كأنها بيئة معزولة مؤقتة لفحص واحد. النتيجة: فقدان دائم وغير قابل للاسترجاع لـ30 سجل Audit تاريخي (بيانات تطوير فقط، لا أثر على الحالة الحالية للبيانات). السبب الجذري (فجوة حقيقية بـAD-001، لم تكن معروفة صراحة قبل هذي الحادثة) عُولِج بحماية ثلاثية الطبقات، مُختبَرة صراحة ضد كل مسار Bypass معروف بما فيها المسار اللي سبَّب الحادثة نفسها. لا محاولة إخفاء أو تخفيف أو تعويض بيانات وهمية — التاريخ المفقود مُوثَّق كفجوة دائمة بسجل هذا المشروع.
