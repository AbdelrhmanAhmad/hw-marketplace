# Legacy Subscription — L1 Spec: Stop New Legacy Writes

**الحالة:** تحليل/تخطيط فقط — بدون كود، بدون Migration، بدون أي تعديل.
**النطاق:** يجيب حصرًا عن الأسئلة A-E المطلوبة. لا يقرر L2 (Migration) ولا ينفّذ L1 نفسها.
**المرجع:** `legacy-subscription-closure-plan.md` (القسم 3 المُحدَّث لخمس مراحل) · AD-006 · AD-013 · AD-014.

## سؤال حاسم قبل أي شيء: هل البيانات المفحوصة Production أم Dev؟

**الجواب الصريح: قاعدة البيانات المحلية المفحوصة هي بيئة تطوير محلية بحتة، ليست Production بأي شكل.**

الدليل المباشر من الإعدادات الفعلية:
```
APP_ENV=local
APP_URL=http://localhost
DB_CONNECTION=sqlite   (ملف database/database.sqlite على القرص المحلي)
```

**حكم ورقم الحقيقية (hw.sa) نظام منفصل تمامًا، لم يُطَّلع عليه أو يُمَس بأي شكل طوال هذا المشروع بالكامل** — هذا تنويه مثبَّت منذ أول سطر بـ`marketplace-architecture-blueprint.md` ("تنويه حرج"). المستخدمون الأربعة المفحوصون بقسم 4 من `legacy-subscription-closure-plan.md` (`test-1786...@example.com`, `phase1b-demo@example.com`, `seat-race-a@example.com`, `seat-race-b@example.com`) **حسابات اختبار أنشأتُها بنفسي أثناء التحقق البصري لمراحل هذا المشروع (Phase 1a/1b/2A/2B)** — لا مستخدمين حقيقيين، لا بيانات عملاء.

**الأثر على القراءة الصحيحة للأرقام:**
- **الاكتشاف السلوكي/المنطقي** (تسجيل الدخول يكتب للـLegacy، الـBackfill يعيد تفعيل اشتراك مُلغى) **حقيقي بمعزل عن حجم العينة** — هذا خلل بالكود نفسه، يحدث بنفس الطريقة تمامًا على أي بيانات حقيقية لاحقًا بـhw.sa لو استُخدم نفس الكود.
- **الأرقام نفسها (4 مستخدمين، 3 غير مُرحَّلين)** **لا تمثّل شيئًا عن الإنتاج الحقيقي** — لا معنى لاستنتاج "٧٥٪ من المستخدمين غير مُرحَّلين" أو أي نسبة مشابهة منها. **لا قرار معماري كبير يُبنى على هذي الأرقام تحديدًا** — بالضبط كما طلبت.

## A — كل Legacy Writes (Writer → Trigger → When → Why → Still Required?)

| Writer | Trigger | When | Why (تاريخيًا) | لا يزال مطلوبًا؟ |
|---|---|---|---|---|
| `App\Support\FreeAppProvisioner::ensure()` — **نقطة الكتابة الوحيدة فعليًا بكل الكودبيس** (`AppSubscription::firstOrCreate(...)`) | يُستدعى من ثلاث نقاط فقط (الصفوف التالية) | — | آلية Provisioning تلقائي بُنيت **قبل** وجود Marketplace Domain الحقيقي (Phase 1b) — كانت الحل الوحيد المتاح وقتها لضمان وصول فوري لتطبيق مجاني | ⚠️ **لا** — الآن يوجد بديل مباشر: `SubscriptionService::subscribeUserToFreeItem()` (يُنشئ `Subscription`+`AccessAssignment`+Audit معًا، بنفس الأثر العملي بالضبط) |
| ↳ استدعاء #1: `RegisteredUserController::store()` سطر 48 | تسجيل حساب جديد | فور إنشاء المستخدم، قبل تسجيل الدخول | ضمان وصول فوري بلا خطوة إضافية للمستخدم الجديد | الحاجة **المنتجية** لا تزال قائمة (تجربة مستخدم جيدة) — لكن **الآلية** (الكتابة للجدول القديم) لم تعد الوسيلة الصحيحة لتحقيقها |
| ↳ استدعاء #2: `HomeController::index()` سطر 15 | أي زيارة مصادَقة لـ`/marefa` | كل تحميل صفحة (مع `firstOrCreate` يمنع التكرار الفعلي) | شبكة أمان لحسابات لم تمر بالتسجيل الحديث (حسابات قديمة من قبل وجود هذي الآلية) | نفس أعلاه — الحاجة قائمة، الآلية قديمة |
| ↳ استدعاء #3: `DashboardController::index()` | أي زيارة مصادَقة لـ`/dashboard` — **بما فيها كل تسجيل دخول ناجح عاديًا** (اكتشاف هذي الوثيقة، راجع القسم B) | كل تحميل صفحة | نفس شبكة الأمان أعلاه، مضاعَفة عبر أكثر نقطة دخول تكرارًا بالنظام | نفس أعلاه |
| `App\Filament\Resources\AppSubscriptionResource` + `Pages/Create*`/`Edit*` | فعل يدوي من طاقم حكم ورقم بلوحة `/admin` | متى ما احتاج الطاقم تعديل سجل يدويًا | إدارة/تصحيح يدوي لحالات دعم | ✅ يبقى مطلوبًا **كأداة أرشيف إداري** طالما الجدول موجود (حتى بعد L1/L2/L3) — لا علاقة له بالكتابة التلقائية محل هذي الوثيقة |

**لا كاتب خامس** — تأكيد عبر قراءة كل ملف يظهر بنتيجة `grep -rn "AppSubscription::"` (لا استدعاء `create`/`save`/`update` مباشر خارج القائمة أعلاه).

## B — مخطط تدفق الدخول/التسجيل الكامل

```
المسار ١ — تسجيل جديد:
  Registration Form
        ↓
  RegisteredUserController::store()
        ↓ [Write #1 — FreeAppProvisioner::ensure()]
        ↓
  Auth::login($user)
        ↓
  redirect(route('dashboard'))
        ↓
  DashboardController::index()
        ↓ [Write #3 — FreeAppProvisioner::ensure() مجددًا — Idempotent، بلا ضرر عملي لكنه استدعاء زائد]

المسار ٢ — دخول مستخدم قائم:
  Login Form
        ↓
  AuthenticatedSessionController::store()   ← Laravel Breeze القياسي، لم يُعدَّل بهذا المشروع إطلاقًا
        ↓
  redirect()->intended(route('dashboard'))   ← الوجهة الافتراضية، ما لم يوجد "intended" مختلف
        ↓
  DashboardController::index()
        ↓ [Write #3]
```

**أين يمكن فصل Legacy بدون لمس وظائف حكم ورقم الأساسية؟**

النقطة الحاسمة: **`FreeAppProvisioner::ensure()` نفسها ليست منطق Core Platform** — هي منطق **Marketplace-domain** (تزويد بعنصر كتالوج) وُلِد تاريخيًا قبل وجود `SubscriptionService` الحقيقي، ووُضِع مؤقتًا داخل ملفات Core-adjacent (`RegisteredUserController`, `HomeController`, `DashboardController`) لغياب مكان أنسب وقتها. **إزالة الاستدعاءات الثلاثة (سطر واحد بكل ملف) لا تمسّ منطق التسجيل/الدخول/عرض اللوحة نفسه إطلاقًا** — فقط تُزيل جملة واحدة "زوّد تلقائيًا" من كل تابع. هذا تعديل **دقيق ومحدود النطاق (Scalpel)**، لا إعادة هيكلة لتلك الملفات.

**لكن بصراحة تامة:** الملفات الثلاثة المُستهدَفة **هي فعليًا ملفات Core Platform** (Auth scaffolding + Dashboard) — تعديلها، ولو بسطر واحد لكل ملف، يمسّ ملفات كانت مصنَّفة "لا تُمَس" بمعظم المراحل السابقة. **هذا يحتاج نفس فئة الإذن الممنوحة لـPhase 2A (CD-001)** — تعديل محدود النطاق على Core، مبرَّر بوضوح، لا إعادة بناء.

## C — هل Free Application Provisioning وظيفة Core Platform أم Legacy Marketplace؟

**الجواب الصريح: الثانية — Legacy implementation لآلية Marketplace قديمة، لا وظيفة Core Platform حقيقية.**

**السبب:**
- Core Platform (بالتعريف المعتمد بالوثيقة التأسيسية) = الهوية، المؤسسات، العضويات، الصلاحيات، الإشعارات — بيانات وخدمات **يعتمد عليها كل تطبيق**، لا خاصة بتطبيق واحد.
- "تزويد تلقائي بتطبيق مجاني محدَّد (بوابة معرفة تحديدًا)" هو قرار **خاص بعنصر Marketplace واحد بعينه** — بالضبط نوع القرار اللي `SubscriptionService`/`EntitlementResolver` (Phase 1b) صُمِّما ليكونا المصدر الوحيد له.
- الدليل الأقوى: **`SubscriptionService::subscribeUserToFreeItem()` موجود فعليًا اليوم ويؤدي نفس الغرض بالضبط**، بمصدر حقيقة واحد (`AD-013`)، مع Audit Trail، بلا الحاجة لأي منطق مواز.

**النتيجة:** لا يجب أن تبقى `FreeAppProvisioner` كما هي — **ليست لأنها "خطأ" وقت كتابتها**، بل لأن البديل الصحيح صار موجودًا فعليًا الآن ولم يكن موجودًا وقتها.

## D — قواعد Migration آمن يمنع سيناريو "Cancelled → Reactivated" بنيويًا

**المبدأ (AD-014 مُطبَّقًا هنا تحديدًا):**

```
❌ خاطئ (السبب الجذري للخطر المكتشَف):
   لا يوجد سجل "فعّال" بالنظام الجديد؟ → أنشئ واحدًا.
   (يفحص active()، يتجاهل وجود سجل بأي حالة أخرى)

✅ صحيح:
   لا يوجد أي سجل بأي حالة إطلاقًا بالنظام الجديد لهذا المستخدم/العنصر؟ → فقط عندها أنشئ.
   يوجد سجل بأي حالة (حتى cancelled)؟ → توقف، لا فعل، هذا قرار مستخدم مسجَّل يُحتَرم.
```

**هذا مبدأ فحص الوجود (`exists()`) لا فحص الحالة الفعّالة (`active()->exists()`)** — الفرق حرفيًا هو ما بين الخطر المكتشَف وسلامته.

**قاعدة إضافية (دفاع ثانٍ):** أي عملية Migration/Backfill **تسجّل قرارها بـ`AuditLog`** (`SubscriptionCreated` بمصدر مميَّز، أو حدث Migration مخصَّص لاحقًا لو تكرر الاستخدام) — بحيث أي "إعادة تفعيل" مستقبلية (لو حدثت بالخطأ لسبب آخر) **تترك أثرًا يمكن اكتشافه بمراجعة لاحقة**، لا تمر بصمت.

**لا حل نقطي لسطر واحد بأمر واحد** — هذا مبدأ يُطبَّق على تصميم أي Migration/Backfill/Sync **مستقبلي** بالمشروع كاملًا، لا يخص `marketplace:backfill-free-access` وحده.

## E — Migration Eligibility Matrix (اقتراح + سبب + مخاطر لكل حالة، لا افتراض بلا تبرير)

| Legacy | New | Historical Cancel | الاقتراح | السبب | المخاطر لو خُولِف |
|---|---|---|---|---|---|
| Active | None (لا سجل إطلاقًا) | لا ينطبق | ✅ **رحّل** — أنشئ `Subscription`+`AccessAssignment` جديدين | أول مرة يُرَى فيها هذا المستخدم/العنصر بالنظام الجديد، لا تاريخ يتعارض | منخفضة — هذي الحالة الوحيدة اللي الأداة الحالية تعالجها صح فعليًا |
| Active | Active | لا | ⚪ **لا فعل (Idempotent Skip)** | مُرحَّل مسبقًا وصحيح | لا يوجد — لو كُرِّر الفعل، `updateOrCreate`-style يمنع التكرار أصلًا |
| Active | Cancelled | **نعم** | 🚫 **لا تلمس إطلاقًا — لا تُعِد التفعيل** | قرار مستخدم صريح مسجَّل بالنظام الجديد — تجاوزه يخالف AD-014 مباشرة | **عالية لو خُولِف — هذا بالضبط الخطر المكتشَف فعليًا اليوم** |
| Active | None، لكن تاريخ إلغاء موجود | نعم | ⚠️ **حالة لا ينبغي إمكانية حدوثها بالمخطط الحالي أصلًا** — `Subscription` لا يُحذَف فعليًا أبدًا بأي كود موجود (فقط `status` يتغيّر)، فـ"None + تاريخ إلغاء" تناقض بنيوي بالبيانات الحالية. **لو ظهرت مستقبلًا** (مثلًا لو أُضيف حذف فعلي لاحقًا) → عاملها كالصف السابق تمامًا (لا تلمس)، الافتراض الأكثر أمانًا دائمًا هو عدم التدخل | الحذر الافتراضي عند الشك | لا مخاطر إضافية لو اتُّبِع نفس منطق الصف الثالث |
| None (لا سجل قديم) | Cancelled | نعم | ⚪ **لا ينطبق على الـMigration أصلًا** — لا إشارة قديمة تدفع أي فعل، حالة المستخدم الجديدة نتيجة قراره هو بالنظام الجديد فقط | لا علاقة للـLegacy بهذي الحالة | لا مخاطر — Migration لا يمسّها أساسًا |
| None | Active | لا | ⚪ **لا ينطبق** — المستخدم له وصول جديد نظيف بلا أي أثر قديم، لا شيء يُرحَّل | نفس أعلاه | لا مخاطر |

**ملاحظة على الصف الرابع تحديدًا:** ذكرته بجدولك الأصلي كسؤال مفتوح — الإجابة الصادقة إنه **غير قابل للحدوث فعليًا بالمخطط الحالي** (ميزة تصميمية، لا فجوة) بسبب قرار Phase 1b "لا حذف فعلي لسجلات Subscription، فقط تغيير حالة" — لكن يستحق قاعدة احتياطية موثَّقة تحسبًا لتغيّر ذاك القرار مستقبلًا.

## الخلاصة

**البيانات المفحوصة بيئة تطوير محلية، لا Production** — الأرقام (4/1/3) لا تُستخدَم لأي قرار حجم/نطاق، فقط **النمط السلوكي المكتشَف** (كتابة تلقائية بالدخول + خطر إعادة التفعيل) حقيقي وينطبق بمعزل عن حجم البيانات.

**جواب مباشر لأسئلتك الثلاثة الأصلية:**
- **A:** ثلاثة مواضع كتابة، كلها عبر نقطة مركزية واحدة (`FreeAppProvisioner::ensure()`) — سهلة الاستبدال تقنيًا، لكن الملفات المُستضيفة لها Core-adjacent فعليًا.
- **B:** أخطر اكتشاف — تسجيل الدخول العادي (لا التسجيل فقط) يكتب للقديم، بسبب إعادة التوجيه الافتراضية لـ`/dashboard` بعد أي دخول.
- **C:** Free Application Provisioning **وظيفة Marketplace قديمة**، ليست Core Platform — لا ينبغي أن تبقى بشكلها الحالي، بديلها الصحيح (`SubscriptionService`) موجود بالفعل.

**لا Migration ولا كود بهذي المرحلة.** بانتظار إذنك على L1 الفعلية (إزالة الاستدعاءات الثلاثة + استبدالها بـ`SubscriptionService::subscribeUserToFreeItem()`) بصفتها تعديلًا محدودًا على ملفات Core-adjacent، بنفس فئة إذن CD-001/Phase 2A.
