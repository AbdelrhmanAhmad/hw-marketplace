# Hukm w Rakam — Marketplace High-Fidelity Design Pilot (6 Screens)

**الحالة:** مسودة Design فقط — بدون كود، بدون Blade/Livewire/Laravel، بدون تعديل أي ملف مشروع، بدون تغيير Core Platform.
**المراجع الملزمة:** `docs/marketplace-architecture-blueprint.md` (Target Architecture) · `docs/marketplace-product-ux-architecture.md` (Product/UX Architecture) · `docs/marketplace-ui-design-system.md` (UI Design System، المصدر لكل الألوان/الأنماط/المكوّنات المستخدمة هنا — لا تُعاد تعريفها بهذي الوثيقة، فقط تُطبَّق).
**النطاق:** ست شاشات فقط، كنموذج أولي (Pilot) يُعتمَد قبل تصميم بقية الـ Marketplace. لا شاشة سابعة، لا صفحة إضافية.

**التزام صريح بالبيانات الحقيقية:** كل محتوى بهذي الوثيقة إما (أ) بيانات حقيقية موجودة فعليًا بالكود (بوابة معرفة، الثمانية عناصر، `service_interests`)، أو (ب) حالة Empty/Future موسومة بوضوح تام، أو (ج) نمط تصميم عام (Pattern) موسوم صراحة "معاينة مستقبلية" بلا أي اسم شركة/رقم/حالة مُختلَقة. لا استثناء.

**ملاحظة UX محورية طُبِّقت بكل الشاشات الثلاث الأولى المتعلقة بالعناصر:** `service-card` الحالية أساس بصري مشترك (Unified Design Language)، لكن التسلسل الهرمي للمعلومات وCTA والحالة والبيانات الوصفية **تختلف فعليًا حسب `type`** — لا تجربة موحّدة حرفيًا بين Application وIntegration (أوضح مثال: الشاشتان 3 و4 أدناه مصمَّمتان بمفردات وتسلسل مختلفين تمامًا رغم وحدة اللغة البصرية).

## الشاشة 1 — Marketplace Home

**Purpose:** توجيه فوري، لا تسويق. الصفحة تجاوب خلال ثوانٍ عن: أين أنا؟ ماذا أضيف؟ ماذا لدي؟ بماذا تنصحني المنصة؟ كيف أبحث؟
**User:** أي مستخدم (زائر غير مسجّل / مستخدم مسجّل بلا اشتراكات / مستخدم مسجّل له بيئة عمل قائمة).
**Context:** Active Organization Context (لو موجود مستقبلًا) يُقرأ من الهيدر العام — هذي الصفحة لا تبني مبدّل سياق خاص بها (قسم ٢٥ بالـDesign System).

### Layout
```
┌───────────────────────────────────────────────────────┐
│  شريط توجيه مضغوط (ليس Hero تسويقي كامل الشاشة)         │
│  "مرحبًا [الاسم] — بيئتك في حكم ورقم"  +  [بحث سريع 🔍]  │
├───────────────────────────────────────────────────────┤
│  المنطقة 1: بيئتك الآن            (أولوية بصرية أعلى)    │
│  [نشط: N]  [يحتاج إجراء: N]  [مهتم بها: N]  → My Apps    │
├───────────────────────────────────────────────────────┤
│  المنطقة 2: استكشف حسب دورك        (3–4 بطاقات فقط)      │
│  عنوان + عنصر توضيح "لأنك [الدور]"  →  تصفّح الكل         │
├───────────────────────────────────────────────────────┤
│  المنطقة 3: الجديد بالمتجر          (2–3 بطاقات)          │
├───────────────────────────────────────────────────────┤
│  المنطقة 4: بيئة الخدمات المتكاملة  (ثانوية، قابلة للطي)   │
│  [رسم توضيحي مصغّر + رابط "كيف تترابط الخدمات؟"]           │
└───────────────────────────────────────────────────────┘
```

### Hierarchy
1. **توجيه/بحث** (أعلى، دائم الظهور) → 2. **بيئتي الآن** (الأهم لمستخدم عائد) → 3. **استكشاف مخصَّص** → 4. **الجديد** → 5. **شرح الـ Ecosystem** (ثانوي صراحة، ليس العنصر الرئيسي كما طُلب — يظهر بحجم بصري أصغر من أي منطقة أخرى، وقابل للطي بالموبايل).

### Components
`SearchBar` (مضغوط) · `SummaryTile` (عدّاد + تسمية، من My Apps) · `ItemCard` (Application variant فقط اليوم) · `SectionHeader` · `EcosystemDiagram` (نسخة مصغّرة من `platform.partials.integration-diagram` الموجود فعليًا، لا تصميم جديد من الصفر).

### States
| الحالة | السلوك |
|---|---|
| زائر غير مسجّل | لا منطقة "بيئتك الآن" إطلاقًا (لا بيانات لها أصلًا) — الصفحة تبدأ مباشرة بمنطقة الاستكشاف، مع CTA "سجّل مجانًا" ضمن شريط التوجيه |
| مسجّل، بلا أي اشتراك | منطقة "بيئتك الآن" تتحول لـEmpty State واحد: "ابدأ ببوابة معرفة، مجانية بالكامل" (لا ثلاثة عدّادات صفرية — عدّاد صفري مكرر ثلاث مرات ضوضاء بصرية بلا فائدة) |
| مسجّل، له بيئة عمل قائمة | العدّادات الثلاثة حقيقية، تنقل مباشرة لأقسام My Apps المطابقة |

### Responsive
موبايل: المناطق تتكدّس رأسيًا بنفس الترتيب، منطقة 4 (Ecosystem) تتحول لرابط نصي "كيف تترابط الخدمات؟" يفتح الرسم بصفحة/Sheet منفصلة بدل عرضه مضمَّنًا (توفير مساحة تمرير طويلة).

### Interactions
النقر على أي `SummaryTile` ينقل مباشرة لقسم مطابق بشاشة My Apps (لا تكرار نفس القائمة هنا وهناك). التمرير فوق بطاقة استكشاف يفعّل حالة Hover القياسية (قسم ٣٦ بالـDesign System) بلا أكثر.

### Empty States
غياب توصيات كليًا (مستخدم جديد بلا دور مُعرَّف) → منطقة 2 تعرض نصًا بسيطًا "أكمل ملفك الشخصي لنقترح عليك ما يناسبك" بدل بطاقات فارغة.

### Error States
فشل تحميل ملخص "بيئتك الآن" (خطأ شبكة) → المنطقة تعرض رسالة قصيرة + "إعادة محاولة"، لا تُخفي القسم بالكامل ولا تكسر باقي الصفحة (Graceful degradation).

### Accessibility
شريط البحث أول عنصر قابل للوصول بلوحة المفاتيح بعد الهيدر (Skip link ضمني)، `SummaryTile` كل واحد `<a>` بنص كامل مقروء لقارئ الشاشة (لا رقم مجرد بلا سياق: "3 تطبيقات نشطة" لا "3" فقط).

## الشاشة 2 — Marketplace Catalog

**Purpose:** تصفّح كامل للكتالوج — نقطة الدخول لأي بحث/فلترة جادة، لا واجهة اكتشاف سريعة كالرئيسية.
**User:** أي مستخدم يبحث عن شيء محدد أو يتصفّح بلا هدف مسبق.
**Context:** لا تأثير لـActive Organization Context هنا (الكتالوج عام، قسم D بوثيقة الـUX) — يُعرض نفسه لكل مستخدم بغض النظر عن سياقه.

### Layout
```
┌───────────────────────────────────────────────────────┐
│  عنوان الصفحة + سطر وصفي قصير                            │
├───────────────────────────────────────────────────────┤
│  [🔍 بحث نصي .......................] [بحث]              │
│  [الكل] [مجاني] [قريبًا] [الجديد]  🔒[النوع] 🔒[التصنيف]   │
├───────────────────────────────────────────────────────┤
│  عدد النتائج: "٨ عناصر"                                  │
│  ┌────────┐ ┌────────┐ ┌────────┐                        │
│  │ Card   │ │ Card   │ │ Card   │   شبكة 3 أعمدة Desktop   │
│  └────────┘ └────────┘ └────────┘                        │
│  ... (يتكرر)                                              │
└───────────────────────────────────────────────────────┘
```

### Hierarchy
1. البحث/الفلاتر (تحكّم فوري) → 2. عدد النتائج (سياق كمّي قبل التصفح) → 3. الشبكة نفسها → 4. أي CTA ثانوي أسفل الشبكة (لا يوجد اليوم — لا Pagination مطلوبة بـ٨ عناصر).

### Components
`SearchBar` (كامل، مطابق للموجود فعليًا بالكود) · `FilterPillGroup` (٤ فعّالة + ٢ محجوزة بصريًا غائبة اليوم، قسم ١٤/١٥ بالـDesign System) · `ResultCount` (عنصر نصي جديد، لم يكن موجودًا بالكود الحالي) · `ItemCard` grid · `EmptyState`.

### الاختبار على ٨ عناصر مقابل الاستيعاب لـ٥٠+ (قرار تصميم صريح)
- عند ٨ عناصر: شبكة كاملة بلا Pagination، `ResultCount` عنصر تجميلي بسيط.
- **قاعدة الاستيعاب المستقبلي:** لحظة تجاوز عدد العناصر حدًا عمليًا (٢٤ تقريبًا لكل صفحة، ٣ صفوف كاملة × ٨ أعمدة منطقية) — نمط **"تحميل المزيد" (Load More)** يُفعَّل تلقائيًا بدل Pagination مرقّمة، لأن سلوك تصفح/فلترة متكررة (لا قراءة تسلسلية) يناسبه تحميل تراكمي أكثر من قفز صفحات. هذا **قرار مسجَّل الآن، غير مُفعَّل بصريًا اليوم** لأنه لا فائدة له بـ٨ عناصر (لا تُبنى واجهة بلا وظيفة، مبدأ ١ بالـDesign System).
- فلاتر النوع/التصنيف (🔒): تظهر فعليًا **بمجرد وجود أكثر من نوع واحد حقيقي بالكتالوج** — التصميم اليوم يترك لهما مكانًا محجوزًا بصفّ الفلاتر (لا فراغ يبدو مكسورًا، بل غياب تام حتى الحاجة الفعلية، كما حُسم بقسم ١٤).

### States
| الحالة | السلوك |
|---|---|
| نتائج موجودة | شبكة قياسية |
| نتيجة بحث فارغة | `EmptyState` بنص "لا توجد نتائج مطابقة" + اقتراح تعديل الفلاتر + رابط لنموذج "أنا مهتم" (تطابق قسم R بوثيقة الـUX) |
| فلتر "مدفوع" 🔒 (لو فُعِّل لاحقًا ببيانات حقيقية) | يُرجع Empty State صادق **لا** رسالة خطأ — "لا توجد عناصر مدفوعة متاحة حاليًا" |
| تحميل | Skeleton بشكل الشبكة نفسها (قسم ٢٨) |

### Responsive
موبايل: صف الفلاتر ينهار لزر "فلترة" واحد يفتح Bottom Sheet (قسم ٣٣)، البحث يبقى ظاهرًا بالأعلى دائمًا. تابلت: عمودان بدل ثلاثة.

### Interactions
اختيار فلتر يحدّث الشبكة والعنوان (`ResultCount`) فورًا بلا إعادة تحميل كاملة للصفحة بصريًا (Optimistic feel، ولو التنفيذ التقني لاحقًا قد يكون Server-side كما اليوم — هذا قرار تصميم لا تقني بهذي المرحلة).

### Empty States
مذكورة أعلاه — القاعدة الموحّدة: لا نتيجة فارغة بلا اقتراح فعل تالٍ.

### Error States
فشل تحميل الكتالوج بالكامل (نادر لكن ممكن) → رسالة صفحة كاملة بسيطة + "إعادة محاولة"، لا شبكة فارغة صامتة.

### Accessibility
كل Pill فلتر له `aria-pressed` يعكس حالته، `ResultCount` يُعلَن ديناميكيًا لقارئ الشاشة عند تغيّر الفلترة (`aria-live="polite"`).

## الشاشة 3 — Application Details (بوابة معرفة)

**Purpose:** تساعد المستخدم يقرر "هل أدخل الآن؟" — تطبيق **حقيقي** بمحتوى حقيقي بالكامل، لا تصوّر افتراضي.
**User:** محامٍ/مكتب/محاسب/طالب — أي زائر يفتح تفاصيل بوابة معرفة تحديدًا.
**Context:** `pricing_model = free`, `billing_model = user_only`, `status = available` — كل القيم أدناه حقيقية من `PlatformApps::all()` الفعلي.

### Layout
```
┌───────────────────────────────────────────────────────┐
│  [أيقونة]  بوابة معرفة                    [Badge: متاحة/مفعّل لديك] [Badge: مجاني] │
│            الخدمات القانونية (Tagline)                   │
├───────────────────────────────────────────────────────┤
│  عمود رئيسي (٦٦٪ العرض)          │  عمود جانبي (٣٤٪)     │
│  ─────────────────────           │  ──────────────      │
│  لماذا بوابة معرفة؟ (فقرة قيمة)   │  حالة الوصول (Box)     │
│  "الأنظمة السعودية وتحديثاتها      │  [CTA — حسب الحالة]   │
│   التشريعية، وحاسبات قانونية       │                      │
│   عملية." + شرح موسّع              │  لمن يخدم:            │
│                                    │  🏷 محامٍ  🏷 مكتب     │
│  المزايا الفعلية:                  │                      │
│  ✓ فهرس الأنظمة السعودية           │  هل يحتاج مؤسسة؟ لا    │
│  ✓ بحث بالأنظمة                    │  هل يحتاج مقاعد؟ لا    │
│  ✓ حاسبة مكافأة نهاية الخدمة        │  هل يدعم AI؟ لا       │
│  ✓ حفظ المفضلة                     │                      │
│                                    │  جاهزية التكامل:      │
│  قدرات ذات صلة (Rules-based)       │  لا تكامل نشط اليوم   │
│  [بطاقات موصى بها + سطر تفسير]      │  (Empty State صادق)   │
└───────────────────────────────────────────────────────┘
```

### Hierarchy
1. الهوية + الحالة (أعلى، تُقرأ خلال ثانية) → 2. القيمة المقترحة (لماذا) → 3. المزايا الملموسة → 4. **الجانب: القرار نفسه (CTA)** يظهر بموازاة المحتوى لا أسفله — لأن قرار الدخول لا ينتظر قراءة كامل الصفحة → 5. "لمن يخدم" و"المتطلبات" (معلومات مساندة للقرار) → 6. قدرات ذات صلة (اكتشاف إضافي، أولوية أدنى) → 7. جاهزية التكامل (معلومة صادقة، أدنى الأولويات لأنها حاليًا "لا شيء").

### Components
`ItemCard` غير مستخدم هنا (هذي صفحة تفاصيل لا بطاقة) — `DetailHero` (جديد)، `AccessStateBox` (جديد، يطبّق قسم ٢٢ بالكامل)، `FeatureList` (جديد، أيقونة ✓ + نص)، `AudienceTagGroup` (Badges محايدة، تستهلك `compatibility` الحقيقي)، `RecommendationCard` (قسم ٢٠)، `IntegrationReadinessNotice` (جديد — Empty State متخصص، ليس عام).

### States (آلة حالة CTA كاملة مطبَّقة هنا فعليًا)
| حالة المستخدم | CTA المعروض | مصدر الحقيقة |
|---|---|---|
| غير مسجّل | "سجّل ودخل مجانًا" | لا Auth |
| مسجّل، بلا AccessAssignment | "ابدأ الآن" | `pricing_model=free`، تزويد تلقائي |
| مسجّل، له وصول فعّال | "فتح" (Open) | `AccessAssignment.status=active` (اليوم فعليًا: `hasActiveSubscription()`) |

لا حالة "اطلب من المدير"/"مقاعد" هنا — بوابة معرفة `user_only` بحتة، هذي الحالات غير منطقية لهذا التطبيق تحديدًا (تصميم صادق يعكس بيانات هذا العنصر بالذات، لا قائمة حالات عامة مكرورة بلا تمييز).

### Responsive
موبايل: العمود الجانبي (حالة الوصول + CTA) **ينتقل لأعلى الصفحة مباشرة تحت الهيدر**، قبل فقرة "لماذا" — لأن القرار أولوية أعلى من الشرح الكامل بشاشة صغيرة (مطابق تمامًا لقسم ٣٣ بالـDesign System).

### Interactions
"ابدأ الآن" فعل فوري بلا نموذج وسيط (التزويد التلقائي موجود فعليًا بالكود) → ينقل مباشرة بعد التفعيل لتجربة تأكيد مختصرة (تفصيلها بالشاشة ٦).

### Empty States
قسم "جاهزية التكامل" **هو نفسه Empty State مصمَّم عمدًا**، لا قسم مخفي: "لا تكامل نشط بهذا التطبيق اليوم" — نص محايد، لا اعتذار، لا وعد بتاريخ.

### Error States
فشل تفعيل التزويد التلقائي (نادر، لكن حالة حقيقية ممكنة تقنيًا) → رسالة واضحة "تعذّر التفعيل، حاول مجددًا" مكان الـCTA نفسه، لا صفحة خطأ منفصلة.

### Accessibility
`AccessStateBox` يُقرأ كوحدة واحدة لقارئ الشاشة (حالة + CTA معًا، لا منفصلين بترتيب DOM مربك)، `FeatureList` عناصر `<ul><li>` دلالية لا `<div>` مجرّدة.

## الشاشة 4 — Integration Details (Future Integration Preview)

🚫 **لا Integration حقيقي واحد موجود بالنظام اليوم.** هذي الشاشة **معاينة نمط مستقبلي موسومة بوضوح تام** — لا اسم شركة، لا شعار، لا حالة اتصال مُختلَقة. الفئة المستخدمة كمثال ("تكامل محاسبة سحابية") فئة عامة من الوثيقة التقنية (قسم ٦)، لا منتج فعلي.

### Layout
```
┌───────────────────────────────────────────────────────┐
│  ⚠ معاينة مستقبلية — لا تكامل فعلي متاح اليوم            │  ← شريط توضيحي دائم، لا يُخفى أبدًا
├───────────────────────────────────────────────────────┤
│  [أيقونة تكامل]  تكامل محاسبة سحابية (فئة توضيحية)         │
│                  [Badge: غير متصل]                       │
├───────────────────────────────────────────────────────┤
│  ماذا سيربط؟                                             │
│  نظامك المحاسبي السحابي ↔ حكم ورقم                        │
│                                                          │
│  ماذا سيتم مزامنته؟ (اتجاه البيانات)                       │
│  → صادر: بيانات الفواتير (مثال فئوي، لا حقل حقيقي بعد)     │
│  ← وارد: —                                               │
│                                                          │
│  الصلاحيات المطلوبة عند الربط (نمط عام):                  │
│  • قراءة بيانات الفوترة                                   │
│  • لا كتابة/تعديل دون إذن صريح إضافي                       │
│                                                          │
│  حالة الاتصال:  غير متصل                                  │
│  آخر مزامنة:    —                                        │
│                                                          │
│              [ ربط ]  ← معطَّل، بلا وظيفة حقيقية اليوم      │
└───────────────────────────────────────────────────────┘
```

### Hierarchy
1. **إشعار "معاينة مستقبلية"** (أعلى كل شيء، غير قابل للتجاهل) → 2. الهوية العامة للفئة → 3. **ماذا يربط / ماذا يُزامَن** (شفافية تشغيلية، أولوية أعلى من "لماذا" — هذا الفرق الجوهري عن Application Details، قسم I بوثيقة الـUX) → 4. الصلاحيات المطلوبة → 5. حالة الاتصال/آخر مزامنة → 6. CTA (هنا بأدنى أولوية بصرية عمدًا، لأنه غير فعّال).

### الفرق المتعمَّد عن Application Details (تطبيق مباشر للملاحظة الحاسمة بالبرومت)
| البُعد | Application (بوابة معرفة) | Integration (هذي الشاشة) |
|---|---|---|
| أول سؤال بالصفحة | "لماذا أختاره؟" (قيمة) | "ماذا سيحصل لبياناتي؟" (شفافية) |
| الـCTA | "ابدأ الآن/فتح" | "ربط" (Connect) — لا "اشترك" أبدًا |
| Metadata مميزة | المزايا، لمن يخدم | اتجاه البيانات، الصلاحيات، آخر مزامنة |
| لا يوجد بهذي الشاشة | — | لا "قدرات ذات صلة"، لا توصيات — تكامل قرار تقني معزول، لا اكتشاف ترويجي |

### Components
`FutureStatePreviewBanner` (جديد — عنصر تحذيري ثابت، لون `state-pending`) · `IntegrationDetailBlock` (جديد، مختلف بنيويًا عن `DetailHero` الخاص بالتطبيقات) · `PermissionScopeList` (جديد) · `ConnectionStatusIndicator` (جديد، حالة واحدة فقط ممكنة اليوم: "غير متصل") · زر `Connect` بحالة `disabled` دائمة (قسم ٣٦: تعطيل بتفسير نصي مرافق: "غير متاح — لا تكامل فعلي بعد").

### States
حالة واحدة فقط ممكنة اليوم بصدق: **غير متصل، دائمًا**. لا تصميم لحالات "متصل"/"خطأ" بمحتوى تفصيلي هنا (ستُصمَّم فعليًا لحظة وجود Integration حقيقي واحد — هذي الشاشة توثّق النمط، لا تدّعي اكتماله).

### Responsive
موبايل: نفس ترتيب المحتوى (لا عمودين هنا أصلًا، الصفحة عمود واحد حتى بالـDesktop لأن كثافة المعلومات معتدلة ولا تبرر تعقيد تخطيط)، شريط التحذير يبقى ظاهرًا بالتمرير الأول قبل أي محتوى آخر.

### Interactions
لا تفاعل فعلي — أي نقر على "ربط" (لو حدث تقنيًا لاحقًا بالخطأ) يجب يُمنَع بمستوى الواجهة لا الخادم فقط. هذا Placeholder Design، لا مسار تفاعل حقيقي بعد.

### Empty States
الشاشة **كلها Empty/Future State** بطبيعتها — لا قسم فرعي إضافي يحتاج تصميم منفصل.

### Error States
غير قابلة للتطبيق اليوم (لا فعل يُنتج خطأ لأن لا فعل حقيقي متاح).

### Accessibility
شريط "معاينة مستقبلية" يُقرأ **أولًا** بترتيب DOM/قارئ الشاشة قبل أي محتوى آخر، لتفادي أي التباس لدى مستخدم تقنيات مساعدة بأن هذا تكامل فعلي.

## الشاشة 5 — My Apps

**Purpose:** ليست Dashboard تقليدي — "بيئة عملي الرقمية" داخل حكم ورقم. مركز إدارة، لا واجهة عرض سلبية.
**User:** مستخدم مسجّل فقط (`@auth`).
**Context:** تتبع Active Organization Context (قسم D بوثيقة الـUX) — **لكن** الحقيقة اليوم: لا Organization-level subscriptions موجودة فعليًا بقاعدة البيانات (Gap موثّق بقسم C بالوثيقة التقنية)، ولا مبدّل سياق مبني بعد (توصية Core Platform معلَّقة). لذلك تصميم هذي الشاشة **بمرحلتين موثّقتين بوضوح**:

### Layout — المرحلة الحقيقية اليوم (كل الاشتراكات شخصية بحتة)
```
┌───────────────────────────────────────────────────────┐
│  بيئتي في حكم ورقم                                       │
├───────────────────────────────────────────────────────┤
│  عضويتي (Membership — عرض معلوماتي فقط، بلا تبديل سياق)   │
│  🏢 [اسم المؤسسة] — [الدور]     ← يظهر فقط لو عضو فعليًا    │
├───────────────────────────────────────────────────────┤
│  نشطة الآن (N)                                          │
│  [بطاقة تطبيق: بوابة معرفة]  [فتح مباشر]                  │
├───────────────────────────────────────────────────────┤
│  مهتم بها (N)                                           │
│  [عناصر من service_interests الحقيقي — بلا CTA فعل، متابعة فقط] │
├───────────────────────────────────────────────────────┤
│  متاحة لك، لم تُضَف بعد                                   │
│  [عناصر تطابق compatibility، رابط لتفاصيلها]               │
└───────────────────────────────────────────────────────┘
```
**"تحتاج إجراء منك" (المجموعة الثالثة من التصميم المنتجي الأصلي) غائبة اليوم عمدًا** — تتطلب `AccessAssignment` منفصلة عن `Subscription`، غير موجودة بقاعدة البيانات الحالية بعد (Phase 1 بالخطة التقنية). عرضها اليوم يعني بيانات لا مصدر حقيقي لها. تُضاف فعليًا لحظة وجود Phase 1.

### Hierarchy
1. عضويتي (سياق، معلوماتي فقط) → 2. نشطة الآن (الأهم فعليًا — بيئة العمل الفعلية) → 3. مهتم بها (متابعة) → 4. متاحة لك (توسّع بيئة العمل، دعوة لفعل).

### Components
`OrganizationContextCard` (جديد، **للعرض فقط** — لا Dropdown/زر تبديل، لأن التبديل الفعلي توصية Core Platform خارج النطاق) · `WorkspaceSection` (جديد، حاوية بعنوان + عدّاد لكل مجموعة) · `ItemCard` (نفس مكوّن الكتالوج، بحالة `subscribed=true` للمجموعة الأولى) · `InterestListItem` (جديد، أبسط من بطاقة كاملة — سطر واحد + تاريخ التسجيل، لا حاجة لبطاقة ثقيلة لعنصر لا فعل متاح عليه) · `EmptyState`.

### States
| الحالة | السلوك |
|---|---|
| بلا أي اشتراك، بلا اهتمام مسجَّل | الصفحة كلها تتحول لـEmpty State واحد مركزي: "ابدأ ببوابة معرفة" — لا ثلاث حاويات فارغة متتالية |
| له اشتراك واحد نشط فقط | مجموعة "نشطة الآن" فقط تظهر بمحتوى، البقية تُخفى بصمت لو فارغة تمامًا (لا عنوان قسم فارغ بلا محتوى — ضوضاء) |
| عضو بمؤسسة | `OrganizationContextCard` تظهر، بدون أي تأثير على باقي الشاشة اليوم (كل الاشتراكات المعروضة شخصية دائمًا حاليًا، بصرف النظر عن العضوية — صدق كامل مع الفجوة الموثّقة) |

### قاعدة الصلاحيات (لا تُظهر ما لا يملك المستخدم صلاحية رؤيته)
لأن كل البيانات هنا اليوم شخصية بحتة (`user_id` مباشر)، لا خطر تسرّب عبر مؤسسات فعليًا بالتنفيذ الحالي — لكن **التصميم مبني الآن على افتراض مستقبلي**: أي مجموعة (خصوصًا "نشطة الآن") تُبنى بالكود لاحقًا باستعلام يمر إلزاميًا عبر فحص صلاحية/سياق (لا استعلام "كل شيء ثم إخفاء بالواجهة") — هذا قيد تصميم يُسجَّل هنا وإن كان تنفيذه فعليًا خارج نطاق هذي المرحلة.

### Responsive
موبايل: `OrganizationContextCard` تتقلّص لسطر واحد أعلى الصفحة (لا بطاقة كاملة)، كل مجموعة تبقى قسمًا منفصلًا بعنوان واضح (لا Tabs تخفي المجموعات الأخرى — المستخدم يحتاج رؤية بيئته كاملة بتمرير واحد، لا تنقّل بين تبويبات لعنصر بهذي الأهمية).

### Interactions
النقر على بطاقة "نشطة الآن" ينقل مباشرة لداخل التطبيق (لا صفحة تفاصيل وسيطة — القرار سبق اتخاذه، هذي بيئة استخدام لا اكتشاف). عناصر "مهتم بها" غير قابلة للنقر كفعل، رابط واحد فقط لصفحة تفاصيل العنصر لو أراد المستخدم مراجعته.

### Empty States
مذكورة أعلاه — القاعدة: لا قسم فرعي فارغ يظهر بعنوانه لو لا محتوى له إطلاقًا (مختلف عن الشاشة 1 و2 حيث الفراغ نفسه معلومة مفيدة — هنا التكرار البصري لثلاث حاويات فارغة أسوأ من إخفائها).

### Error States
فشل تحميل حالة اشتراك واحد ضمن قائمة (لا الصفحة كاملة) → تلك البطاقة فقط تعرض حالة خطأ مصغّرة داخلها، لا تعطّل باقي الشاشة.

### Accessibility
كل مجموعة (`WorkspaceSection`) عنصر `<section>` بعنوان `<h2>` حقيقي، لا `<div>` بصري فقط — أساسي لمستخدم قارئ شاشة يحتاج التنقّل السريع بين أقسام "بيئته".

## الشاشة 6 — Application / Access / Subscription Flow

**Purpose:** تصميم المسار الكامل، لا شاشة معزولة — إظهار الفرق بين Subscription/Access/Entitlement/Seat/User **بمفردات بشرية**، بلا مصطلحات تقنية بالواجهة نفسها.

### المسار الأول — السيناريو الحقيقي اليوم (تطبيق مجاني، شخصي، بلا مؤسسة)
```
[الشاشة 2: Catalog]
      ↓ نقر على بطاقة
[الشاشة 3: Application Details]
      ↓ CTA "ابدأ الآن"
[لحظة انتقالية: تفعيل فوري]  ← لا نموذج، لا خطوة دفع (مجاني)
      ↓
[تأكيد مختصر: "تم! بوابة معرفة صارت جزء من بيئتك"]  ← لحظة Subscription + Access معًا (مبسّطة لأنها متطابقتان زمنيًا بهذا السيناريو تحديدًا)
      ↓
[الشاشة 5: My Apps]  ← تظهر مباشرة بمجموعة "نشطة الآن"
```

### المسار الثاني — سيناريو مستقبلي (اشتراك مؤسسي، مقعد يُخصَّص لاحقًا) — 🔒 يتطلب Phase 2، مُصمَّم كنمط مسبق فقط
```
[Application Details]  (عنصر Organization-only أو both)
      ↓ CTA "اشترك" (باسم المؤسسة)
[تأكيد مرحلة ١: "تم الاشتراك باسم مكتبك"]   ← هذي لحظة Subscription وحدها — بمفردات بشرية: "مكتبك الآن مشترك"
      ↓ (فعل منفصل، منتظر، ليس تلقائيًا)
[مدير المكتب يخصّص مقعدًا — بشاشة Organization UX، خارج هذا المسار]
      ↓
[تأكيد مرحلة ٢ للمستخدم المخصَّص له: "تم منحك صلاحية الدخول الآن"]   ← هذي لحظة Access/Seat منفصلة زمنيًا وبصريًا عن الأولى
      ↓
[My Apps]  ← ينتقل من "تحتاج إجراء" إلى "نشطة الآن" فقط الآن
```

### كيف تُترجَم المصطلحات التقنية لمفردات بشرية بالواجهة (جدول إلزامي لأي تنفيذ لاحق)
| المصطلح التقني | لا يظهر بالواجهة أبدًا كنص | يظهر بالواجهة كـ |
|---|---|---|
| Subscription | "Subscription" | "مشترك بـ[اسم التطبيق]" |
| Access / AccessAssignment | "Access Assignment" | "صلاحية الدخول مفعّلة" / "بانتظار تفعيل الدخول" |
| Entitlement | "Entitlement" | لا يظهر كمفهوم مستقل بهذي المرحلة — ينعكس فقط كوجود/غياب ميزة فعلية بالتطبيق نفسه (لا شاشة "صلاحياتي التفصيلية" بهذا الـPilot) |
| Seat | "Seat" | "مقعد مخصَّص لك من [اسم المكتب]" |
| User (الفاعل) | — | ضمنيًا دائمًا "أنت" — لا حاجة لإظهاره كمفهوم منفصل بالواجهة |

**القاعدة المصمَّمة هنا:** الفرق بين Subscription وAccess يظهر للمستخدم **كلحظتي تأكيد منفصلتين محتملتين**، لا كحقلين بجدول تقني (الجدول التقني موجود فقط بشاشة "اشتراكاتي" الإدارية، قسم ٢١ بالـDesign System — لا بهذا المسار التفاعلي).

### Components (عبر المسار كامل)
`ConfirmationToast/Modal` (جديد — قسم ٣٠ بالـDesign System يوفّر النمط البصري للتأكيد، يُستخدم هنا بمحتوى نصي بشري لا تقني) · بقية المكوّنات مذكورة أعلاه بالشاشات 2/3/5.

### States
المسار الأول فقط له حالة "نجاح" حقيقية قابلة للتصميم الكامل اليوم. المسار الثاني حالاته (مرحلة ١ منفصلة عن مرحلة ٢) **نمط مصمَّم مسبقًا فقط**، غير قابل للاختبار الفعلي بلا Phase 2.

### Responsive
كل لحظة بالمسار شاشة/Toast مستقلة أصلًا (لا تخطيط معقّد يحتاج تكيّف خاص) — تأكيد النجاح على الموبايل يُفضَّل كـToast مضغوط أعلى الشاشة لا Modal كامل الشاشة (لا يقاطع تدفق المستخدم نحو My Apps مباشرة).

### Interactions
تأكيد النجاح (المسار الأول) يحمل CTA مباشر "اذهب لبيئتي" — لا يترك المستخدم بشاشة تأكيد بلا خطوة تالية واضحة.

### Empty/Error States
فشل التفعيل التلقائي بمنتصف المسار (نفس الحالة المذكورة بالشاشة ٣) → المستخدم يبقى بصفحة التفاصيل مع رسالة الخطأ، **لا ينتقل** لتأكيد وهمي.

### Accessibility
كل لحظة تأكيد تُعلَن فوريًا لقارئ الشاشة (`role="status"` أو مكافئ)، لا تعتمد فقط على ظهور بصري (Toast) قد يُفوَّت.

## Desktop → Tablet → Mobile Behavior (ملخص عابر للشاشات الست)

| الشاشة | Desktop (≥1024px) | Tablet (640–1023px) | Mobile (<640px) |
|---|---|---|---|
| 1. Home | شبكة توصيات 3 أعمدة، كل المناطق مفتوحة | عمودان، منطقة Ecosystem تبقى مفتوحة لكن مصغَّرة | عمود واحد، منطقة Ecosystem تتحول لرابط قابل للفتح |
| 2. Catalog | فلاتر أفقية كاملة + شبكة 3 أعمدة | فلاتر أفقية (قد تتكدّس بصفّين) + شبكة عمودين | فلتر واحد "فلترة" يفتح Sheet + عمود واحد |
| 3. Application Details | عمودان (محتوى ٦٦٪ + جانبي ٣٤٪) | عمودان لكن الجانبي أضيق، أو ينزل تحت المحتوى الأول حسب المساحة | عمود واحد، القسم الجانبي (الحالة+CTA) **أولًا** فوق فقرة "لماذا" |
| 4. Integration Details | عمود واحد (لا حاجة لعمودين، كثافة معتدلة) | نفسه | نفسه، شريط "معاينة مستقبلية" يبقى أول عنصر مرئي دومًا |
| 5. My Apps | كل المجموعات ظاهرة بتمرير رأسي واحد، بطاقات 3 أعمدة داخل كل مجموعة | نفسه، عمودان بالبطاقات | نفسه (لا Tabs)، `OrganizationContextCard` يتقلّص لسطر |
| 6. Flow (تأكيدات) | Modal مركزي للتأكيد | Modal مركزي أضيق | Toast علوي مضغوط بدل Modal كامل |

**قاعدة عابرة واحدة لكل الشاشات:** أي عنصر يمثّل **قرارًا** (CTA رئيسي، حالة وصول، شريط تحذير مستقبلي) **لا ينزل لأسفل الترتيب البصري بأي Breakpoint** — فقط عناصر الشرح/الاستكشاف الثانوية تتحرك أو تُطوى. هذا التطبيق المباشر لـVisual Priority المطلوب (User Goal → Context → Content → Action قبل أي Decoration)، محفوظ عبر كل نقاط الكسر لا فقط بـDesktop.

**ملخص الحالة:** High-Fidelity Design Specification كاملة للشاشات الست، بدون كود أو تنفيذ. كل محتوى إما بيانات حقيقية (بوابة معرفة، الثمانية عناصر، `service_interests`، `Membership`) أو حالة Empty/Future موسومة بوضوح تام — لا بيانات وهمية بأي شكل. بانتظار الاعتماد قبل الانتقال لتصميم بقية شاشات الـMarketplace.
