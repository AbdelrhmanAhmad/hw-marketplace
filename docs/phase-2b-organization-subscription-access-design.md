# Phase 2B — Organization Subscription & Seat Access — Design

**الحالة:** Design فقط — بدون كود، بدون Migration، بدون تعديل أي ملف تشغيلي.
**الإذن الممنوح:** 🟢 التصميم فقط. 🔴 التنفيذ **غير مُصرَّح به** حتى اعتماد هذي الوثيقة صراحة.
**تُبنى فوق:** `phase-2a-completion-report.md` (معتمدة، **لا تُعاد صياغتها هنا**) + `phase-2-organization-access-design.md` (AD-008/009/010/011) + `marketplace-implementation-specification.md` (AD-012، Phase 1b).

**ملاحظة نطاق مهمة:** هذي الوثيقة تغطي تصميميًا ما سمّته AD-010 بـ2B (Organization Subscription) و2C (Seat Management) و2D (Organization Access) **معًا بوثيقة تصميم واحدة** — لأن الثلاثة لا يمكن تصميمها بمعزل صحيح عن بعضها (كما أظهرت الحالات الثمانية اللي طلبت حسمها، كلها تمس الثلاثة معًا). **هذا لا يغيّر AD-010** — تسلسل **التنفيذ** الفعلي لاحقًا (لو اعتُمد) يبقى ملزَمًا بالترتيب 2B→2C→2D خطوة بخطوة، لا دفعة واحدة.

**المشكلة الوحيدة اللي هذي الوثيقة تحلّها:** مكتب لديه اشتراك بتطبيق، يريد يعطي هذا الاشتراك لأعضاء محددين من المكتب — لا أكثر. لا Billing، لا Payment، لا Renewal.

# مبدأ حاكم جديد (AD-012 مُطبَّق حرفيًا هنا)

> **`Active Organization Context` مؤشِّر (Pointer)، لا مصدر حقيقة.**

كل فعل حسّاس بهذي الوثيقة (إنشاء اشتراك، تعيين/سحب مقعد، أي استعلام Access مؤسسي) **يعيد التحقق من `Membership` بقاعدة البيانات مباشرة عند نقطة الفعل نفسها** — لا يقرأ `ActiveOrganizationContext::current()` ويثق بها كفاية. النمط الإلزامي بكل Controller/Service هنا:

```
1. حدّد المؤسسة المستهدفة صراحة من معامل الطلب نفسه (Route Model Binding)، لا من السياق النشط وحده.
2. تحقّق مباشرة: Membership::where('user_id', $actor->id)->where('organization_id', $target->id)->whereIn('role', [...])->exists()
3. فقط لو نجح التحقق (٢) → نفّذ الفعل.
```
السياق النشط (Phase 2A) يُستخدَم فقط **لتحديد أي مؤسسة يُفتَرض المستخدم "يعمل باسمها" افتراضيًا بالواجهة** (تعبئة القيمة الافتراضية بنموذج/رابط) — **لا** كخط تحقق أمني وحيد بأي فعل كتابة.

# A. الكيانات (تأكيد لا تكرار — من AD-008 والوثيقة التقنية)

```
Organization ──< Subscription (subscriber_type=organization) ──> SubscriptionPlan
                        │
                        └──< SubscriptionSeat ──> User
                                    │
                                    └──> AccessAssignment (1:1 فعليًا لكل Seat فعّال)
```

`SubscriptionSeat` (AD-008): يمثّل "هذا المقعد مخصَّص لهذا المستخدم إداريًا" — منفصل عن `AccessAssignment` ("وصوله الفعلي مفعَّل الآن"). كل `SubscriptionSeat` نشط ينشئ `AccessAssignment` مرافقًا تلقائيًا (نفس لحظة التعيين، مطابق لمنطق "Create+Activate معًا" من Phase 1b) — لكن يمكن تعليق الثاني بمعزل عن الأول (مثال حالة ٣ أدناه).

# B. الحالات الثمانية — محسومة بقواعد عمل صريحة

### الحالة 1 — من يملك حق إنشاء Organization Subscription؟
**القرار: `Owner` فقط.** ليس `Admin`. السبب: إنشاء اشتراك مؤسسي فعل بمسؤولية مالية/تعاقدية (حتى بلا Billing فعلي اليوم، هو التزام تجاري مستقبلي) — `Owner` وحده يمثّل المؤسسة قانونيًا بالمعنى العملي، `Admin` يدير التشغيل اليومي لا الالتزامات. **BR-2B-01.**

### الحالة 2 — من يستطيع تعيين/سحب Seat؟
**القرار: `Owner` + `Admin` معًا.** هذا فعل تشغيلي يومي (إدارة فريق)، لا التزام تعاقدي جديد — يناسب صلاحية Admin. **BR-2B-02.**

### الحالة 3 — سحب Seat: يُبطَل الوصول فورًا أم يبقى لنهاية الفترة؟
**القرار: فورًا، بلا استثناء.** السبب الحاسم: **لا يوجد "نهاية فترة" حقيقية بلا Billing Engine** (لا تاريخ تجديد فعلي، لا دورة فوترة حقيقية اليوم) — تصميم "يبقى لنهاية الفترة" يفترض بنية تسعير غير موجودة، وهذا بالضبط النوع من الافتراض المرفوض صراحة (Future-ready ≠ Future-built). سحب المقعد إداريًا = نية واضحة وفورية لسحب الوصول، تُنفَّذ فورًا: `SubscriptionSeat` يُحذَف/يُعطَّل → `AccessAssignment` المرافق → `revoked` بنفس اللحظة، معاملة واحدة. **BR-2B-03.**

### الحالة 4 — المستخدم يغادر المؤسسة
```
Membership Removed (حدث موجود فعليًا من Core Platform)
        ↓
كل SubscriptionSeat لذاك المستخدم ضمن اشتراكات تلك المؤسسة تحديدًا → يُحذَف/يُعطَّل
        ↓
AccessAssignment المرافق لكل واحد → revoked
        ↓
Subscription (المؤسسي) نفسه: **لا يتأثر إطلاقًا** — يبقى active، فقط عدد المقاعد المستخدَمة ينقص بمقدار واحد
```
**BR-2B-04.** (هذا امتداد مباشر لقسم E بوثيقة تصميم Phase 2، الآن بمصطلحات `SubscriptionSeat` الفعلية بدل `AccessAssignment` وحدها).

### الحالة 5 — مستخدم بمؤسستين، وصول من A لا يظهر بسياق B
**القرار (تأكيد، لا تغيير):** أي استعلام Seat/Access مؤسسي **يُقيَّد صراحة بـ`organization_id` المُستهدَف من الطلب نفسه** (لا السياق النشط وحده، AD-012) — استعلام "كل مقاعدي عبر كل مؤسساتي" **ممنوع معماريًا**، لا مسار كود واحد ينتجه. **BR-2B-05 — يُختبَر صراحة (قسم D أدناه).**

### الحالة 6 — اشتراك شخصي + مؤسسي لنفس التطبيق
**القرار:** السجلّان مستقلّان تمامًا بنيويًا (صفّان منفصلان بجدول `subscriptions`، `subscriber_type` مختلف) منذ Phase 1b/AD-002 — لا تغيير مطلوب هنا، فقط تأكيد: مغادرة المؤسسة (حالة ٤) أو انتهاء اشتراكها أو سحب المقعد **لا يمسّ أبدًا** صف الاشتراك الشخصي (`subscriber_type=user`) لنفس المستخدم لنفس التطبيق — منطقيًا مستحيل يتأثر لأنه صف مختلف كليًا بلا FK بينهما. **BR-2B-06.**

### الحالة 7 — آخر Seat، تزامن
**القرار (تأكيد من `phase-2-organization-access-design.md` قسم I):** Transaction + `lockForUpdate()` على صف `Subscription` + تحقق خادم صريح (عدّ `SubscriptionSeat` النشطة < `seat_limit`) + `UNIQUE(subscription_id, user_id)` كخط دفاع DB إضافي. **BR-2B-07 — اختبار Concurrency صريح إلزامي (لا Unit Test عادي)، نفس التحدي التقني الموثَّق بـImplementation Spec قسم Z (استراتيجية معاملة منفصلة عن غلاف اختبار RefreshDatabase الافتراضي).**

### الحالة 8 — تغيير الخطة (Basic→Professional، 5→10 مقاعد) بلا Billing
**القرار — آلية بلا فوترة:**
- **زيادة `seat_limit` ضمن نفس الخطة:** تحديث حقل واحد (`SubscriptionPlan.seat_limit`) — فعل إداري، **من طرف حكم ورقم عبر Filament فقط بهذي المرحلة** (لا واجهة ذاتية للمكتب لطلب "زيادة مقاعد" — ذاك قرار مبيعات/تسعير خارج نطاق Access تمامًا).
- **تخفيض `seat_limit`:** **يُمنَع لو العدد الجديد أقل من عدد `SubscriptionSeat` النشطة حاليًا** — لا حذف تلقائي لمقاعد قائمة لإرضاء رقم أصغر؛ المدير يجب يسحب مقاعد يدويًا أولًا (حالة ٣) لحد الوصول للعدد المطلوب، عندها فقط يُقبَل التخفيض.
- **تغيير الخطة نفسها (Basic→Professional):** `Subscription.subscription_plan_id` يُحدَّث لخطة أخرى (`SubscriptionPlan` منفصلة، مرتبطة بنفس `MarketplaceItem`) — **لا حذف/إعادة إنشاء الاشتراك**، فقط تبديل الـFK. `AccessAssignment` القائمة **لا تتأثر** (لا تزال نفس المستخدمين لهم وصول، الفرق فقط بحدود الخطة الجديدة — `seat_limit` أعلى مثلًا).
**BR-2B-08.**

# C. Business Rules — ملخّص قابل للاختبار

| # | القاعدة |
|---|---|
| BR-2B-01 | إنشاء `Subscription` مؤسسي: `Owner` فقط. |
| BR-2B-02 | تعيين/سحب `SubscriptionSeat`: `Owner` أو `Admin`. |
| BR-2B-03 | سحب Seat يُبطِل `AccessAssignment` فورًا، بلا "فترة سماح" (لا معنى له بلا Billing). |
| BR-2B-04 | مغادرة العضوية تُبطِل مقاعده بتلك المؤسسة فقط، الاشتراك المؤسسي نفسه يبقى قائمًا. |
| BR-2B-05 | لا استعلام Seat/Access يجمع أكثر من مؤسسة واحدة بنفس الوقت — `organization_id` من الطلب صراحة، لا السياق وحده. |
| BR-2B-06 | اشتراك شخصي واشتراك مؤسسي لنفس التطبيق سجلّان مستقلّان بلا أي ربط بنيوي بينهما. |
| BR-2B-07 | تعيين آخر مقعد متاح: Transaction+`lockForUpdate`+تحقق خادم+قيد DB معًا، لا عنصر منفردًا. |
| BR-2B-08 | تخفيض `seat_limit` تحت العدد النشط الحالي مرفوض حتى يُسحَب العدد الزائد يدويًا أولًا. |
| BR-2B-09 (جديدة، AD-012) | أي طلب فعل حسّاس (إنشاء/تعديل/حذف Subscription/Seat) يتحقق من `Membership` بقاعدة البيانات مباشرة عند التنفيذ — رفض `session('active_organization_id')` وحدها كدليل صلاحية. |

# D. Security Scenario Matrix — رفض من الـBackend، لا إخفاء واجهة فقط

كل سطر أدناه **يجب** يُختبَر كـFeature Test صريح يتحقق من كود استجابة HTTP (403/404)، لا فقط غياب زر بالواجهة:

| المحاولة | الفاعل | الهدف | النتيجة المطلوبة |
|---|---|---|---|
| تعيين Seat بمؤسسة B عبر URL مباشر | User A، Owner بمؤسسة A فقط، لا عضوية بـB | `POST /organizations/B/seats` | 403 — `Membership` تحقق مباشر يرفض |
| قراءة قائمة أعضاء/مقاعد مؤسسة B | نفس أعلاه | `GET /organizations/B/seats` | 403 أو 404 (لا تسريب حتى بوجود المورد) |
| تغيير `active_organization_id` بالجلسة يدويًا لمعرّف B ثم طلب فعل إداري | نفس أعلاه | أي فعل كتابة بسياق B المزيَّف | يُرفَض — الفعل نفسه يعيد التحقق من `Membership` بمعزل عن قيمة الجلسة (AD-012، BR-2B-09) |
| تخمين `subscription_id` لاشتراك مؤسسة أخرى برقم تسلسلي | نفس أعلاه | `POST /subscriptions/{id}/seats` بمعرّف لا يخصّه | 403/404 — لا اعتماد على صعوبة التخمين كحماية |
| Admin بمؤسسة A يحاول إنشاء Subscription (فعل مقصور على Owner) | Admin بمؤسسة A | `POST /organizations/A/subscriptions` | 403 — BR-2B-01 يتحقق من الدور تحديدًا لا مجرد العضوية |
| مستخدم بمؤسستين (A، B) بسياق نشط=A، يطلب بيانات Access الخاصة بـB مباشرة | User بعضويتين فعليتين | أي استعلام بمعرّف B صراحة رغم سياق A | يُرفَض أو يتطلب تبديل سياق صريح أولًا — **لا دمج تلقائي بأي حال** (BR-2B-05) |

# E. State Machines (امتداد لما بُني بـPhase 1b)

### `SubscriptionSeat` (جديد)
```
(غير موجود) → assigned → released
```
لا حالة "معلَّق" منفصلة على المقعد نفسه — التعليق يحدث على `AccessAssignment` المرافق (قسم أدناه)، لا على المقعد. المقعد إما مخصَّص أو غير موجود، بلا حالة وسيطة.

### `AccessAssignment` (تأكيد من Phase 1b، بلا تغيير على الكيان نفسه)
```
active ⇄ suspended → revoked
```
`suspended` هي الحالة اللي تفصل "له مقعد" عن "وصوله مفعَّل الآن" (مثال: تعليق تأديبي — المقعد يبقى `assigned`، الـAccessAssignment يتحول لـ`suspended` بمعزل تام). **لا واجهة لهذا الفعل بـPhase 2B** — الكيان يدعمه بنيويًا (يمنع Migration لاحقة)، لكن لا زر/فعل يُبنى له الآن (لا حاجة منتجية مؤكَّدة اليوم، Future-ready ≠ Future-built).

# F. UX Flows

لا تصميم جديد — الشاشات موجودة مسبقًا (`marketplace-high-fidelity-full.md` أقسام J/K/L: Organization Management/Access Management/Seat Management). هذي الوثيقة فقط تُثبِت إن الحالات الثمانية أعلاه **قابلة للتنفيذ حرفيًا خلف تلك الشاشات بلا فجوة تصميم** — لا حاجة لإعادة فتحها.

# G. Non-Goals — قائمة الاستبعاد الصريحة (Billing)

**لا يُبنى بـPhase 2B بأي حال:** محرك دفع (Stripe/Mada/Apple Pay أو أي بوابة) · فواتير · Renewal Engine (تجديد تلقائي حقيقي) · Payment Retry · Coupons/أكواد خصم · Tax Engine · Revenue Recognition. **الموجود فقط:** حقول وصفية (`SubscriptionPlan.price`, `.billing_cycle`) بلا أي منطق تنفيذي خلفها — تُقرأ يوم يوجد قرار تجاري فعلي وبنية دفع حقيقية، لا قبل.

**كذلك خارج النطاق صراحة:** Organization Authorization الكاملة (2E) — دور `Owner`/`Admin` يُستهلَك هنا **فقط** لقرارَي BR-2B-01/02 (من يقدر يدير الاشتراك/المقاعد)، لا لبناء نظام Authorization عام داخل أي تطبيق مستقبلي (يبقى AD-005: كل تطبيق يبني طبقته بمفرده).

# I. Migration / Backward Compatibility

**لا تعديل على أي جدول من Phase 1b** (`subscriptions`, `access_assignments`, `subscription_plans`, `audit_logs`) — `subscriber_type=organization` مدعوم بنيويًا فيها أصلًا منذ AD-002/Morph Map (Phase 1b)، لم يُستخدَم فعليًا لحد الآن فقط. `SubscriptionSeat` جدول جديد بحت (AD-008)، إضافي بالكامل. `ActiveOrganizationContext` (Phase 2A) يُستهلَك للقراءة فقط (تعبئة قيم افتراضية بالواجهة) — **لا تعديل عليه هنا** (AD-012 يحكم كيف يُستهلَك، لا يغيّر بنيته).

---

**ملخص الحالة:** تصميم كامل للحلقة الوسطى الحرجة (Subscription↔Seat↔Access مؤسسي) — ثمان حالات محسومة بقواعد عمل صريحة، مصفوفة أمان بستة سيناريوهات هجوم يجب رفضها من الـBackend، لا كود ولا Migration. بانتظار اعتمادك قبل أي انتقال لتنفيذ فعلي (وحتى بعده، ملتزم بترتيب AD-010 خطوة بخطوة، لا دفعة واحدة).
