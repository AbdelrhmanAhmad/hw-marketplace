# Phase 2 — Organization Access Design

**الحالة:** Design فقط — بدون كود، بدون Migration، بدون تعديل أي ملف تشغيلي.
**الإذن الممنوح:** 🟢 التصميم فقط. 🔴 التنفيذ **غير مُصرَّح به** حتى اعتماد هذي الوثيقة صراحة.
**المراجع الملزمة:** `marketplace-architecture-blueprint.md` (AD-001 – AD-007) · `marketplace-implementation-specification.md` (الحالة الفعلية بعد Phase 1a/1b) · `phase-1b-completion-report.md` (نقطة الانطلاق الحقيقية).

**لماذا هذي الوثيقة موجودة:** Phase 2 أول مرة يدخل فيها النظام منطقة B2B SaaS حقيقية — Organization كفاعل مستقل، مقاعد متعددة، مستخدم بعضويات متعددة، وعزل بيانات بين مؤسسات. هذي أخطر منطقة بالنظام كامل لأن خطأ فيها يعني **تسرّب بيانات بين عملاء حقيقيين لبعضهم**، لا مجرد Bug تجربة مستخدم. لذلك: تصميم كامل، عشر سيناريوهات مُختبَرة على الورق، ثم مراجعة — قبل أي كود.

---

## القاعدة الحاكمة (تُطبَّق على كل قرار بهذي الوثيقة)

> **Organization Subscription ≠ كل أعضاء المؤسسة يستطيعون كل شيء.**

السلسلة الإلزامية، بلا اختصار بأي حال:

```
Subscription → Entitlements → Access → Application Authorization
```

كل طبقة مسؤوليتها منفصلة تمامًا: `Subscription` = حقيقة تجارية (مين يدفع). `Entitlements` = وش تشمله الخطة. `Access` (`AccessAssignment`) = مين بالضبط مخوَّل الآن من بين مين يدفع. `Application Authorization` = وش يقدر يفعل داخل التطبيق الفعلي (خارج نطاق Marketplace تمامًا، AD-005).

**قاعدة ثانية بنفس الوزن (AD-011، معتمدة):** اختيار مؤسسة نشطة (Context) **لا يمنح صلاحية إدارية تلقائيًا**. السلسلة الكاملة المُحدَّثة:
```
Authenticated User → Active Organization Context → Membership → Organization Role → Entitlement → Application Access → Application Authorization
```
اختيار "أعمل الآن باسم مكتب A" فعل **محايد** — لا يعني تلقائيًا "صرت Admin بمكتب A". الصلاحية الفعلية دائمًا من `Membership.role` الحقيقي لذاك المستخدم بتلك المؤسسة تحديدًا، تُحسَب من جديد بكل تبديل سياق، لا تُورَّث من السياق نفسه.

# A. الوضع الحالي الحقيقي (نقطة الانطلاق)

من `phase-1b-completion-report.md`، هذي الكيانات موجودة فعليًا بالكود اليوم:

| الكيان | الحالة اليوم |
|---|---|
| `Organization`, `Membership` (+`MembershipRole` enum بثمانية أدوار) | موجودة من Core Platform Phase 1 — **لا تُمَس** |
| `Subscription` | موجود، `subscriber_type` مقيَّد بـ`user`/`organization` عبر Morph Map (AD-002) — لكن **لا سجل واحد بـ`subscriber_type=organization` أُنشئ فعليًا بعد** |
| `AccessAssignment`, `SubscriptionPlan`, `AuditLog` | موجودة، تعمل حصرًا بمسار شخصي (`subscriber_type=user`) اليوم |
| `EntitlementResolver` | يعمل بخطوات ١-٤ فقط (شخصي) — خطوة "اشتراك مؤسسي" **غير مكتوبة أصلًا**، لا كود ميت بالانتظار |
| Active Organization Context | **غير موجود إطلاقًا** — لا جلسة، لا Middleware (CD-001 لم يُحلّ بعد) |
| `subscription_seats` | **لا يوجد جدول أصلًا** — لم يُبنَ حتى كبنية فارغة (قرار Phase 1a/1b الصريح) |

**النتيجة:** Phase 2 تبني فوق أساس نظيف حقيقي، لا فوق كود مؤجَّل جزئيًا.

# B. القرارات المعمارية المطلوب حسمها هنا (قبل أي كود)

## B.1 — Active Organization Context (الأساس الذي يعتمد عليه كل شيء تالٍ)

**التصميم:**
- الجلسة تحمل مفتاحًا واحدًا: `active_organization_id` — قيمته إما `null` ("شخصي") أو معرّف مؤسسة المستخدم فيها عضوية فعّالة.
- Middleware جديد (`ResolveActiveOrganizationContext`، **تصميم فقط الآن**) يقرأ الجلسة، يتحقق إن المستخدم لا يزال عضوًا فعليًا بتلك المؤسسة (دفاع ضد جلسة قديمة بعد إزالته)، ويحقن كائن `?Organization $activeOrganization` بالطلب.
- **لا Fallback ضمني لأول مؤسسة بالقائمة** — غياب اختيار صريح = "شخصي" دائمًا. هذا يمنع افتراض خاطئ بمؤسسة معيّنة بدون فعل واعٍ من المستخدم (مطابق تمامًا لقرار وثيقة الـUX السابقة).
- **هذا العنصر بالذات (Middleware + الجلسة + مبدّل الهيدر) هو CD-001 نفسه** — لا يزال Core Dependency خارج نطاق Marketplace المباشر. تصميمه موثَّق هنا لأن Phase 2 لا تعمل بدونه، لكن **بناءه الفعلي خطوة منفصلة قبل أي كود Marketplace آخر بـPhase 2**.

## B.2 — Seat: كيان منفصل أم مفهوم مُشتق؟ (سؤال تصميم حقيقي، غير محسوم)

هذي أهم نقطة تصميم بالوثيقة كاملة — تؤثر على كل شيء تالٍ. خياران حقيقيان:

**الخيار أ (مطابق حرفيًا لـBlueprint الأصلي، قسم ٤):** `SubscriptionSeat` كيان منفصل (جدول مستقل) يمثّل "التخصيص الإداري" — الأدمن يخصّص مقعدًا، وهذا يُطلِق إنشاء `AccessAssignment` تلقائيًا كنتيجة. الفصل يسمح مستقبلًا بحالات مثل "له مقعد لكن وصوله معلَّق مؤقتًا لسبب لا علاقة له بالمقعد نفسه" (مثال: تعليق تأديبي بمعزل عن حالة المقعد الإدارية).

**الخيار ب (أبسط، اكتُشف أثناء اختبار السيناريوهات أدناه):** لا جدول `SubscriptionSeat` منفصل إطلاقًا — "المقعد" مفهوم تجاري مُشتق فقط: `عدد AccessAssignment النشطة المرتبطة باشتراك مؤسسي معيّن ≤ SubscriptionPlan.seat_limit`. `AccessAssignment` نفسه **هو** سجل تخصيص المقعد، لا حاجة لكيان وسيط.

| المعيار | الخيار أ | الخيار ب |
|---|---|---|
| مطابقة القرار المعماري المعتمد سابقًا | ✅ حرفيًا | ⚠️ تبسيط عن المعتمد |
| عدد الجداول الجديدة | +1 (`subscription_seats`) | +0 |
| يدعم "مقعد بلا وصول مفعَّل" (حالة مستقبلية نادرة) | ✅ طبيعي | ⚠️ يحتاج حالة إضافية على `AccessAssignment` نفسه (`status=suspended` بمعزل عن سحب المقعد) |
| تعقيد منطق التحقق من الحد (Concurrency، قسم P) | يتحقق من عدد صفوف `SubscriptionSeat` | يتحقق من عدد `AccessAssignment` النشطة — نفس التعقيد بالضبط |

**القرار النهائي (AD-008، معتمد): الخيار أ.** `SubscriptionSeat` كيان مستقل. السبب المعتمد: ليس فقط "مرونة مستقبلية" بل فصل مفاهيمي صحيح — **Seat = حق/سعة مخصَّصة داخل الاشتراك، Access = صلاحية استخدام فعلية**، والاثنان قد ينفصلان (مقعد مخصَّص + وصول معلَّق حالة صالحة ومصمَّمة، لا استثناء نادر). السلسلة المعتمدة:
```
Subscription → SubscriptionSeat → User → AccessAssignment
```
**ليست** `Subscription → عدّ AccessAssignment`. **قاعدة إضافية معتمدة:** ملكية المقعد (`SubscriptionSeat`) ترتبط بـ`Subscription` لا بالمستخدم مباشرة — هذا يجعل انتقال المستخدم بين المؤسسات (وما يترتب عليه من مقاعد مختلفة بكل مؤسسة) واضحًا بنيويًا بلا التباس.
**نطاق البناء الآن (Phase 2C لاحقًا، ليس 2A):** الكيان والـLifecycle الأساسي فقط (Assign/Release) — **لا Seat Management UI كامل الآن**، ذاك ينتظر دوره الصحيح بالتسلسل (قسم Q أدناه).

## B.3 — من يملك صلاحية إدارة اشتراك/مقاعد المؤسسة؟

`MembershipRole` الموجود فعليًا يكفي، **بلا حاجة لدور جديد**: صلاحية إدارة الاشتراك/المقاعد = `Membership.role ∈ {Owner, Admin}` حصرًا. باقي الأدوار الستة (Partner, Lawyer, Accountant, FinancialConsultant, Trainee, Client) يملكون وصولًا استخداميًا فقط لو خُصِّص لهم مقعد، بلا أي صلاحية إدارية على الاشتراك نفسه.

# C. Organization Switching — التصميم الوظيفي

فعل صريح فقط (مبدّل بالهيدر، توصية CD-001) — يكتب بالجلسة، **لا فعل ضمني**. عند التبديل:
- شاشات "مساحتي" (My Apps/My Subscriptions) تُعيد التحميل بسياق المؤسسة الجديدة.
- شاشات تصفّح الكتالوج (Catalog/Home) **لا تتأثر إطلاقًا** — عامة دومًا (قرار قائم من وثيقة الـUX، لا تغيير هنا).
- لا "دمج" بين مؤسستين بنفس الشاشة (مرفوض صراحة سابقًا، يبقى مرفوضًا هنا).

---

# D. مستخدم بعضويات متعددة — كيف يُحسَب "وصوله" الكلي؟

**القاعدة (اتحاد Union، من Blueprint قسم ٢، مُطبَّقة هنا فعليًا لأول مرة):**
```
وصول المستخدم لعنصر معيّن =
    AccessAssignment شخصي مباشر (دائمًا مرئي، بصرف النظر عن السياق النشط)
    ∪
    AccessAssignment عبر مقعد بالمؤسسة النشطة حاليًا فقط (Active Organization Context)
```
**لا اتحاد عبر كل مؤسساته دفعة واحدة** — لو له مقعد بمؤسستين لنفس العنصر، يرى وصول المؤسسة النشطة فقط + وصوله الشخصي. التبديل الصريح يغيّر أي مجموعة "مؤسسي" يراها، **الشخصي ثابت دائمًا** (نفس منطق قسم D بوثيقة الـUX، مُطبَّق تقنيًا هنا).

---

# E. ماذا يحدث لما يغادر عضو المؤسسة؟ (تفعيل حقيقي لـ`MembershipRevoked`)

**السلسلة:** حذف/إلغاء `Membership` → حدث `MembershipRevoked` يُطلَق (مُعرَّف مسبقًا بـImplementation Spec قسم V، بلا مستهلك حتى الآن — **Phase 2 هو أول مستهلك حقيقي له**) → Listener يبحث كل `AccessAssignment` لذاك المستخدم ضمن اشتراكات تلك المؤسسة تحديدًا (لا كل اشتراكاته) → يُبطِلها (`status=revoked`) → `AuditLog` (`AccessRevoked`) لكل واحد.

**لا يُمَس اشتراكه الشخصي المباشر إطلاقًا** — مغادرة مؤسسة لا علاقة لها بوصوله الفردي لأي عنصر (مطابق للفصل التام بين النوعين، قسم D أعلاه).

---

# F. انتهاء/إلغاء اشتراك المؤسسة نفسها

**لا مفهوم "انتهاء تلقائي بتاريخ" بـPhase 2** — لا Billing Engine (AD غير موجود لهذا، قرار ثابت منذ Blueprint). "الانتهاء" هنا يعني فقط **إلغاء إداري** (Owner/Admin يلغي، أو حكم ورقم إداريًا لسبب تشغيلي). عند الإلغاء:
1. `Subscription.status = cancelled` (سجل واحد، الاشتراك المؤسسي نفسه).
2. **كل** `AccessAssignment` المرتبطة به (كل المقاعد) → `status=revoked`، بمعاملة واحدة (Transaction) — لا إبطاء تدريجي.
3. `AuditLog`: سجل `SubscriptionCancelled` واحد للاشتراك + سجل `AccessRevoked` **لكل مقعد** كان نشطًا (لا حدث جماعي جديد — نفس الخمسة أحداث المعتمدة بـAD-001، لا حدث سادس).

مطابق لـImplementation Spec قسم H، مُفعَّل الآن فعليًا:

| الجدول | القاعدة |

# H. Authorization vs Entitlement — التطبيق العملي بـPhase 2

`EntitlementResolver::resolve()` (الموجود من Phase 1b) يُوسَّع بخطوة خامسة **إضافية فقط** (لا تعديل على الأربع الحالية — توافق رجعي كامل، قسم U أدناه):

```
5. لو billing_model يسمح بمؤسسة (organization_only|both) و$activeContext ليس null:
   يوجد Subscription(subscriber=organization=$activeContext, item, status=active)
   و AccessAssignment(user, subscription, status=active) عبر مقعد؟
   نعم → allowed=true, reason=has_access
   لا  → allowed=false, reason=needs_org_membership (قيمة جديدة تُضاف لـAccessReason enum)
```

**`AccessReason::NeedsOrgMembership` قيمة جديدة واحدة فقط تُضاف** — قائمة الأسباب تبقى صغيرة ومقصودة، لا توسّع عشوائي.

**Authorization يبقى خارج هذا كليًا** — دور المستخدم (`Owner`/`Admin`/`Lawyer`...) لا يُستهلَك أبدًا داخل `EntitlementResolver` لاتخاذ قرار "يقدر يستخدم التطبيق؟" — فقط لاحقًا **داخل التطبيق نفسه** لقرار "يقدر يفعل وش بالضبط؟" (AD-005، بلا استثناء).

# I. Concurrent Seat Allocation — الخوارزمية الكاملة (AD-003 مُطبَّق حرفيًا)

```
BEGIN TRANSACTION
  1. lockForUpdate() على صف Subscription (المؤسسي) — قفل حصري لمدة المعاملة
  2. عدّ AccessAssignment(subscription=هذا, status=active) الحالي
  3. لو العدّ ≥ SubscriptionPlan.seat_limit → ROLLBACK، رفض صريح ("لا مقاعد متاحة")
  4. لو أقل → إنشاء/تفعيل AccessAssignment للمستخدم المستهدف
  5. AuditLog(SeatAssigned أو AccessGranted — راجع قسم J أدناه لحسم الاسم)
COMMIT
```

**لا اعتماد على الواجهة لمنع التجاوز أبدًا** — الفحص كامل داخل القفل، من جهة الخادم حصرًا. **تعيين دفعة (5 مستخدمين مرة واحدة، سيناريو ٣ أدناه) = خمس استدعاءات متتالية لنفس الخوارزمية، لا مسار Batch منفصل** — يبقي منطق التزامن موحّدًا بمكان واحد، لا نسخة موازية له مخاطرها الخاصة.

**خط دفاع إضافي (Database Constraint):** فوق قفل الصف والتحقق التطبيقي، `UNIQUE(subscription_id, user_id)` على `subscription_seats` (يمنع تخصيص مقعدين لنفس المستخدم بنفس الاشتراك) — دفاع بنيوي مستقل عن منطق العدّ، لا يعتمد عليه وحده لكنه خط ثانٍ لا يُستغنى عنه.

| BR-101 | مغادرة/إزالة عضو تمر **حصرًا** عبر `MembershipRevoked` (قسم E) — لا حذف مباشر لـ`SubscriptionSeat`/`AccessAssignment` من أي مكان آخر بالكود. السلسلة إلزامية: `Membership Removed → Seat Released → Access Revoked`، بهذا الترتيب، لا افتراض تزامني. |

# J. Audit Requirements (AD-009، معتمد)

AD-001 حدَّد ثمانية أحداث بالاسم أصلًا (شاملة `SeatAssigned`/`SeatReleased` — لم تُستخدَم بـPhase 1b لغياب المقاعد، **تُفعَّل الآن فعليًا بـPhase 2 لأول مرة**). **لا حدث تاسع يُضاف** — القائمة المغلقة بـAD-001 تكفي حرفيًا:

| الفعل | الحدث |
|---|---|
| تعيين مقعد | `SeatAssigned` (وليس `AccessGranted` — تمييز مقصود: `AccessGranted` للمسار الشخصي، `SeatAssigned` للمسار المؤسسي، كلاهما يُنشئ `AccessAssignment` لكن السياق التجاري مختلف ويستحق تمييزًا بالسجل) |
| سحب مقعد | `SeatReleased` |
| إلغاء اشتراك المؤسسة كاملًا | `SubscriptionCancelled` + `SeatReleased` لكل مقعد كان نشطًا |
| مغادرة عضو (قسم E) | `SeatReleased` (لا `AccessRevoked` — نفس المنطق، الفعل مصدره المقعد لا وصول شخصي) |

**تعديل دقيق على AD-001:** `AccessGranted`/`AccessRevoked` يبقيان حصرًا للمسار الشخصي، `SeatAssigned`/`SeatReleased` للمسار المؤسسي — تمييز لم يكن واضحًا وقت اعتماد AD-001 (لغياب مسار مؤسسي وقتها)، يُحسَم هنا صراحة.

# K. Failure Scenarios

| الحالة | السلوك المصمَّم |
|---|---|
| انقطاع الاتصال منتصف تعيين مقعد | Transaction تتراجع بالكامل (Rollback) — لا مقعد جزئي، لا AccessAssignment يتيم |
| مؤسسة حُذفت (نظريًا، لا واجهة حذف مؤسسة موجودة اليوم) بينما مستخدم بجلسة نشطة بسياقها | Middleware (B.1) يتحقق من صحة العضوية بكل طلب — لو المؤسسة/العضوية لم تعد موجودة، السياق يرجع لـ"شخصي" تلقائيًا، لا خطأ 500 |
| Seat Limit = 0 أو Plan محذوفة بينما اشتراك قائم | يُمنَع منطقيًا بقيد FK (`restrictOnDelete` على `subscription_plan_id`، موجود فعليًا من Phase 1b) — لا يمكن حذف خطة عليها اشتراكات قائمة |
| مستخدم له مقعدان بمؤسستين لنفس العنصر بالضبط، يبدّل بينهما بسرعة | لا تعارض — كل سياق مستقل، القسم D أعلاه يحسم هذا بوضوح (اتحاد يُعاد حسابه لحظيًا حسب السياق النشط، لا حالة مخزَّنة تتضارب) |

# L. Security Scenarios

| السيناريو | الحماية |
|---|---|
| مستخدم يعدّل الجلسة يدويًا (Cookie tampering) ليضع `active_organization_id` لمؤسسة ليس عضوًا فيها | Middleware (B.1) يتحقق من `Membership` فعليًا بكل طلب، لا يثق بقيمة الجلسة وحدها — تعديل مزيَّف يُرفَض فورًا، يرجع لـ"شخصي" |
| Admin بمؤسسة A يحاول (عبر URL مباشر أو API لاحقًا) تعديل مقاعد مؤسسة B | كل Controller إداري (Access/Seat Management) يتحقق من `$user->memberships()->where('organization_id', $targetOrgId)->whereIn('role', [Owner, Admin])->exists()` صراحة — لا اعتماد على "افترض السياق النشط صحيح"، تحقّق مستقل بكل فعل حسّاس (دفاع مزدوج، نفس مبدأ قسم G) |
| طلب مباشر (لا واجهة) لبيانات وصول مؤسسة عبر تخمين معرّف (`subscription_id` مثلًا) | كل استعلام Entitlement/Access يمر عبر `EntitlementResolver`/فحص عضوية صريح، لا اعتماد على "المستخدم لن يخمّن الرقم" (Security through obscurity مرفوض) |

# O. Backward Compatibility

**كل استدعاء حالي لـ`EntitlementResolver::resolve($user, $item)` بلا المعامل الجديد يستمر يعمل بلا أي تغيير سلوك** — التوسّع بمعامل اختياري افتراضه `null` يحافظ حرفيًا على سلوك الخطوات ١-٤ كما هي، الخطوة ٥ فقط تُفعَّل لو مُرِّر سياق مؤسسة فعليًا. `MarketplaceController`/`MyAppsController` الحاليان (Phase 1b) **لا يحتاجان أي تعديل** لحد ربطهما فعليًا بمبدّل السياق (خارج نطاق هذا الـPhase حتى يُبنى CD-001).

# عشر سيناريوهات — مُختبَرة على الورق

### 1) مستخدم في مؤسسة واحدة
Membership واحدة، `Owner`. يفتح My Apps → يرى اشتراكاته الشخصية + (لو له مقعد) اشتراكات مؤسسته — سياق نشط تلقائي الوحيد الممكن (لا خيار تبديل ذو معنى، لكن يبقى "شخصي" الافتراضي الصريح لحد اختياره المؤسسة يدويًا — لا قفز تلقائي، قسم B.1). **لا مشكلة، مسار مباشر.**

### 2) مستخدم في مؤسستين
Membership بمؤسسة A (Lawyer) وB (Partner) — تطابق مثال "محمد" بالوثائق السابقة حرفيًا. سياق نشط = A → يرى اشتراكات A فقط + شخصي. يبدّل لـB → يرى اشتراكات B فقط + نفس الشخصي (لا يتغيّر). **لا دمج بأي لحظة (قسم C/D).**

### 3) مؤسسة لديها اشتراك، تريد إضافة 5 مستخدمين
Admin يفتح Seat Management → يعيّن 5 مقاعد بخمس استدعاءات متتالية لخوارزمية قسم I. لو `seat_limit=10` وكان مستخدَمًا منها 3 → الخمسة تنجح (يصل لـ8/10). لو كان مستخدَمًا 7 → أول ثلاثة تنجح، الرابع والخامس يُرفَضان صراحة ("لا مقاعد متاحة") — **لا فشل صامت، رسالة واضحة لكل محاولة رُفِضت تحديدًا.**

### 4) آخر Seat متاح، محاولتان متزامنتان (الأهم تقنيًا)
`seat_limit=5`، 4 مقاعد مستخدَمة. طلبان لتعيين المستخدَمَين A وB لآخر مقعد بنفس اللحظة تقريبًا. عبر خوارزمية قسم I: أول معاملة تحصل على القفل (`lockForUpdate`) تكمل (5/5)، الثانية تنتظر انتهاء الأولى، تعيد العدّ (تجده 5)، ترفض فورًا. **لا سيناريو 6/5 ممكن بنيويًا.** هذا بالضبط ما يتطلب اختبار Concurrency صريح (موثَّق بـImplementation Spec قسم Z) لا Unit Test عادي.

### 5) مستخدم يغادر المؤسسة
تفصيل كامل بقسم E — `MembershipRevoked` يُطلَق لأول مرة فعليًا، يُبطِل فقط المقاعد المرتبطة بتلك المؤسسة، اشتراكه الشخصي (لو له) يبقى سليمًا تمامًا.

### 6) حذف مستخدم من المؤسسة (بفعل إداري من Admin، لا مغادرة طوعية)
نفس مسار سيناريو ٥ تقنيًا (كلاهما ينتهي بحذف/تعطيل `Membership` فيُطلِق نفس الحدث) — الفرق فقط بالفاعل (Admin بدل المستخدم نفسه)، لا فرق بالنتيجة التقنية. **لا مسار كود منفصل مطلوب لكلا الحالتين.**

### 7) انتهاء اشتراك المؤسسة
تفصيل كامل بقسم F — إلغاء إداري (لا تاريخ تلقائي، لا Billing) يُبطِل كل المقاعد دفعة واحدة بمعاملة واحدة.

### 8) مستخدم لديه اشتراك شخصي + المؤسسة لديها اشتراك (لنفس العنصر بالضبط)
سيناريو دقيق: مستخدم مشترك شخصيًا بتطبيق مجاني (Phase 1b)، ومؤسسته اشتركت به أيضًا مؤسسيًا (Phase 2) ومنحته مقعدًا. عبر قاعدة الاتحاد (قسم D): وصوله = `has_access=true` من **مصدرين مستقلّين معًا** (`AccessAssignment` شخصي + `AccessAssignment` عبر مقعد). لا تعارض، لا أولوية أحدهما على الآخر يحتاج حسمًا — `EntitlementResolver` يتوقف عند أول `AccessAssignment` نشط يجده (الترتيب لا يهم، النتيجة `has_access` بأي الحالتين). **لو أُلغي أحد المصدرين (مثلًا انسحب من المؤسسة)، يبقى الآخر (اشتراكه الشخصي) سليمًا تمامًا.**

### 9) المستخدم لديه صلاحية بـA وليس بـB
هذا فعليًا Authorization لا Entitlement (قسم H) — خارج نطاق `EntitlementResolver` بالكامل. مثال ملموس: محامٍ له دور `Lawyer` بمؤسسة A (يقدر يعدّل قضايا)، ودور `Client` بمؤسسة B (يقدر يشوف فقط) — هذا الفرق **يُحسَم داخل كل تطبيق مستقبلي بمفرده** (مثال: إفلاس تك)، مستهلكًا `Membership.role` بالسياق النشط كمُدخَل، **لا** عبر Marketplace's `EntitlementResolver`. Marketplace فقط يحدد "يقدر يفتح إفلاس تك أصلًا بسياق B؟" — لا "وش يقدر يسوي بداخله".

### 10) محاولة الوصول المباشر لبيانات مؤسسة أخرى
مغطّى بالكامل بقسم L (Security Scenarios) — ثلاث طبقات دفاع مستقلة: (أ) Middleware يتحقق من العضوية الفعلية لا الجلسة وحدها، (ب) كل Controller إداري يتحقق من الصلاحية صراحة بمعزل عن السياق، (ج) لا اعتماد على تخمين معرّفات كخط دفاع. **فشل أي طبقة واحدة لا يعني اختراقًا — الطبقتان الأخريان تبقيان قائمتين.**
