# Hukm w Rakam — Marketplace Product & UX Architecture

**الحالة:** مسودة للمراجعة — بدون أي تنفيذ. لا كود، لا Migrations، لا تعديل على أي ملف تشغيلي، لا Core Platform جديدة، لا UI نهائي، لا Components فعلية.
**المرجع التقني الملزم:** `docs/marketplace-architecture-blueprint.md` (معتمدة مبدئيًا). كل قرار هنا يجب أن يكون متسقًا مع الكيانات والقيود المعرّفة هناك (`MarketplaceItem`, `Partner`, `Subscription`, `SubscriptionPlan`, `AccessAssignment`, `Active Organization Context`، إلخ) — هذي الوثيقة لا تُعرِّف كيانات جديدة، فقط تصمم كيف يعيشها المستخدم.

**التذكير الحاكم:**
> حكم ورقم = Core Platform. Marketplace = طبقة داخلها. الـ Marketplace ليس متجر تطبيقات تقليديًا — هو النظام اللي يسمح للمستخدم يبني بيئة عمله الرقمية من Applications وIntegrations وServices، بصلاحيات واستخدامات مختلفة حسب السياق.

**قاعدة العمل بهذي الوثيقة (كما طُلب):**
```
User Goal → User Context → User Journey → Product Capability → UX Flow → Screen → Component
```
ما نبدأ من "أي صفحات نحتاج" — كل قسم أدناه يُشتق من هدف مستخدم حقيقي، لا من قائمة صفحات جاهزة سلفًا. وكل قسم بالمعلومات المعمارية (IA) خضع لسؤال واحد إلزامي: **هل يوجد اليوم محتوى/بيانات حقيقية تخدم هذا القسم فعليًا؟** لو لا، القسم إما يُؤجَّل بالكامل أو يظهر بحالة Empty State صادقة — لا بيانات وهمية بأي شكل (Reviews، Ratings، Popular، عدد مستخدمين، إلخ).

**تذكير بالحالة الواقعية اليوم (من Section A بالوثيقة التقنية):** عنصر واحد فقط له محتوى ووظيفة حقيقية كاملة (بوابة معرفة، مجاني، `user_only`). البقية سبعة عناصر "قريبًا" بدون محتوى تشغيلي، لها فقط نموذج تسجيل اهتمام حقيقي (`service_interests`). لا Integration ولا Service حقيقي واحد موجود بعد. هذا يحدد بشكل مباشر أي قسم أدناه "يُبنى الآن" وأي قسم "نمط محجوز لاحقًا".

## 0. User-Facing Simplicity — طبقة الترجمة الإلزامية

**Complex Architecture ≠ Complex UX.** المعمارية بقسم ١-١٠ أعلاه (`MarketplaceItem`, `Subscription`, `AccessAssignment`, `Entitlement`, `SubscriptionSeat`, `Tenant`, `Polymorphic Subscriber`, `Billing Model`, `Active Organization Context`) تبقى دقيقة ومعقّدة بقدر ما تحتاجه حماية النظام وتوسّعه — لكن **لا مصطلح من هذي القائمة يظهر حرفيًا بأي شاشة أو نص واجهة بأي وقت**. المستخدم (محامٍ أو محاسب) يتعامل مع لغة بشرية بحتة.

| المصطلح التقني | الترجمة البشرية بالواجهة |
|---|---|
| Subscription (شخصي) | "اشتراكك" |
| Subscription (مؤسسي) | "اشتراك المؤسسة" |
| AccessAssignment | "لديك وصول" / "ليس لديك وصول" |
| Entitlement | "المزايا المتاحة لك" |
| SubscriptionSeat | "مقعد مستخدم" |
| Active Organization Context | "المؤسسة الحالية" |
| Request Access | "طلب الوصول" |
| Ask Admin | "طلب من مدير المؤسسة" |
| Tenant / Polymorphic Subscriber | لا تظهران — "أنت" أو اسم المؤسسة مباشرة |
| Billing Model | لا يظهر كمصطلح — ينعكس ضمنيًا فقط ("شخصي"/"للمؤسسة") |

هذا الجدول مرجع ملزم لكل قسم UX أدناه ولأي وثيقة تصميم لاحقة تُبنى فوق هذي الوثيقة (Design System، High-Fidelity) — أي نص واجهة يُقترَح لاحقًا يُفحَص مقابله أولًا.

## A. Product Architecture

الـ Marketplace ليس كتالوج عرض — هو **الطبقة اللي تربط قرار "أشترك/أربط/أطلب" بحياة المستخدم الفعلية بحكم ورقم** (هويته، مؤسسته، صلاحياته). خمس قدرات منتج أساسية، كل واحدة مبنية فوق التي قبلها:

```
1. Discover   — يكتشف المستخدم وش موجود (تصفح/بحث/توصية)
2. Evaluate    — يقرر هل يناسبه (صفحة تفاصيل تجيب "ليش أختاره")
3. Acquire     — يحصل عليه (Subscribe / Connect / Request — حسب النوع، قسم ٤ بالبرومت)
4. Access      — يستخدمه فعليًا (نقطة الدخول الحقيقية = AccessAssignment، لا مجرد "مشترك")
5. Manage      — يدير علاقته المستمرة به (My Apps، اشتراكات، مقاعد، فصل اتصال)
```

**قرار معماري-منتجي مهم:** الـ Marketplace **لا يملك بياناته الخاصة عن المستخدم** — هو عدسة (Lens) تعرض حالة حقيقية موجودة أصلًا بـCore Platform (اشتراكات، عضويات، صلاحيات). أي شاشة Marketplace تعرض "حالتك الآن" تقرأ من `Subscription`/`AccessAssignment`/`Membership` مباشرة، لا تخزّن نسخة موازية. هذا يمنع تعارض حالة بين "ما يراه المستخدم بالمتجر" و"ما يراه فعليًا بالتطبيق نفسه".

**الفرق الجوهري عن App Store تقليدي:** App Store يبيع "تنزيل"، وحكم ورقم تبني "بيئة عمل". لذلك القدرة الخامسة (Manage) ليست ميزة ثانوية — هي نفس أهمية Discover، لأن قيمة حكم ورقم الحقيقية تكبر كل ما زاد عدد العناصر المُدارة ضمن حساب واحد، لا كل ما زاد عدد التنزيلات.

## B. Information Architecture

كل عقدة بالشجرة أدناه مربوطة بحالة صريحة: **✅ يُبنى الآن** (له بيانات حقيقية اليوم) / **🔒 محجوز — Empty State صادق** (القسم موجود بالتصفح لكن فاضٍ بصدق، لا مخفي ولا وهمي) / **🚫 غير موجود إطلاقًا الآن** (لا رابط، لا عنوان، لا إشارة — نفس المبدأ المعتمد سابقًا لبنود التصميم المؤجَّلة).

```
Marketplace
├── Home                                  ✅ (زوايا حقيقية فقط — قسم G)
├── Browse (تصفح كامل)
│   ├── الكل                              ✅
│   ├── حسب النوع (Applications/Integrations/Services)  🔒 التبويب موجود بنيويًا، لكن Integrations/Services فاضية بصدق حاليًا (لا عنصر واحد من النوعين)
│   ├── حسب التصنيف (Category)             🔒 الجدول جاهز بالمعمارية، لكن لا تصنيفات حقيقية مُعرَّفة بعد غير التلميحي الحالي — يُفعَّل أول ما تُبنى `marketplace_categories` فعليًا (Phase 1)
│   ├── مجاني                             ✅ (له عناصر حقيقية اليوم: بوابة معرفة + عدة عناصر "قريبًا" مُعلَّمة مجانية)
│   ├── مدفوع/Premium                     🔒 موجود كفلتر بنيوي فقط — يُرجع نتيجة فارغة بصدق لأنه لا يوجد عنصر مدفوع واحد فعليًا اليوم. لا يظهر كقسم مروَّج بالصفحة الرئيسية (قسم G) حتى يوجد عنصر واحد حقيقي
│   ├── الجديد (New)                       ✅ (مبني على `created_at` حقيقي — ترتيب زمني صادق، لا يحتاج بيانات وهمية)
│   ├── مميّز (Featured)                   🔒 محجوز — يتطلب حقل `is_featured` بقرار تحريري إداري صريح (Filament)، لا يُفعَّل حاليًا لأن لا معيار تحرير مُعتمد بعد
│   └── الأكثر استخدامًا (Popular)          🚫 لا يظهر إطلاقًا — يتطلب Usage Tracking غير موجود أصلًا (قسم ٨ بالوثيقة التقنية: Events جزئي فقط)
├── تفاصيل عنصر (Application/Integration/Service)  ✅ للتطبيق الحقيقي · 🔒 Empty/Coming-soon للباقي (قسم H)
├── Search                                 ✅ (نص + فلاتر حقيقية، قسم N)
├── Recommendations                        🔒 Rules-based فقط، لا AI (قسم O)
├── مساحتي (My Workspace)
│   ├── My Apps                            ✅
│   ├── My Integrations                    🚫 لا واجهة إطلاقًا — لا عنصر Integration واحد بالنظام
│   ├── My Services                        🚫 لا واجهة إطلاقًا — لا عنصر Service واحد بالنظام
│   └── اشتراكاتي (Subscriptions)          ✅ (حتى لو حاليًا اشتراك مجاني وحيد لكل مستخدم — الشاشة حقيقية ومفيدة اليوم)
└── تجربة المؤسسة (Organization Apps/Seats)  🔒 محجوزة — تتطلب Phase 2 من الوثيقة التقنية (Seats/Active Org Context مفعّلة فعليًا)
```

**قاعدة الحسم:** أي عقدة تظهر بالتنقّل (Navigation) الفعلي **يجب** يكون لها Empty State صادق لو ما فيها محتوى (🔒) — لا تظهر أصلًا بالتنقّل لو 🚫. "Premium" مثال دقيق للفرق: فلتر تقني موجود (🔒، غير مروَّج) وليس قسم تسويقي بالواجهة الرئيسية.

## C. User Personas

مبنية على الجمهور الرسمي المعتمد بالوثيقة التأسيسية + حقل `compatibility/audiences` الحقيقي الموجود بالكود (`lawyer`, `firm`, `finance`, `student`) + مفهوم Partner المستقبلي.

| Persona | السياق (Context) | ملاحظة تصميم حاسمة |
|---|---|---|
| **محامٍ مستقل** | User-level، بلا مؤسسة غالبًا | اشتراكاته شخصية بحتة (`subscriber_type = User`) — لا Active Organization Context له أصلًا |
| **مالك/مدير مكتب محاماة** | Organization Owner/Admin | يرى Organization UX (قسم L) — يدير الاشتراكات والمقاعد لغيره، لا فقط لنفسه |
| **موظف/محامٍ بمكتب** | Organization Member، بلا صلاحية إدارة | يرى فقط ما خُصِّص له عبر `AccessAssignment`/Seat — لا يرى شاشات الإدارة إطلاقًا (قسم Q) |
| **محاسب/مستشار مالي** | User أو Organization Member، حسب سياق عمله | نفس منطق أعلاه، الفرق بـ`compatibility` tag المعروض له بالتصفح لا ببنية مختلفة |
| **طالب** | User-level، مهتم بمحتوى تعليمي/تدريب | يرى عناصر بحقل `compatibility` يشمل `student` بأولوية أعلى بالتوصيات (قسم O) |
| **عميل نهائي (فرد)** | User-level بحت | جمهور معتمد رسميًا بالوثيقة التأسيسية — يحتاج تجربة أبسط، عناصر أقل تقنية (Service مثل "طلب استشارة" أقرب لاحتياجه من Integration محاسبي) |
| **شريك خارجي (Partner)** 🔒 مستقبلي | خارج Core Platform الحالية | لا تجربة مستخدم نهائي له بهذي المرحلة — فقط ذكر مفاهيمي، القسم كامل مؤجَّل (Partner Portal، Phase 5 بالوثيقة التقنية) |
| **مستخدم متعدد السياقات** (مثال محمد بالوثيقة التقنية) | عضو بأكثر من مؤسسة، بأدوار مختلفة | الحالة الأكثر تعقيدًا تصميميًا — محور القسم D بالكامل |

## D. User Context Model

هذا القسم يترجم "Active Organization Context" من مفهوم معماري إلى قرار تجربة مستخدم ملموس.

### النموذج
```
User (هوية واحدة ثابتة)
 └── Memberships (0..N مؤسسة، كل واحدة بدور مستقل)
      └── Active Organization Context: قيمة واحدة فقط وقت أي لحظة
           ∈ { "شخصي" (Personal) , Organization X , Organization Y , ... }
```

### القرار الحاسم: متى يؤثر السياق ومتى لا يؤثر
ليس كل شيء بالـ Marketplace يتأثر بالسياق النشط بنفس الطريقة — الخلط هنا هو بالضبط الخطر اللي حذّرت منه المعمارية التقنية (Tenant Isolation). القاعدة المعتمدة:

| الشاشة | تتأثر بالسياق النشط؟ | السبب |
|---|---|---|
| Browse / Search / تفاصيل عنصر | **لا** | الكتالوج نفسه عام لكل المستخدمين — بيانات وصفية (Metadata) لا بيانات مؤسسة. الشخصنة هنا حسب الـ Role/compatibility (قسم O)، لا حسب Tenant |
| My Apps / اشتراكاتي / My Workspace | **نعم، إلزاميًا** | هذي بيانات ملكية واستخدام فعلية — تخضع لنفس قيد Tenant Isolation المعرَّف بالوثيقة التقنية |
| داخل أي تطبيق فعلي (مثال مستقبلي: إفلاس تك) | **نعم، إلزاميًا** | هذا بالضبط سيناريو "قضايا مكتب A لا تظهر وأنت شغّال باسم مكتب B" |

### كيف تظهر "مساحتي" حسب السياق
- **السياق = "شخصي":** تظهر فقط اشتراكات/عناصر المستخدم المباشرة (`subscriber_type = User`).
- **السياق = مؤسسة معيّنة:** تظهر اشتراكات تلك المؤسسة اللي له فيها Seat/AccessAssignment فعّال، **بالإضافة** إلى اشتراكاته الشخصية المباشرة معروضة بوسم واضح "شخصي" — لأن اشتراك شخصي حق للمستخدم بغض النظر عن أي مؤسسة يعمل باسمها الآن (متسق مع قاعدة "الاتحاد/Union" بالوثيقة التقنية، قسم ٢).
- **لا يوجد وضع "كل مؤسساتي مجتمعة بنفس الشاشة"** بهذي المرحلة — عرض مدمج عبر عدة مؤسسات بنفس الوقت هو بالضبط "خلط السياقات" الممنوع صراحة بالبرومت. أي حاجة لمقارنة سريعة بين مؤسستين تُحل بالتبديل الصريح بين السياقات، لا بعرض مدمج (هذا مطروح كسؤال مفتوح بقسم X لأنه قرار UX له كلفة احتكاك حقيقية).

### أين يعيش المبدّل (Context Switcher)
عنصر ثابت بالهيدر، وليس داخل Marketplace فقط — لأنه يخص كل حكم ورقم لا الـ Marketplace وحده. هذا **يُسجَّل كتوصية Core Platform منفصلة** (قسم U)، لأنه تعديل بسيط لكنه خارج نطاق ما يُسمح تنفيذه بهذي المرحلة.

## E. User Journeys

كل رحلة بصيغة السلسلة المطلوبة. الرحلات الأولى فقط لها Capability حقيقية اليوم؛ الباقي مؤجَّل ومُعلَّم صراحة.

### 1) محامٍ مستقل يكتشف بوابة معرفة ويبدأ استخدامها — ✅ ممكنة اليوم فعليًا
```
Goal:      "أبغى أعرف آخر تحديثات الأنظمة اللي تخص شغلي"
Context:   محامٍ مستقل، بلا مؤسسة، Active Context = شخصي
Journey:   يدخل Marketplace → يلقى بوابة معرفة بحالة "متاحة الآن، مجاني" → يفتح تفاصيلها → يدخل مباشرة (لا خطوة اشتراك يدوية، مجاني تلقائي)
Capability: Discover → Evaluate → Access (بدون Acquire صريح — التزويد التلقائي `FreeAppProvisioner` موجود فعليًا بالكود)
Flow:      Home/Browse → Application Detail → CTA "دخول" (Open، ليس Install لأنه بلا تثبيت فعلي)
Screen:    Marketplace Home, Application Detail
Component: service-card (حالة "متاحة الآن")، CTA button (حالة Open)
```

### 2) مستخدم يعبّر عن اهتمام بتطبيق "قريبًا" — ✅ ممكنة اليوم فعليًا (النموذج موجود بالفعل)
```
Goal:      "أبغى أعرف أول ما يتوفر إفلاس تك"
Context:   أي مستخدم، أي سياق
Journey:   يفتح تفاصيل عنصر "قريبًا" → يضغط "أنا مهتم" → تسجيل حقيقي بـ service_interests
Capability: Discover → Evaluate → (لا Acquire حقيقي — العنصر غير موجود بعد)
Flow:      Application Detail (حالة قريبًا) → Interest Modal (موجود فعليًا بالكود)
Screen:    Application Detail
Component: interest-modal (موجود)، CTA button (حالة "أنا مهتم")
```

### 3) مستخدم عضو بمؤسستين يبدّل السياق ليشوف اشتراكات مختلفة — 🔒 يتطلب Context Switcher (توصية Core Platform، قسم U)
```
Goal:      "أبغى أشوف تطبيقات مكتبي B، مو مكتبي A اللي أنا شغّال باسمه الآن"
Context:   عضو بمؤسستين، أدوار مختلفة
Journey:   يفتح المبدّل بالهيدر → يختار "مكتب B" → My Apps تعيد التحميل بسياق مكتب B فقط
Capability: (Manage) — يعتمد على وجود Active Organization Context بالجلسة، غير موجود بعد
Flow:      Header Switcher → My Apps (سياق جديد)
Screen:    My Apps / My Workspace
Component: org-context-switcher (غير موجود — توصية قسم U)
```

### 4) مالك مكتب يشترك مؤسسيًا ويوزّع مقاعد — 🔒 يتطلب Phase 2 (Seats + Organization billing)
```
Goal:      "أبغى أشترك بتطبيق مدفوع لمكتبي كامل، وأحدد مين يستخدمه من موظفيني"
Context:   Organization Owner/Admin
Journey:   يشترك باسم المؤسسة (لا شخصيًا) → يفتح "إدارة المقاعد" → يوزّع Seats على موظفين محددين
Capability: Acquire (Organization-level) → Manage Seats → كل موظف يحصل AccessAssignment مستقل
Flow:      Application Detail (billing_model=organization/both) → Subscribe as Organization → Organization UX (قسم L) → Seat Assignment
Screen:    Application Detail, Organization Apps, Seat Management
Component: subscriber-selector (شخصي/مؤسسة)، seat-assignment-table — لا شيء منها موجود اليوم
```

### 5) مالك مكتب يربط تكامل محاسبي — 🚫 خارج أي مدى زمني قريب (Phase 3)
```
Goal:      "أبغى أربط نظامي المحاسبي السحابي بحكم ورقم"
Context:   Organization Owner/Admin
Capability: Connect (لا Subscribe) — نمط UX مختلف تمامًا، قسم I
ملاحظة:    لا عنصر Integration واحد موجود بالنظام — هذي الرحلة IA/UX pattern فقط، بلا أي تنفيذ متوقع قريبًا
```

## F. Marketplace Navigation

**بنية التنقّل الأساسية (اليوم):**
```
Header حكم ورقم (عام)
 └── رابط "متجر التطبيقات" (موجود فعليًا)

داخل Marketplace:
 ├── الرئيسية (Home)
 ├── تصفح (Browse) — فلاتر: الكل / مجاني / قريبًا / الجديد
 ├── بحث (Search)
 └── مساحتي (My Workspace) — يتطلب تسجيل دخول، يظهر فقط @auth
```

**تبويبات محجوزة بنيويًا لكن غير معروضة الآن (🚫 لا تظهر بالتنقّل الفعلي):** تبويب Integrations وServices داخل Browse لا يُعرضان كخيارين منفصلين بالتنقّل حتى يوجد عنصر واحد حقيقي من كل نوع — إضافة تبويب فاضٍ بالتنقّل الرئيسي أسوأ من عدم إضافته (يوحي بوجود شيء غير موجود). بمجرد وجود Integration واحد حقيقي، يُضاف تبويبه — التصميم أعلاه يستوعب هذا بدون إعادة هيكلة IA.

**Breadcrumb:** Marketplace ›  [التصنيف/النوع لو محدَّد] › اسم العنصر — على صفحات التفاصيل فقط، يعتمد على `MarketplaceItem.type`/`category`.

**موضع Context Switcher:** الهيدر العام (توصية Core Platform، قسم U) — لا داخل تنقّل Marketplace نفسه، لأنه يخص كل حكم ورقم.

## H. Application UX

صفحة التفاصيل تجاوب على أسئلة القرار المطلوبة كلها (ماذا يحل / لمن / كيف يعمل / ماذا يشمل الاشتراك / هل يحتاج مؤسسة/مقاعد/تكامل/AI / ما البيانات والصلاحيات) — لكن **بمحتوى حقيقي فقط**. لأي حقل ما له قيمة حقيقية اليوم (مثال: "هل يدعم AI؟" لبوابة معرفة = لا)، يُعرض بصراحة "لا" أو يُحذف السطر، لا يُترك غامضًا.

### آلة حالة CTA (State Machine) — القاعدة المحورية بهذا القسم
CTA **دالة** بمدخلات حقيقية من Core Platform، لا نص ثابت لكل نوع:

| الحالة | الشرط (من بيانات حقيقية) | نص CTA |
|---|---|---|
| غير مسجّل دخول، عنصر مجاني | لا Auth | "سجّل ودخل مجانًا" |
| مسجّل، بلا AccessAssignment، عنصر مجاني | `AccessAssignment` غير موجود، `pricing_model=free` | "ابدأ الآن" (تزويد تلقائي) |
| مسجّل، له AccessAssignment فعّال | يوجد `AccessAssignment.status=active` | "فتح" (Open) |
| مسجّل، عنصر مدفوع، بلا اشتراك | لا `Subscription` | "اشترك" (Subscribe) 🔒 يتطلب Billing لاحقًا |
| مسجّل، له `Subscription` فعّال، بلا `AccessAssignment` (مثال: مقعد لم يُخصَّص له بعد) | Subscription نشط، Access غير موجود | "اطلب وصول" (Request Access) — يوجّه لمدير المؤسسة |
| عضو بمؤسسة، العنصر Organization-only، هو ليس Admin | لا صلاحية اشتراك | "اطلب من المدير" (Ask Admin) — لا يظهر له زر اشتراك مباشر إطلاقًا |
| اشتراك موجود، خطة أدنى من المطلوب للميزة | `PlanEntitlement` غير كافٍ | "ترقية" (Upgrade) 🔒 |
| عنصر يدعم فترة تجريبية 🔒 مستقبلي | — | "ابدأ تجربة" (Start Trial) — لا يوجد مفهوم Trial بالمعمارية التقنية الحالية أصلًا، هذا بند **مفتوح** (قسم X) لا مُقرَّر |

**مبدأ صارم:** لا يوجد زر "Install" بأي حال — هذا المصطلح لا يوصف طبيعة Application بحكم ورقم (بدون تثبيت فعلي، دخول مباشر بالهوية الموحّدة).

## I. Integration UX  — 🚫 نمط مصمَّم، لا تنفيذ قريب

مختلف جذريًا عن Application UX — لا "تفاصيل تسويقية"، بل **شفافية تشغيلية**:

```
Application Detail يجاوب:  "ليش أختاره؟"
Integration Detail يجاوب:  "وش بالضبط راح يحصل لبياناتي؟"
```

عناصر الشاشة (مفاهيمي فقط): ماذا يربط (نظامين بالاسم) → ماذا يُزامَن (اتجاه البيانات: صادر/وارد/الاثنين) → الصلاحيات المطلوبة من المزوّد الخارجي (Scope صريح قبل الموافقة) → حالة الاتصال الحالية (متصل/منقطع/خطأ) → آخر مزامنة ناجحة → سجل مشاكل حديثة → زر **Disconnect** صريح ومنفصل بصريًا عن أي CTA إيجابي (لتفادي ضغط عرضي).

CTA وحيد: **Connect** (لا Subscribe/Install). بعد الاتصال: **Configure** يستبدل Connect بنفس المكان.

هذا القسم كله IA/UX pattern محجوز — لا شاشة واحدة منه تُبنى قبل أول Integration حقيقي (Phase 3 بالوثيقة التقنية).

---

## J. Service UX — 🚫 نمط مصمَّم، لا تنفيذ قريب

خدمة = دورة حياة طلب، لا اشتراك مستمر بالضرورة:

```
Service Profile (مين يقدّمها — Partner أو حكم ورقم نفسها، وصف، نطاق التقديم)
 → Pricing (لو موجود — ثابت أو "عند الطلب")
 → Availability (لو خدمة بشرية — أوقات/سعة)
 → CTA: Request / Book / Contact (حسب طبيعة الخدمة، ليس زر واحد موحّد)
 → Status tracking بعد الطلب: قيد الطلب → مجدولة → قيد التنفيذ → مكتملة
```

هذا فعليًا امتداد UX لمفهوم "طلب استشارات" الموجود أصلًا بحكم ورقم الحقيقية (hw.sa) — الفرق أنه يصير عنصر Marketplace قابل للعرض والتصفح، لا ميزة معزولة. **لا يُبنى قبل وجود Service واحد حقيقي بالمعمارية التقنية.**

## K. Subscription UX

شاشة "اشتراكاتي" — حقيقية ومفيدة من اليوم الأول حتى باشتراك مجاني وحيد:

| العمود | المصدر |
|---|---|
| اسم العنصر | `MarketplaceItem` |
| مين المشترك (شخصي/باسم مؤسسة X) | `Subscription.subscriber_type` |
| الخطة | `SubscriptionPlan` |
| المقاعد (لو ينطبق) | `مستخدَم/الإجمالي` من `SubscriptionSeat` — 🔒 يظهر فقط بعد Phase 2 |
| تاريخ التجديد | `SubscriptionPlan.billing_cycle` — 🔒 لا قيمة حقيقية بلا Billing Engine (بلا CTA "جدد الآن" فعلي حتى ذاك الحين) |
| الحالة | `Subscription.status` |
| **وصولي الفعلي** | صف منفصل صراحة يعتمد على `AccessAssignment`، لا الحالة أعلاه — تصميم يجسّد "Subscription ≠ Access" بصريًا لا نصيًا فقط |

**حالة حافة مهمة يجب تصميمها بصراحة:** اشتراك `active` لكن `AccessAssignment` غير موجود/معلَّق (مثال: مقعد لم يُخصَّص بعد، أو وصول عُلِّق إداريًا). الشاشة تعرض هذا بوضوح: "أنت مشترك، لكن وصولك غير مفعَّل حاليًا — [اطلب من المدير]" — لا تظهره كأنه "يعمل" فقط لأن Subscription نشط.

## L. Organization UX

مخصصة حصرًا لأدوار Owner/Admin بالعضوية — لا يراها عضو عادي (قسم Q):

- **تطبيقات المؤسسة:** كل `Subscription` بـ`subscriber_type=Organization` لهذه المؤسسة.
- **إدارة الاشتراكات:** ترقية/إلغاء اشتراك مؤسسي — 🔒 يعتمد Billing لاحقًا، لكن **عرض الحالة** (بدون فعل شراء حقيقي) ممكن من اليوم لو وُجد اشتراك مؤسسي واحد (Phase 1 يتيح `subscriber_type=Organization` بنيويًا حتى لو لا استخدام فعلي بعد).
- **إدارة المقاعد:** تخصيص/سحب مقعد من عضو محدد — 🔒 Phase 2.
- **تعيين/إزالة مستخدمين من عضوية المؤسسة نفسها:** هذي فعليًا موجودة جزئيًا اليوم لكن **فقط من لوحة Filament**، لا من واجهة المستخدم — فجوة حقيقية تُسجَّل كتوصية Core Platform (قسم U)، لأن Marketplace Organization UX يفترض وجودها كواجهة مستخدم أصلًا.
- **رؤية الاستخدام:** 🚫 مؤجَّل بالكامل — يتطلب Usage Tracking غير موجود، لا يُعرض حتى كقسم فارغ (لا فائدة UX من "استخدام: —" بلا سياق).

## M. My Apps UX

يُصمَّم كـ **Workspace حقيقي**، لا قائمة بطاقات مكررة عن Browse. أربع مجموعات، كل واحدة لها معنى قرار مختلف:

```
1. نشطة الآن       — يوجد AccessAssignment فعّال (يمكن الدخول مباشرة، زر "فتح")
2. تحتاج إجراء منك  — Subscription موجود لكن Access غير مفعَّل/معلَّق (زر "اطلب وصول" أو توضيح السبب)
3. مهتم بها         — سجّل "أنا مهتم" بعناصر "قريبًا" (لا فعل مطلوب، فقط متابعة — يُشعَر تلقائيًا 🔒 عند الإطلاق، يتطلب Notifications غير موجودة، فعليًا حاليًا فقط قائمة بلا إشعار تلقائي)
4. متاحة لك، لم تُضَف بعد — عناصر تطابق compatibility المستخدم لكنه لم يتفاعل معها بعد (رابط مباشر لتفاصيلها، لا اشتراك تلقائي)
```

**العلاقة بـDashboard الموحّد الحالي (`platform/dashboard.blade.php`):** يوجد فعليًا قسم "تطبيقاتي" بالـ Dashboard اليوم يعرض المشترَك بها فقط (مجموعة 1 هنا تقريبًا). القرار المُوصى به: My Apps تصير **الصفحة الكاملة**، وقسم Dashboard الحالي يتحول لملخص مختصر منها بدل تكرار منطق منفصل — هذا تعديل بسيط لملف قائم فعليًا، **يُسجَّل كتوصية Core Platform (قسم U)** لأنه خارج الإذن الممنوح بهذي المرحلة (ممنوع تعديل ملفات تشغيلية).

## O. Recommendation UX

**المرحلة الأولى Rules-based صراحة، بلا أي ادّعاء ذكاء:**

| القاعدة | المصدر |
|---|---|
| "أدوات تناسب دورك" | `compatibility`/`audiences` مطابق لملف المستخدم |
| "أضِف ما يكمّل بيئتك" | عناصر لها نفس `category` لعنصر مشترك فيه المستخدم فعليًا (منطق بسيط، لا تعلّم آلي) |
| "بناءً على اهتمامك المسجَّل" | يستخدم `service_interests` الحقيقي الموجود فعليًا |

**ممنوع صراحة بهذي المرحلة:** "المستخدمون الذين اشتروا هذا اشتروا أيضًا" (يتطلب بيانات سلوك جماعي غير موجودة) — أي شكل من Collaborative Filtering مؤجَّل بالكامل، لا حتى بنسخة مبسّطة، لأنه يوحي بذكاء غير موجود فعليًا.

**شفافية إلزامية بالواجهة:** أي بطاقة "مقترح لك" تحمل توضيح مختصر *لماذا* (مثال: "لأنك محامٍ" أو "لأنك مهتم بإفلاس تك") — لا توصية بلا سبب معروض، هذا يمنع انطباع "AI يعرف كل شيء" الممنوع صراحة بالبرومت حتى قبل وجود AI فعلي أصلًا.

## P. AI UX

**الوضع الحقيقي اليوم: لا يوجد أي ميزة AI بالمنصة إطلاقًا — لا نقطة امتداد واحدة مُفعَّلة.** هذا القسم تصوّر مبدئي فقط لكيفية ظهوره **يوم يوجد** (Phase 4 بالوثيقة التقنية)، متسق مع طبقته المشتركة هناك:

```
AI لا يظهر كـ:  عنصر Marketplace مستقل، نافذة منبثقة إجبارية، badge يفرض نفسه
AI يظهر كـ:      تحسين داخل قدرة موجودة أصلًا (Search أذكى، توصية بتفسير أوضح، مساعدة سياقية داخل تطبيق مفتوح)
```

أربع خصائص إلزامية لأي ظهور AI مستقبلي بالواجهة (من البرومت مباشرة): **مفيد، سياقي، مدرك للصلاحيات، قابل للتفسير**. الخاصية الثالثة (Permission-aware) تعني بمصطلحات UX: أي نتيجة AI تُعرض للمستخدم لا يمكن أبدًا أن تحتوي معلومة هو نفسه لا يملك صلاحية رؤيتها كإنسان — هذا انعكاس مباشر لقيد Tenant Isolation بالوثيقة التقنية (قسم ٢) على مستوى الواجهة، لا مجرد قيد خلفي.

## Q. Permission UX

قاعدة عرض موحّدة عبر كل الشاشات أعلاه:

| الحالة | السلوك بالواجهة |
|---|---|
| عنصر غير مرتبط بدور المستخدم إطلاقًا (مثال: عميل نهائي يشوف Integration محاسبي معقّد) | **إخفاء** — لا فائدة من عرضه أصلًا (ليس قيد صلاحية، قيد ملاءمة) |
| عنصر مرتبط لكن يتطلب صلاحية غير متوفرة (مثال: موظف بلا صلاحية اشتراك مؤسسي) | **عرض + CTA بديل واضح** ("اطلب من المدير") — لا زر معطَّل (Disabled) بلا تفسير |
| بيانات تخص مؤسسة أخرى غير السياق النشط | **لا تظهر إطلاقًا بأي شاشة**، مهما كانت صلاحية المستخدم التقنية بالمؤسسة الأخرى — هذا القيد أعلى من أي قاعدة عرض ثانية بهذا الجدول، تطبيق مباشر لـTenant Isolation |
| وظائف إدارية (Organization UX، قسم L) لعضو عادي | **إخفاء كامل** — لا تظهر كـ tab معطَّل، تختفي من التنقّل تمامًا |

## S. Responsive Strategy

يتبع نفس نمط RTL/Tailwind المعتمد فعليًا بالمشروع (`layouts/platform.blade.php` وما حوله) — لا نظام جديد:

- **الفلاتر** (Browse/Search): تتحول من صف أفقي (Desktop) إلى Bottom Sheet قابل للطي (Mobile) — نمط شائع لا يحتاج اختراع مكوّن جديد.
- **مبدّل السياق (Context Switcher):** بالهيدر يتقلّص لأيقونة/قائمة منسدلة على الشاشات الصغيرة، لا يختفي أبدًا (خطورة خلط السياقات تبرر بقاءه ظاهرًا دومًا مهما ضاقت الشاشة).
- **بطاقات الخدمة:** شبكة 3 أعمدة (Desktop) → عمودين (Tablet) → عمود واحد (Mobile) — نفس الشبكة الحالية فعليًا بالكود.
- **جدول الاشتراكات/المقاعد:** يتحول لبطاقات مكدَّسة على الموبايل بدل جدول أفقي مضغوط (الجداول العريضة تجربة سيئة بالعربي/RTL على الموبايل تحديدًا).

## T. Accessibility Considerations

- **لا اعتماد على اللون وحده لنقل حالة** — كل Badge حالة (متاحة/قريبًا/مفعّل لديك) يحمل نصًا صريحًا دائمًا، لا لون فقط (مهم تحديدًا لأن نظام الحالات هنا أوسع من قبل — 7+ حالة CTA بقسم H).
- **تباين الألوان مع هوية البراند الحالية:** الذهبي (`gold-400`/`#F6B41B`) يُستخدم حاليًا كخلفية Badge بنص فاتح بمواضع بالكود — يحتاج تدقيق تباين فعلي (WCAG AA) عند التنفيذ، خصوصًا مع تضاعف عدد الـ Badges بهذا التصميم (حالة + مجاني + جديد + إلخ) — **يُسجَّل كملاحظة تنفيذ لمرحلة UI Design System القادمة**، لا قرار هنا.
- **لوحة المفاتيح:** الفلاتر ومبدّل السياق يجب يعملان بالكامل بلوحة المفاتيح فقط (لا اعتماد فقط على hover/click) — أساسي لمستخدمي مكاتب يستخدمون النظام ساعات طويلة يوميًا.
- **قارئ الشاشة:** أزرار CTA متغيّرة النص (قسم H) تحتاج `aria-label` يوضّح السبب لا النص فقط (مثال: زر "اطلب من المدير" يحتاج وصف مين المدير تحديدًا لو ممكن).
- **RTL:** موروث فعليًا وصحيح بالمشروع الحالي بالكامل — لا تغيير مطلوب هنا، فقط الحفاظ عليه بأي مكوّن جديد.

## U. Core Platform Recommendations

تعديلات بسيطة على Core Platform الحالية يحتاجها تصميم Marketplace UX أعلاه، لكن **لا تُنفَّذ بهذي المرحلة** حسب القيد الصريح — تُسجَّل فقط:

### 1. Active Organization Context Switcher بالهيدر العام
- **المشكلة:** لا توجد اليوم أي طريقة للمستخدم يحدد "أعمل الآن باسم أي مؤسسة؟" — القسم D بالكامل يفترض وجوده.
- **السبب:** بدونه، أي شاشة "مساحتي" تضطر تعرض كل شيء مختلطًا أو تختار مؤسسة عشوائيًا — كلاهما يخالف Tenant Isolation.
- **الحل المقترح:** عنصر ثابت بالهيدر (`layouts/platform.blade.php`)، يخزّن الاختيار بالجلسة، يُقرأ من كل استعلام Marketplace-context-aware.
- **الأثر:** يمس ملف تشغيلي حالي (الهيدر) + الجلسة — خارج إذن هذي المرحلة تحديدًا.
- **الأولوية:** عالية — شرط أساسي لأي شاشة بقسم D/L/M تتجاوز مستخدمًا واحد بمؤسسة واحدة.

### 2. تطوير قسم "تطبيقاتي" بالـ Dashboard الحالي ليصير مدخل My Apps
- **المشكلة:** يوجد منطق مشابه جزئيًا بـ`dashboard.blade.php` اليوم (يعرض `subscribedApps`) لكنه معزول عن أي تصميم Workspace أوسع (قسم M).
- **السبب:** تجنّب ازدواجية منطق بين Dashboard وMy Apps مستقبلًا.
- **الحل المقترح:** Dashboard يعرض ملخصًا مختصرًا فقط + رابط "عرض الكل" لصفحة My Apps الكاملة الجديدة.
- **الأثر:** تعديل ملف Blade + Controller موجودَين فعليًا.
- **الأولوية:** متوسطة — يمكن تأجيله لحد بناء My Apps فعليًا (لا استعجال قبل ذلك).

### 3. واجهة مستخدم لإدارة أعضاء المؤسسة (بدل Filament فقط)
- **المشكلة:** إضافة/إزالة عضو من مؤسسة تعمل اليوم فقط من لوحة Filament الإدارية، لا من واجهة المستخدم نفسها.
- **السبب:** Organization UX (قسم L) يفترض أن مالك المكتب يدير فريقه بنفسه، لا عبر طلب دعم فني.
- **الحل المقترح:** شاشة بسيطة ضمن Organization UX (دعوة بالبريد، تحديد دور، إزالة) فوق نموذج `Membership` الموجود أصلًا.
- **الأثر:** ملف/Controller جديد بالكامل، لا تعديل على ملف قائم — لكن يبقى خارج إذن هذي المرحلة (لا كود إطلاقًا).
- **الأولوية:** متوسطة-عالية — تصير عالية بمجرد اعتماد Organization UX للتنفيذ الفعلي.

## W. UX Risks

- **خطر الوهم بالاكتمال:** تبويبات/فلاتر محجوزة (🔒) بالتصفح، حتى لو فارغة بصدق، قد تُفهَم كـ"موجود لكن معطَّل" لا "غير مبني بعد" — يحتاج صياغة نص Empty State دقيقة جدًا، لا افتراض إنها تُفهَم تلقائيًا.
- **إرهاق الاهتمام (Interest Fatigue):** سبعة عناصر "قريبًا" بنفس الوقت، كل واحد يطلب "أنا مهتم" — خطر أن يتوقف المستخدم عن التفاعل الجاد بعد أول مرتين. لا حل مطروح هنا، يُسجَّل كمخاطرة مفتوحة.
- **تعقيد آلة حالة CTA:** 7+ حالة CTA مختلفة (قسم H) دقيقة معماريًا لكنها خطر ارتباك حقيقي لمستخدم عادي لو لم تُصمَّم بصريًا بعناية شديدة (تفريق واضح جدًا بين "اطلب من المدير" و"اطلب وصول" مثلًا، فرق دقيق لغويًا بالعربي).
- **ارتباك تبديل السياق:** مستخدم بمؤسستين قد ينسى أي سياق هو نشط الآن ويظن إنه يشترك باسم مؤسسة وهو فعليًا بسياق "شخصي" — يحتاج تأكيد بصري قوي جدًا بأي نقطة Acquire (ليس فقط بالهيدر).
- **تضارب توقعات "Premium":** وجود فلتر مدفوع فارغ قد يجعل المستخدم يفترض خطأً بالنظام بدل غياب محتوى — يحتاج نص توضيحي صريح لا اعتماد على الفراغ وحده.

## X. Open Questions

هذي أسئلة قرار حقيقية، لا أسئلة بلاغية — تحتاج إجابة صريحة من حكم ورقم قبل مرحلة UI Design System:

1. **عرض مدمج عبر عدة مؤسسات:** رفضنا "كل مؤسساتي بشاشة واحدة" حفاظًا على Tenant Isolation (قسم D) — لكن هل هذا صحيح فعليًا لتجربة مستخدم بمؤسسات كثيرة (محاسب يخدم عدة مكاتب مثلاً)؟ أم نحتاج "وضع مقارنة" للقراءة فقط بدون خلط بيانات تشغيلية؟
2. **مفهوم Trial:** لا وجود له بالمعمارية التقنية الحالية إطلاقًا (لا `SubscriptionPlan.trial_days` ولا أي حقل مشابه) — هل هو مطلوب فعليًا لنموذج تسعير حكم ورقم المستقبلي، أم نُسقطه من قسم H نهائيًا بدل إبقائه كخيار مذكور؟
3. **تسمية "Marketplace" بالعربي:** هذي الوثيقة استخدمت "متجر التطبيقات"/"Marketplace" بالتبادل تبعًا للكود الحالي (`platform.marketplace`) — هل الاسم النهائي المعتمد تسويقيًا "متجر التطبيقات" أم مصطلح آخر (مثال: "مساحة العمل"، أقرب لفلسفة "بيئة عمل" من "متجر")؟
4. **إشعار الاهتمام عند الإطلاق:** المستخدم اللي سجّل "أنا مهتم" — هل يُشعَر تلقائيًا عند إطلاق العنصر فعليًا؟ هذا يتطلب خدمة Notifications غير موجودة (قسم ٨ بالوثيقة التقنية) — قرار: نبنيها JIT عند أول تطبيق حقيقي يُطلَق من قائمة الاهتمام، أم نعتبرها أولوية أبكر لأنها تمس تجربة فعلية موجودة اليوم (نموذج الاهتمام شغّال بالفعل بلا إغلاق للحلقة)؟
5. **من يقرر "Featured"؟** ذكرنا حقل `is_featured` بقرار تحريري إداري (قسم B) — لا معيار تحرير مُعتمد اليوم. هل هذا قرار تسويقي (فريق تسويق حكم ورقم) أم منتجي (فريق المنصة)؟ يحدد أين تعيش الصلاحية بلوحة Filament لاحقًا.
