# Legacy Subscription Closure Plan — `app_subscriptions`

**الحالة:** تخطيط فقط — بدون كود، بدون Migration، بدون أي تعديل. كل رقم بهذي الوثيقة **حقيقي**، مُستخرَج فعليًا من قاعدة البيانات المحلية وقت الكتابة (لا تقديرات).
**المرجع:** `marketplace-access-control-audit.md` قسم 10 (نظاما وصول متوازيان) · AD-006 (Legacy Migration Boundary) · AD-013 (Single Source of Truth for Effective Access) · **AD-014 (Explicit User Intent Must Be Preserved)** — راجع أيضًا `legacy-subscription-l1-spec.md` للتحليل التفصيلي لـL1.
**الهدف الوحيد:** مسار آمن، تدريجي، بلا حذف مبكِّر، من "نظامَين متوازيَين" إلى "نظام واحد بمصدر حقيقة واحد" — **بدون** حذف الجدول القديم و**بدون** مزامنة تلقائية مستمرة بين النظامين (كلاهما ممنوع صراحة بطلبك).

**تحديث بعد المراجعة (2026-08-10):** التسلسل بقسم 3 أدناه **صُحِّح** من ثلاث مراحل لخمس — اكتشاف إن التسجيل/الدخول يكتبان للنظام القديم تلقائيًا (لا فقط `Dashboard` يقرأ منه) يعني "إيقاف الكتابة" خطوة منفصلة **يجب تسبق** أي Migration فعلي، لا تتبعه.

## 2. من هو مصدر الحقيقة اليوم؟ ومن يجب أن يكون؟

**اليوم (كما هو، غير مرغوب طويل المدى):**
```
Dashboard (القديمة)  → app_subscriptions → User::hasActiveSubscription()
Marketplace/My Apps  → subscriptions/access_assignments → EntitlementResolver
```

**الهدف (AD-013):**
```
Dashboard + Marketplace + أي شاشة مستقبلية
        ↓
        EntitlementResolver (مصدر واحد فقط)
```

**القرار (معتمد):** ✅ **المسار ب — تقاعد قسم "تطبيقاتي" باللوحة القديمة لصالح My Apps.** السبب المعتمد: ربط Dashboard القديمة بـ`EntitlementResolver` (المسار أ) كان سيعني ربط Core Platform بـMarketplace Domain الجديد — بعكس المبدأ التأسيسي إن Marketplace **إضافة فوق** حكم ورقم لا إعادة هندسة لنواتها. اللوحة القديمة تبقى موجودة مؤقتًا كـLegacy UI (لا تُحذَف)، لكنها **لا تصير مصدرًا جديدًا لمنطق Marketplace** — يطابق توصية `CD-002` المسجَّلة أصلًا. تنفيذ هذا القرار يبقى ضمن L3 (لم يُرخَّص بعد، ينتظر دوره بالتسلسل).

**تحديث (2026-08-10، بعد تنفيذ L1 فعليًا):** اكتشاف L1 التنفيذي (`phase-l1-legacy-write-cutoff-completion-report.md` §11 — مستخدم جديد لا يرى بوابة معرفة تلقائيًا بالوحة القديمة) دفع لتوثيق قرار أوسع بوثيقة مستقلة: `docs/dashboard-marketplace-transition-decision.md`. **لا يُلغي المسار ب أعلاه، يُنقِّحه:** `/dashboard` مستقبلًا لن يبقى Core-only ولا يُدمَج بالكامل بـMarketplace — يصير **Unified Home** بقسمين منفصلَي المصدر تمامًا (Core حقيقي + Marketplace عبر نفس مصدر My Apps الواحد، AD-013). "تقاعد القسم القديم" لا يزال قائمًا بمعناه الدقيق (القسم الحالي المبني على `app_subscriptions` يُحذف)، لكنه يُستبدَل بقسم Marketplace جديد يقرأ من المصدر الصحيح، لا يُحذَف بلا بديل. لا تنفيذ بعد — راجع الوثيقة الجديدة للتفاصيل الكاملة.

## 3. خطة إزالة الاعتماد — خمس مراحل (صُحِّحت من ثلاث)

**لماذا التصحيح:** الترتيب الأصلي افترض "قراءة فقط" هي المشكلة، ثم Migration، ثم تقاعد. اكتُشف إن **الكتابة نفسها مستمرة تلقائيًا بكل تسجيل دخول** (لا فقط التسجيل الأول) — فلو رحَّلنا البيانات (L2 قديمًا) قبل إيقاف الكتابة، أي دخول لاحق لمستخدم يعيد كتابة سجل قديم قد يُقرَأ لاحقًا بالخطأ لو أُعيد تشغيل أي أداة ترحيل. **إيقاف الكتابة الجديدة يجب يسبق أي Migration فعلي، لا يتبعه.**

### L0 — Discovery ✅ (مكتمل بهذي الوثيقة)
الجرد الكامل بقسم 1 أعلاه — لا مستهلك غير موثَّق تبقّى (تأكيد عبر `grep` شامل، لا اعتماد على الذاكرة).

### L1 — Stop New Legacy Writes ✅ (منفَّذة ومعتمدة رسميًا — `phase-l1-legacy-write-cutoff-completion-report.md`)
**الهدف:** لا كاتب واحد جديد يكتب لـ`app_subscriptions` بعد اكتمال هذي المرحلة. **لا Migration بيانات — لم تحدث.** ثلاث نقاط استدعاء (`RegisteredUserController`, `HomeController`, `DashboardController`) عُطِّلت بحذف سطر/سطرين لكل ملف فقط، بلا بديل/Synchronization. تحقَّق بدليل قاعدة بيانات حقيقي (before=after على ثلاثة جداول) + 109/109 اختبار + تحقق بصري بمتصفح حقيقي.

### Dashboard Decision ✅ (`dashboard-marketplace-transition-decision.md`، تخطيط فقط)
اتجاه معماري بعيد المدى لـ`/dashboard`: Unified Home (Core + Marketplace بمصدرين منفصلين تمامًا) — لا تنفيذ، فقط تثبيت اتجاه لأي مرحلة تنفيذ لاحقة.

### L2 — Safe Migration (تحتاج إذنًا منفصلًا، بعد L1 فقط)
**الهدف:** ترحيل البيانات التاريخية (الفروق المتبقية من L0/L1) بأمان تام — يطبّق AD-014 حرفيًا (فحص "وجود أي سجل" لا "غياب حالة فعّالة"، Migration Eligibility Matrix الكاملة بـ`legacy-subscription-l1-spec.md` قسم E). لا تُنفَّذ قبل إصلاح خطر إعادة التفعيل المكتشَف بقسم 4 أدناه.

### L3 — Legacy Read Elimination (تحتاج إذنًا منفصلًا، بعد L2)
**الهدف:** لا قارئ واحد يستهلك `app_subscriptions`/`hasActiveSubscription()` لاتخاذ قرار وصول. يشمل حسم قرار مسار Dashboard (أ/ب بقسم 2 — **معتمد الآن: المسار ب، تقاعد القسم لصالح My Apps**، راجع تحديث القرار بالمحادثة).

### L4 — Retirement (مرحلة لاحقة، بعد استقرار L3 لفترة، تحتاج إذنًا منفصلًا)
**الهدف:** الجدول نفسه **لا يُحذَف حتى هنا** — يبقى موجودًا كأرشيف تاريخي بعد توقف كل قراءة وكتابة جديدة إليه. حذف الجدول فعليًا (Migration `down`/`dropIfExists`) **قرار منفصل، خارج نطاق هذي الخطة بالكامل** — لا يُطرَح إلا بعد فترة استقرار طويلة تُحدَّد وقتها.

**لا مزامنة تلقائية مستمرة بين النظامين بأي مرحلة من الخمس** — بالضبط كما طلبت، تفاديًا لدورة كتابة متبادلة يصعب تتبعها.

## 4. Backfill — أرقام حقيقية من قاعدة البيانات المحلية الآن

```
سجلات app_subscriptions فعّالة:           4  (مستخدمون: 5, 6, 7, 8)
سجلات subscriptions (شخصي) فعّالة:         1  (مستخدم: 5)

مستخدمون بالقديم فقط (لم يُرحَّلوا):        3  → 6, 7, 8
مستخدمون بالجديد فقط (بلا أي سجل قديم):     0
مستخدمون بالاثنين معًا:                    1  → 5
```

### هل يوجد تعارض؟
**نعم — تعارض حقيقي واحد مكتشَف فعليًا، لا نظري:**

المستخدم رقم 6 له سجل قديم **فعّال** (`app_subscriptions.status=active`)، لكن سجله الجديد **`cancelled`** صراحة (ألغى اشتراكه بنفسه عبر واجهة Marketplace الجديدة وقت اختبار Phase 1b). **اختُبِر فعليًا الآن أثناء إعداد هذي الوثيقة:**

```
حالة سجل المستخدم 6 الجديد قبل: cancelled
$ php artisan marketplace:backfill-free-access
→ "تم ترحيل 3 سجل وصول..."
حالة سجل المستخدم 6 الجديد بعد: active   ← أُعيد تفعيله تلقائيًا، بعكس رغبته الصريحة
```

**هذا خطر حقيقي مؤكَّد بالتجربة، لا افتراض:** `marketplace:backfill-free-access` بصيغته الحالية **غير آمن لإعادة التشغيل** — الشرط الوحيد بالأمر هو "هل عنده سجل جديد **فعّال** حاليًا؟" (`active()`)، لا "هل سبق له أي سجل جديد بأي حالة (حتى لو ألغاه)؟". أُعيد الحالة لطبيعتها يدويًا فور اكتشاف هذا (`SubscriptionService::cancel()`)، لا أثر متبقٍ بقاعدة البيانات.

### هل يمكن تشغيل Backfill بأمان؟
**ليس بصيغته الحالية دون تعديل — يحتاج شرطًا إضافيًا** ("لا يوجد سجل جديد بأي حالة إطلاقًا لهذا المستخدم/العنصر، لا فقط 'غير فعّال حاليًا'") قبل أي تشغيل ثانٍ مستقبلي. **هذا تعديل كود — خارج نطاق هذي الوثيقة التخطيطية، يُسجَّل هنا كمتطلب لـPhase L2/L3، لا يُنفَّذ الآن.**

### كيف نتحقق من 100% Parity؟
معيار مقترَح (تصميم فقط): استعلام مقارنة بسيط يعادل ما بقسم Backfill أعلاه — عدد "قديم فقط" يجب يساوي صفر بعد الترحيل، **مع** استثناء صريح للمستخدمين اللي ألغوا اشتراكهم الجديد عمدًا (لا يُحسَبون "غير مطابقين"، حالتهم صحيحة ومقصودة). لا Parity Check آلي مكتوب لهذا بعد (بخلاف Parity الكتالوج بـPhase 1a) — يُبنى وقت تنفيذ L2 لو احتيج فعليًا.

## 5. Rollback

| الخطوة | كيف نرجع لو ظهرت مشكلة |
|---|---|
| L1 — Stop New Legacy Writes | تراجع بسيط — إعادة استدعاء `FreeAppProvisioner::ensure()` بنقاط الاستدعاء الثلاث (تغيير كود بحت، لا بيانات فُقِدت) |
| L2 — Safe Migration | لو اكتُشف خطأ ترحيل، السجلات الجديدة المُنشأة بـL2 تُلغى (`cancel()`) فرديًا — لا تراجع جماعي مطلوب لأن كل سجل مستقل |
| L3 — Legacy Read Elimination | تراجع بسيط — `DashboardController` يعود لقراءة `user->subscriptions()` كما كان |
| L4 — Retirement | غير مطروح بهذي الخطة أصلًا — لا Rollback مطلوب لخطوة لم تُرخَّص |

## الخلاصة

**L1 منفَّذة ومعتمدة رسميًا.** **قرار مسار Dashboard محسوم بمستويين الآن:** المسار ب (قسم 2، تقاعد القسم القديم) + اتجاه Unified Home بعيد المدى (`dashboard-marketplace-transition-decision.md`) — لم يعد عائقًا أمام L3 لاحقًا. **اكتُشف أثناء إعداد L1 Spec خطر تشغيلي حقيقي بأداة الترحيل نفسها** (قسم 4، الآن مُقنَّن بـAD-014 ومُشدَّد إضافيًا بوثيقة قرار Dashboard) — يجب حله **قبل** L2، لا أثناءه أو بعده.

**لا Hardening أمني مطلوب** — كل ما بهذي الوثيقة تنظيم/دَين تقني تشغيلي، لا ثغرة.
