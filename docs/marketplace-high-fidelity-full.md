# Hukm w Rakam — Marketplace High-Fidelity Design (Full Coverage)

**الحالة:** مسودة للمراجعة — Design فقط. لا كود، لا Blade/Livewire/Laravel، لا تعديل ملف تشغيلي، لا تغيير Core Platform.
**المراجع الملزمة (بالترتيب):** `marketplace-architecture-blueprint.md` (Target Architecture) → `marketplace-product-ux-architecture.md` (Product/UX Architecture، يتضمّن الآن قسم ٠ Terminology) → `marketplace-ui-design-system.md` (UI Design System، يتضمّن الآن قسم ٠ Terminology) → `marketplace-high-fidelity-pilot.md` (**معتمدة** — الشاشات 1-6 هنا مرجعها الأساسي، لا تُعاد من الصفر، فقط دلتا/توسيع).

**التزام المصطلحات (قسم ٠ بالوثيقتين المرجعيتين):** كل نص واجهة بهذي الوثيقة يلتزم حرفيًا بجدول الترجمة المعتمد — "اشتراكك"، "اشتراك المؤسسة"، "لديك وصول/ليس لديك وصول"، "المزايا المتاحة لك"، "مقعد مستخدم"، "المؤسسة الحالية"، "طلب الوصول"، "طلب من مدير المؤسسة". لا `MarketplaceItem`/`Subscription`/`AccessAssignment`/`Entitlement`/`Seat`/`Tenant`/`Billing Model` بأي نص مستخدم-مواجه بهذي الوثيقة.

**قاعدة الصدق (بلا استثناء عبر كل الأقسام):** أي شاشة/حالة لا بيانات حقيقية وراءها اليوم = **Future State موسومة بوضوح**، لا تنفيذ، لا بيانات مُختلَقة، لا سلوك خلفي مُفترَض. الحالات الحقيقية القابلة للاختبار اليوم فعليًا محدودة: بوابة معرفة (تطبيق مجاني شخصي)، سبعة عناصر "قريبًا" + `service_interests`، عضوية مؤسسة (`Membership`, عرض فقط). كل ما هو أبعد من هذا = Future.

**القاعدة النهائية الحاكمة لكل قرار بهذي الوثيقة:**
> Simple UX + Strong Architecture + Professional Information Density + Clear Actions + Trust — **لا** More Screens + More Cards + More Badges + More Features.

# القسم الأول: A–Z (التجارب والشاشات)

## A. Marketplace Home
**المرجع الأساسي:** الشاشة 1 بـPilot المعتمد — لا إعادة تصميم، البنية (توجيه → بيئتي الآن → استكشف → الجديد → Ecosystem ثانوي) تبقى كما هي حرفيًا.

**دلتا عند التوسّع (50-500 عنصر مستقبلًا):** منطقتا "استكشف حسب دورك" و"الجديد" **تبقيان بنفس الحجم البصري** (3-4 و2-3 بطاقات على التوالي) بغض النظر عن حجم الكتالوج — الصفحة الرئيسية أداة توجيه سريع، لا معرض كامل. أي زيادة بحجم الكتالوج تُمتَص بصفحة Catalog (قسم B)، لا بالرئيسية.

**دلتا العلاقات:** بدل الرسم التوضيحي الكامل كعنصر متكرر، منطقة "بيئة الخدمات المتكاملة" تبقى رابطًا ثانويًا (كما بـPilot) — أي علاقات فعلية بين عناصر مملوكة للمستخدم (Related Items، قسم S) **لا تظهر بالرئيسية إطلاقًا**، فقط بصفحات التفاصيل حيث القرار سياقي.

## B. Catalog
**المرجع الأساسي:** الشاشة 2 بـPilot المعتمد.

**دلتا التوسّع لـ50/100/500 عنصر:**
| العتبة | السلوك |
|---|---|
| حتى ~24 عنصر | شبكة كاملة بلا تقسيم صفحات (وضع اليوم: ٨ عناصر) |
| > 24 عنصر | زر **"تحميل المزيد"** يظهر أسفل الشبكة (نمط مُقرَّر مسبقًا بـPilot، يُفعَّل الآن فعليًا كقاعدة نشطة عند العتبة) |
| > ١ نوع حقيقي (`type`) | تبويب/فلتر نوع يظهر (Application/Integration/Service) — 🔒 حتى وجود نوع ثانٍ حقيقي |
| > ١ تصنيف حقيقي (`category`) | شريط تصنيفات ثانوي أسفل الفلاتر الأساسية مباشرة (Chips قابلة للطي على الموبايل) — 🔒 حتى وجود `marketplace_categories` فعلية (Phase 1) |
| وجود وسوم (Tags) حقيقية | 🔒 بعيد المدى — لا تصميم تفصيلي له الآن (لا كيان `marketplace_item_tags` مبني، ولا حتى مجدول قريبًا) |

**قاعدة صارمة عند التوسّع:** الفلاتر لا "تتراكم" بلا حدود بصرية — بعد فلترين نشطين معًا، شريط "الفلاتر النشطة" (Chips قابلة للإزالة الفردية) يظهر أعلى الشبكة مباشرة بدل الاكتفاء بتظليل الـPills وحدها، لوضوح أعلى بكثافة معلومات أكبر.

## E. Service Details — 🚫 جديد بالكامل، Future Pattern

لا Service حقيقي واحد بالنظام. تصميم نمط جديد كامل، بنفس شارة "معاينة مستقبلية" الثابتة المستخدمة بـD:

```
┌───────────────────────────────────────────────────────┐
│  ⚠ معاينة مستقبلية — لا خدمة فعلية متاحة اليوم            │
├───────────────────────────────────────────────────────┤
│  [أيقونة]  اسم الخدمة (فئة توضيحية عامة، لا اسم حقيقي)     │
│            مقدَّمة من: [نمط عام — "مزوّد الخدمة"]           │
├───────────────────────────────────────────────────────┤
│  ماذا تقدّم؟ (وصف الفئة)                                  │
│  السعر: "عند الطلب" — لا رقم مُختلَق أبدًا                  │
│  التوفر: نمط عام، لا جدول مواعيد وهمي                     │
│                                                          │
│         [ طلب / حجز / تواصل ]  ← معطَّل، لا وظيفة حقيقية    │
└───────────────────────────────────────────────────────┘
```

**الفرق البنيوي عن Integration Details:** لا "اتجاه بيانات"/"صلاحيات ربط" هنا — بدلها "مقدَّم من" (شفافية عن الجهة المقدِّمة، امتداد لمفهوم Partner المستقبلي) و"التوفر" (سعة/جدولة، لا مزامنة بيانات). CTA يتغيّر حسب فئة الخدمة المفترَضة (آلي/بشري) لا نص ثابت — لكن **لا فرع تصميم فعلي لكل فئة الآن**، فقط الإشارة إلى إن الـCTA سيتغيّر (Request/Book/Contact) لحظة وجود خدمة حقيقية تحدد فئتها.

## F. My Apps — من قائمة إلى Workspace حقيقي

**تطوير مباشر للشاشة 5 بـPilot.** التصميم الآن يستوعب الأنواع الثلاثة (Application/Integration/Service) ببنية واحدة، بخمس مجموعات دلالية بدل الأربع السابقة — لكن **كل مجموعة تظهر فقط لو لها محتوى حقيقي أو حالة Future قابلة للعرض بصدق**:

```
┌───────────────────────────────────────────────────────┐
│  بيئتي في حكم ورقم                                       │
│  عضويتي: [اسم المؤسسة — الدور]  ← عرض فقط (كما بـPilot)   │
├───────────────────────────────────────────────────────┤
│  أستخدمه الآن (N)               ← لديك وصول فعّال          │
├───────────────────────────────────────────────────────┤
│  يحتاج إجراء منك (N)  🔒         ← مشترك، لكن "ليس لديك وصول" بعد │
├───────────────────────────────────────────────────────┤
│  متاح لي (N)                    ← يطابق دورك، لم تُضِفه بعد  │
├───────────────────────────────────────────────────────┤
│  متاح للمؤسسة (N)  🔒            ← اشتراك المؤسسة، لم يُخصَّص لك مقعد بعد │
├───────────────────────────────────────────────────────┤
│  مهتم به (N)                    ← "أنا مهتم" الحقيقي        │
└───────────────────────────────────────────────────────┘
```

**"غير متاح لي" — قرار تصميم صريح: لا يظهر كمجموعة منفصلة.** عناصر لا تخص دور المستخدم إطلاقًا **تُخفى بالكامل** (قاعدة Permission UX، قسم Q بوثيقة الـUX الأصلية) — لا مجموعة "غير متاح لي" تُعرض كقائمة حسرة/حرمان. الفرق بينها وبين "يحتاج إجراء"/"متاح للمؤسسة" (وهي عناصر ذات صلة لكن تنتظر فعلًا): تلك تظهر لأنها **قابلة للفعل قريبًا**، هذي لا قيمة لعرضها إطلاقًا.

**الحقيقة اليوم:** فقط مجموعتا "أستخدمه الآن" و"مهتم به" لهما محتوى حقيقي قابل للعرض. "متاح لي" ممكنة جزئيًا (عناصر تطابق `compatibility` المستخدم، بيانات حقيقية). "يحتاج إجراء" و"متاح للمؤسسة" 🔒 **تُخفيان بالكامل اليوم** (لا `AccessAssignment` ولا اشتراك مؤسسي بقاعدة البيانات) — يظهران فقط لحظة Phase 1/2 فعليًا، لا حتى كـEmpty State (سبق تقريره بـPilot: لا عنوان قسم فارغ بلا محتوى حقيقي محتمل).

**قاعدة عدم الازدحام عند تعدد الأنواع مستقبلًا:** كل مجموعة تعرض بطاقات مختلطة الأنواع (Application + Integration + Service معًا) — **لا تبويب منفصل لكل نوع داخل My Apps** إلا لحظة وجود ≥٣ عناصر حقيقية من نوع واحد على الأقل (عندها فلتر نوع اختياري أعلى المجموعات، لا تبويبات منفصلة تكسر رؤية "بيئتي كاملة بنظرة واحدة").

## G. My Integrations — 🚫 Future Pattern بالكامل

لا رابط تنقّل حقيقي له اليوم (قاعدة IA: 🚫 لا Integration واحد حقيقي). النمط مصمَّم مسبقًا: نفس بنية `WorkspaceSection` من My Apps، لكن مُصفّاة لنوع Integration فقط. المحتوى الوحيد الممكن بصدق اليوم لو فُتحت الصفحة يدويًا: Empty State واحد كامل الشاشة — "لا تكامل مفعّل بعد" + رابط لتصفح فئات التكامل المستقبلية (نفسها 🔒 بقسم B). **لا تُضاف كرابط فعلي بالتنقّل قبل أول Integration حقيقي.**

## H. My Services — 🚫 Future Pattern بالكامل

نفس معاملة G حرفيًا، لنوع Service. Empty State: "لا خدمة مطلوبة بعد" + رابط لتصفح الخدمات المستقبلية.

## I. My Subscriptions

**قرار تصميم صريح: ليست Finance Dashboard.** الجدول التقني الكامل (قسم ٢١/٣٢ بالـDesign System) **يبقى محجوزًا لسياق Organization Management (قسم J) الإداري**، لا لهذي الشاشة الشخصية. هنا: بطاقات مبسّطة، كل واحدة تجاوب مباشرة على الأسئلة الستة المطلوبة، بلا جدول كثيف:

```
┌─────────────────────────────────────────┐
│  [أيقونة] بوابة معرفة          اشتراكك    │  ← ماذا أملك + مين المشترك
│  الخطة: مجانية بالكامل                     │  ← ما الخطة
│  يستخدمها: أنت فقط                        │  ← من يستخدمها
│  التجديد: لا ينطبق (اشتراك مجاني دائم)      │  ← متى تتجدد
│  [ماذا لو ألغيت؟ ▾]                        │  ← ماذا يحدث إذا انتهت (قابل للطي، لا يُفرَض ظاهرًا)
└─────────────────────────────────────────┘
```

**"كيف أغيّرها؟"** 🔒 لا يظهر كزر فعلي اليوم — لا خطط بديلة حقيقية لأي عنصر حاليًا (خطة وحيدة لكل عنصر). يظهر لحظة وجود ≥٢ خطة حقيقية لنفس العنصر.

**اشتراك مؤسسي (🔒 Future):** نفس بنية البطاقة، لكن السطر الثاني "اشتراك المؤسسة" + "يستخدمها: N من M مستخدم" (رابط لصفحة الأعضاء لو المستخدم Admin، نص ثابت غير قابل للنقر لو عضو عادي — قاعدة صلاحيات Q تُطبَّق هنا مباشرة).

## J. Organization Management — مدير/مالك المؤسسة فقط

🔒 **Future بمعظمها** (تتطلب اشتراكات مؤسسية حقيقية، Phase 2) — النمط يُصمَّم الآن كاملًا:

```
┌───────────────────────────────────────────────────────┐
│  إدارة [اسم المؤسسة]                                     │
├───────────────────────────────────────────────────────┤
│  اشتراكات المؤسسة (N)         → بطاقات (مثل I، بمعلومات إضافية: عدد المقاعد المستخدمة) │
├───────────────────────────────────────────────────────┤
│  الأعضاء (N)                  → قائمة (اسم، دور، تاريخ الانضمام) — [دعوة عضو] [إزالة] │
├───────────────────────────────────────────────────────┤
│  [إدارة الوصول →]  [إدارة المقاعد →]   ← روابط لـK وL       │
└───────────────────────────────────────────────────────┘
```

**قاعدة صلاحية صارمة (مكرَّرة من وثيقة الـUX، مُثبَّتة هنا تصميميًا):** هذي الشاشة **بأكملها** غير موجودة بالتنقّل لمستخدم ليس Owner/Admin بعضويته — لا تبويب معطَّل، لا رابط مخفي بـCSS فقط، غياب تام من شجرة التنقّل المُقدَّمة له.

**ملاحظة فجوة حقيقية (غير مُعاد بناؤها هنا، فقط مُشار لها):** إدارة الأعضاء (دعوة/إزالة) تعمل اليوم فقط من Filament — توصية Core Platform مسجَّلة مسبقًا بوثيقة الـUX (قسم U هناك)، لا تتكرر هنا كتوصية جديدة.

## K. Access Management — أداة المدير لمنح/سحب "الوصول"

🔒 **Future بالكامل** (تتطلب `AccessAssignment` + اشتراك مؤسسي، Phase 1/2):

```
العضو            التطبيق/الخدمة       الحالة          إجراء
─────────────────────────────────────────────────────
أحمد محمد         بوابة معرفة          لديه وصول        [سحب الوصول]
سارة علي          بوابة معرفة          ليس لديه وصول     [منح الوصول]
```

نمط جدول (قسم ٣٢ بالـDesign System) — هذا **بالضبط** السياق الإداري المبرِّر لاستخدام الجدول الكثيف (بخلاف I الشخصية). فعل "منح/سحب" فوري بتأكيد مصغَّر (Toast، لا Modal ثقيل لفعل متكرر إداريًا).

## L. Seat Management — أداة المدير لتوزيع "مقاعد المستخدمين"

🔒 **Future بالكامل** (Phase 2):

```
اشتراك المؤسسة: بوابة معرفة (Enterprise) — ٧ من ١٠ مقاعد مستخدَمة
─────────────────────────────────────────────────────
[+ تعيين مقعد لعضو]

العضو            تاريخ التعيين
─────────────────────────────────────────────────────
أحمد محمد          ٢٠٢٦/٠١/١٠           [إزالة المقعد]
```

**الفرق عن K:** Seat Management يتحكّم بـ"من له مقعد ضمن حد الخطة" (رقم محدود)، Access Management يتحكّم بتفعيل/تعليق الوصول لمن *له* مقعد أصلًا — طبقتان منفصلتان بصريًا وإداريًا، مطابقتان لفصل Subscription≠Access≠Seat المعماري، **لكن بلا أي مصطلح تقني ظاهر** (قسم ٠).

## M. Application Lifecycle UX

الحالة **لا تكتفي بتغيير Badge** — تغيّر CTA والمحتوى والإجراءات والنبرة معًا:

| الحالة | Badge | CTA | المحتوى | الإجراءات المتاحة | الحقيقة اليوم |
|---|---|---|---|---|---|
| **Available** (غير مشترك) | "متاحة الآن" | "ابدأ الآن"/"اشترك" | كامل (مزايا، لمن يخدم) | تصفّح، بدء | ✅ حقيقي (٦ من الثمانية "قريبًا" ليست هنا فعليًا — بوابة معرفة فقط) |
| **Active** (لديك وصول) | "مفعّل لديك" | "فتح" | نفسه + ملخص استخدام مبسّط (لو وُجد) | فتح مباشر | ✅ حقيقي (بوابة معرفة) |
| **Needs Access** | "بانتظار الوصول" (`state-pending`) | "طلب الوصول" | رسالة صريحة: "أنت مشترك، لكن وصولك غير مفعَّل بعد" | طلب الوصول | 🔒 Future |
| **Needs Subscription** (Organization-only، بلا اشتراك مؤسسي) | "يتطلب اشتراك المؤسسة" | "طلب من مدير المؤسسة" | يوضّح إنه يتطلب اشتراك مؤسسي، لا اشتراك فردي ممكن لهذا العنصر تحديدًا | طلب من المدير فقط — **لا** زر اشتراك مباشر | 🔒 Future |
| **Coming Soon** | "قريبًا" | "أنا مهتم" | وصف مختصر + سبب عدم التوفر لو معروف | تسجيل اهتمام | ✅ حقيقي (٧ عناصر اليوم) |
| **Suspended** | "غير متاح مؤقتًا" (`state-attention`، محجوز) | لا CTA فعّال — رسالة فقط | بانر تنويه: "هذا التطبيق غير متاح مؤقتًا" (بلا تفاصيل تقنية داخلية) — **يبقى ظاهرًا للمشتركين الحاليين فقط**، يختفي من الكتالوج العام تمامًا | لا إجراء — عرض فقط | 🔒 Future، لا عنصر معلَّق اليوم |
| **Deprecated** | "سيتوقف قريبًا" | "فتح" (يبقى يعمل لحد تاريخ الإيقاف) | إشعار مسبق بتاريخ التوقف + بديل مقترح لو وُجد | فتح، مراجعة بدائل | 🔒 Future |

**قاعدة الرسالة (Messaging):** كل حالة غير "Available/Active" تحمل جملة تفسير واحدة بلغة بشرية (لا رمز/لون فقط) — امتداد مباشر لمبدأ الصدق البصري.

## N. Integration Lifecycle UX

```
Not Connected → Connecting → Connected → Syncing → Sync Warning / Connection Error → Disconnected
```

| الحالة | الحقيقة اليوم | ملاحظة تصميم |
|---|---|---|
| Not Connected | 🔒 نقطة الانطلاق الافتراضية للنمط (لا Integration حقيقي أصلًا) | الحالة الوحيدة المعروضة فعليًا بـD اليوم |
| Connecting | 🚫 Future (لحظية) | مؤشر تحميل مضمَّن بزر "ربط" نفسه، لا شاشة منفصلة |
| Connected | 🚫 Future | Badge أخضر + "آخر مزامنة: [وقت]" حقيقي حينها |
| Syncing | 🚫 Future | مؤشر نشاط صغير بجانب Badge "متصل"، لا يحجب باقي الشاشة |
| Sync Warning | 🚫 Future | لون `state-pending`، رسالة محددة (مثال فئوي: "بعض البيانات لم تُزامَن") |
| Connection Error | 🚫 Future | لون `state-attention`، CTA "إعادة المحاولة" + "قطع الاتصال" معًا |
| Disconnected (بفعل المستخدم) | 🚫 Future | يعود لحالة Not Connected، مع سجل "آخر اتصال كان بتاريخ X" لو مفيد |

**كل حالة أبعد من "Not Connected" تبقى توثيقًا للنمط فقط بهذي المرحلة** — لا اختبار بصري حقيقي ممكن بلا أول تكامل فعلي.

---

## O. Service Lifecycle UX

```
Discover → View → Request → Submitted → In Progress → Completed / Cancelled
```

**Framework مرن، لا افتراض توحّد:** الخطوات "Submitted → In Progress → Completed" تُعرَض كـStepper بسيط (نقاط متصلة بخط) — لكن **النص داخل كل خطوة يتغيّر حسب `delivery_type` المستقبلي** (آلي: خطوات فورية شبه لحظية / بشري: خطوات بجداول زمنية وتواصل). لا تصميم مُلزَم لكل فئة الآن — فقط الهيكل العام (Stepper) والقاعدة (نص متغيّر لا ثابت). **Cancelled** حالة نهائية بديلة عن Completed، تظهر بلون محايد لا `state-attention` (إلغاء ليس بالضرورة خطأ).

كل هذا 🚫 Future بالكامل — لا Service حقيقي واحد.

## P. Search

امتداد لقسم ١٤ بالـDesign System، بتصور مباشر للتوسّع:

- **عند 50-100 عنصر:** البحث النصي + الفلاتر الحالية كافية، مع إضافة تجميع نتائج بصري بسيط حسب `type` لو تنوّع (عناوين فرعية داخل نتائج البحث: "تطبيقات (٣)"، "تكاملات (١)" — لا صفحات نتائج منفصلة).
- **عند 500+ عنصر (بعيد المدى، لا تصميم تفصيلي، فقط اتجاه):** حاجة فعلية لبحث دلالي (AI-powered discovery، مذكور مسبقًا كتصوّر مستقبلي بحت بقسم N بوثيقة الـUX) — **لا تصميم واجهة له الآن**، فقط تأكيد إن بنية البحث النصي الحالية (حقل واحد + فلاتر) لا تُستبدَل ببنية موازية لاحقًا، بل الطبقة الذكية تُضاف *خلف* نفس حقل البحث الموجود، لا حقل بحث "ذكي" منفصل بصريًا.
- **اقتراحات بحث تلقائية (Autocomplete):** 🔒 نمط محجوز، لا يُبنى قبل وجود كتالوج كبير كفاية ليكون مفيدًا فعليًا (بـ٨ عناصر لا قيمة له).

## Q. Filters

امتداد لقسم ١٥ بالـDesign System:

- **عدّاد نتائج بكل Pill** (مثال: "مجاني (٥)") — 🔒 يُفعَّل لحظة وجود كتالوج أكبر يبرر الحاجة لمعرفة الحجم قبل النقر (بـ٨ عناصر العدّاد بديهي بصريًا بالفعل).
- **شريط "الفلاتر النشطة" القابل للمسح** (مذكور بقسم B أعلاه) — يظهر بمجرد تفعيل أكثر من فلتر بنفس الوقت، بصرف النظر عن حجم الكتالوج.
- **منطق AND إلزامي** بين فلاتر من أبعاد مختلفة (نوع + سعر معًا، مثلًا) — لا فلترة OR مربكة بلا توضيح.

## R. Recommendations

امتداد مباشر لقسم ٢٠ بالـDesign System — **لا قاعدة جديدة تُضاف هنا** بلا بيانات حقيقية وراءها. القواعد الثلاث المعتمدة (دور المستخدم / تكامل مع عنصر مملوك بنفس التصنيف / اهتمام مسجَّل) تبقى الحد الأقصى المسموح به اليوم. أي قاعدة رابعة (Co-subscription patterns "مؤسسات مثل مؤسستك تستخدم أيضًا") **تنتظر وجود بيانات استخدام جماعية حقيقية** — لا تُصمَّم حتى كنمط مسبق الآن لأنها أقرب لـCollaborative Filtering الممنوع صراحة.

---

## S. Related Items — بلا Ecosystem وهمي

بديل عن الرسم التوضيحي الكامل بصفحات التفاصيل — ثلاثة أنماط عرض محتملة، **تظهر فقط لو علاقة حقيقية موجودة فعليًا**:

| النمط | يظهر متى |
|---|---|
| **"يعمل مع" (Works With)** | فقط لعنصر Integration حقيقي مرتبط فعليًا بعنصر Application حقيقي (علاقة بيانات صريحة، لا تخمين) — 🔒 Future |
| **"مقترح معه" (Recommended With)** | نفس منطق قسم R (قاعدة Rules-based موجودة) — لا شيء جديد |
| **"مفيد معًا" (Useful Together)** | عنصران بنفس `category` الحقيقي — 🔒 حتى وجود تصنيفات حقيقية (Phase 1) |

**القاعدة الحاسمة (لا Ecosystem وهمي):** صفحة تفاصيل بوابة معرفة **اليوم لا تعرض قسم "عناصر ذات صلة" إطلاقًا** — ليس Empty State، **غياب تام** — لأنه لا يوجد عنصر ثانٍ حقيقي يصلح للعلاقة أصلًا (كتالوج من عنصر حقيقي واحد لا "علاقات" ممكنة منطقيًا). القسم يظهر أول مرة لحظة وجود علاقة حقيقية واحدة قابلة للإثبات — لا قبل.

## T. Notifications

امتداد لقسم ٣١ بالـDesign System — لا خدمة Notifications خلفية حقيقية اليوم:
- **Toast عابر:** النمط الوحيد المتاح فعليًا اليوم (تأكيد إرسال "أنا مهتم"، تأكيد تفعيل تطبيق مجاني) — موجود مفهوميًا بالفعل.
- **مركز إشعارات دائم (أيقونة جرس):** 🚫 **لا يظهر إطلاقًا بالهيدر** حتى وجود الخدمة الخلفية فعليًا — لا أيقونة "معطَّلة" أو بعدّاد صفري توحي بوجودها.

## U. Confirmation

توحيد لكل لحظات التأكيد عبر الوثيقة (تفعيل تطبيق مجاني [حقيقي]، منح/سحب وصول [Future]، تعيين/إزالة مقعد [Future]، إلغاء اشتراك [Future]، قطع اتصال تكامل [Future]):

**قاعدة موحّدة واحدة:** أي فعل **قابل للتراجع فورًا** (منح وصول، تعيين مقعد) = Toast بلا تأكيد مسبق (الفعل نفسه بسيط، التراجع سهل). أي فعل **له عواقب** (قطع اتصال، إلغاء اشتراك، سحب وصول من عضو نشط) = Modal تأكيد إلزامي بزرين واضحين (قسم ٣٠ بالـDesign System) — لا استثناء.

## V. Error States

| السياق | الرسالة/السلوك |
|---|---|
| فشل شبكة عام | رسالة عربية + "إعادة محاولة"، أي مكان بالنظام |

## Y. Mobile UX — إعادة تفكير، لا تصغير

| العنصر | إعادة التفكير (لا مجرد تصغير Desktop) |
|---|---|
| **التنقّل** | My Workspace (My Apps/Integrations/Services/Subscriptions) يتجمّع بقائمة واحدة مبسَّطة بدل أربع تبويبات أفقية متزاحمة — الأولوية لـ"أستخدمه الآن" ظاهرة أولًا دومًا |
| **البطاقات** | Metadata ثانوية (Tagline الطويل، وصف كامل) تختفي من البطاقة المصغَّرة على الموبايل — الاسم + الأيقونة + Badge الحالة فقط، الباقي بصفحة التفاصيل |
| **الفلاتر** | Bottom Sheet (مؤكَّد سابقًا) |
| **الجداول الإدارية (K/L/J)** | **لا Scroll أفقي إطلاقًا** — كل صف يتحول لبطاقة قابلة للتوسّع (Tap للتفاصيل والإجراءات)، لا جدول مضغوط بخط صغير |
| **الإجراءات (CTA رئيسي بصفحة تفاصيل)** | شريط سفلي ثابت (Sticky Bottom Bar) يحمل الـCTA الأساسي دومًا ظاهرًا أثناء التمرير — نمط Enterprise Mobile قياسي، لا انتظار وصول المستخدم لأسفل الصفحة |
| **السياق (عضويتي/المؤسسة الحالية)** | شريحة (Chip) صغيرة ثابتة أعلى الشاشة، تفتح تفاصيل للقراءة فقط (لا تبديل فعلي، التبديل خارج النطاق) |
| **النوافذ (Modals)** | تأكيدات العواقب (قسم U) = Bottom Sheet كامل الارتفاع تقريبًا، لا نافذة مركزية صغيرة يصعب لمسها بدقة على شاشة صغيرة |

## Z. Accessibility

قائمة تحقق موحَّدة (تجميع لكل ما سبق بوثائق الـUX والـDesign System + إضافات خاصة بالشاشات الإدارية الجديدة):

- لا حالة تعتمد على اللون وحده — مؤكَّد بكل جدول Badge/CTA أعلاه.
- كل جدول إداري (K/L) يستخدم عناصر `<table>` دلالية حقيقية (رؤوس أعمدة `<th>` مرتبطة)، لا `<div>` مصفوفة بصريًا فقط — أساسي لقارئ شاشة يدير مؤسسة.
- أي فعل جماعي (Bulk action، لو أُضيف لاحقًا لـK/L) يُعلَن نتيجته لقارئ الشاشة فور تنفيذه (`aria-live`).
- Focus Trap صحيح داخل أي Modal تأكيد (قسم U) + إعادة التركيز للعنصر الذي فتحه عند الإغلاق.
- تباين الألوان (خصوصًا `state-attention`/`maroon` المُفعَّل أول مرة فعليًا بقسم M/V هنا) يحتاج قياس WCAG AA فعلي وقت التنفيذ — مُسجَّل كبند تحقق، لا قرار نهائي.
- RTL: ترتيب أزرار Modal التأكيد (قسم U) يتبع اتجاه القراءة العربي (مؤكَّد مسبقًا بقسم ٣٥ بالـDesign System) — يُطبَّق بلا استثناء على كل تأكيد جديد هنا.

| `OrgMemberList` | J | جديد |
| `ActiveFiltersBar` (Chips قابلة للمسح) | B | جديد |
| `StickyMobileActionBar` | C, D, E (موبايل فقط) | جديد |
| بقية المكوّنات (`ItemCard`, `Badge`, `Button`, إلخ) | كل الشاشات | مرجعها Pilot/Design System، لا تغيير |

**كل مكوّن "جديد" هنا يُضاف رسميًا لـ`marketplace-ui-design-system.md` عند اعتماد هذي الوثيقة**، بنفس Tokens والقواعد الموجودة، لا نظام موازٍ.

## 4. State Map

مرجع موحَّد واحد يجمع كل أبعاد الحالة المذكورة بالمعمارية التقنية وتأثيرها البصري — لا تفصيل جديد، فقط دمج الجداول السابقة (M/N/O) بجدول واحد للرجوع السريع:

| البُعد | القيم الممكنة | أين يؤثر |
|---|---|---|
| `type` | application / integration / service | شكل البطاقة (١٧-١٩)، تفاصيل (C/D/E)، My Workspace grouping |
| `status` (Lifecycle) | draft/submitted/under_review/approved/published/updated/suspended/deprecated | Badge + Messaging (قسم M بالكامل لـApplication، نظائرها N/O) |
| Access State | لديك وصول / ليس لديك وصول (بانتظار) | Badge + CTA (قسم ٢٢-٢٣ بالـDesign System) |
| Subscription | اشتراكك / اشتراك المؤسسة / لا يوجد | I، My Apps grouping |
| Seat | مُخصَّص / غير مُخصَّص / لا ينطبق (فردي) | L، تأثير غير مباشر على Access State |
| Organization Context | عرض فقط اليوم (لا تبديل فعلي) | J، شريحة الهيدر (خارج النطاق التنفيذي) |
| Role/Compatibility | lawyer/firm/finance/student/client | R (توصيات)، إخفاء/إظهار حسب Q (Permission UX) |
| Billing Model | user_only/organization_only/both | يحدد أي مسار CTA بقسم M (اشتراك فردي مقابل "طلب من المدير") |

## 5. Cross-Screen Consistency Rules

قواعد إلزامية تمنع تناقضًا بصريًا بين شاشتين تعرضان نفس البيانات:

1. **حالة العنصر (Badge) مصدرها واحد دائمًا** — Catalog وHome وMy Apps وصفحة التفاصيل تعرض نفس Badge لنفس العنصر بنفس اللحظة، لا نسخة "مخبَّأة" بشاشة تتأخر عن تحديث بشاشة أخرى (قرار تصميم يُترجَم تقنيًا لاحقًا كاستعلام حي، لا Cache منفصل لكل شاشة).
2. **نص CTA لنفس الحالة المنطقية ثابت حرفيًا** بكل مكان يظهر فيه — "طلب الوصول" لا تتحول لـ"اطلب الوصول"/"طلب صلاحية" بشاشة أخرى (المفردات مصدرها الوحيد جدول قسم ٠).
3. **لا مرادف ثانٍ لنفس المفهوم بأي شاشة جديدة** — أي شاشة بهذي الوثيقة تلتزم حرفيًا بجدول الترجمة (قسم ٠)، ولا تخترع تسمية بديلة ولو بدت أوضح لسياقها الخاص.
4. **لون الحالة الدلالي (`state-*`) لا يتغيّر معناه بين شاشة وأخرى** — `state-pending` يعني "بانتظار فعل" بكل مكان (Badge تطبيق، حالة تكامل، حالة طلب خدمة)، لا معنى مختلف حسب الشاشة.
5. **قواعد الصلاحية (Q) موحَّدة**: عنصر مخفي عن مستخدم بشاشة My Apps يبقى مخفيًا عنه بأي شاشة أخرى (بحث، توصيات) — لا تسرّب ظهور جزئي عبر مسار مختلف.

## 6. Future-State Rules

القاعدة الحاكمة لكل حالة/شاشة مُعلَّمة 🔒/🚫 بهذي الوثيقة كاملة — تُطبَّق حرفيًا بلا استثناء واحد:

1. **علامة "معاينة مستقبلية" ظاهرة دائمًا، غير قابلة للإخفاء أو التجاهل** — أول عنصر يُقرأ/يُرى بأي شاشة Future بالكامل (مطابق لقسم D بـPilot).
2. **أي فعل غير حقيقي = زر معطَّل بتفسير نصي مرافق**، لا زر يعمل بسلوك وهمي، ولا زر يختفي بصمت (الاختفاء الصامت يوحي بخطأ، لا بغياب مقصود — التعطيل الموسوم أصدق).
3. **لا بيانات مُختلَقة تحت أي مسمى** — لا "مثال توضيحي"، لا "بيانات تجريبية"، لا اسم شركة/سعر/تاريخ وهمي بأي سياق مهما كانت النية تعليمية.
4. **إعادة استخدام مكوّنات حقيقية دائمًا** — كل نمط Future (D/E/G/H/J/K/L) مبني من نفس مكوّنات الحالة الحقيقية (Badge/Button/Card بنفس Tokens)، لا نظام تصميم موازٍ "للمستقبل" يحتاج إعادة بناء لاحقًا.
5. **الانتقال من 🔒 إلى ✅ إضافي لا هدمي** — لحظة توفر بيانات حقيقية (أول Integration، أول اشتراك مؤسسي)، الشاشة/الحالة تُفعَّل بتبديل مصدر البيانات فقط، لا إعادة تصميم. هذا الاختبار النهائي لصحة كل قرار بهذي الوثيقة: **لو تفعيل حالة Future يومًا ما يتطلب "تصميمًا من جديد"، فالتصميم الحالي لها كان خاطئًا من الأساس.**
