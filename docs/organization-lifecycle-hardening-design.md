# Organization Lifecycle Hardening — Design (Active / Archived / Hard Delete)

**الحالة:** تصميم نهائي (Design + Decision Matrix + Security Matrix + Lifecycle Matrix + Test Strategy). **صفر كود، صفر Migration، صفر تعديل Filament/Policies/Header/Dashboard/Marketplace/L2/L3/L4/2C.** كل حقيقة هنا مصدرها الكود الفعلي + تجارب تحكُّمية سابقة موثَّقة (لا تجارب جديدة بهذي الجولة — الأدلة اللازمة موجودة مسبقًا).
**النطاق:** Core Organization Domain — دورة حياة كيان Organization نفسه. **لا Marketplace UI، لا Header، لا Dashboard، لا Navigation، لا بوابة معرفة.**
**المرجع:** `owner-integrity-hardening-design.md` (القرارات النهائية المعتمَدة هناك تُبنى عليها هذي الوثيقة مباشرة) · `audit-log-integrity-hardening.md`/`audit-log-integrity-incident-report.md`.

## الاتجاه المعماري المعتمَد (المستخدم، نهائي — يحكم كل قرار بهذي الوثيقة)

1. لا يُتجاوَز أو يُعطَّل حماية `AuditLog` لأي عملية حذف، بأي حال.
2. لا مسار "Disable Trigger → Delete → Re-enable" — ممنوع نهائيًا، بلا استثناء.
3. `AuditLog` تاريخ غير قابل للتعديل، ويبقى كذلك دائمًا.
4. Hard Delete **ليس** المسار التشغيلي الطبيعي لمؤسسة.
5. Archive/Deactivate هو المسار الطبيعي لأي مؤسسة لها تاريخ أو بيانات مرتبطة.
6. لو بقي Hard Delete كعملية Domain مستقبلية، يجب تكون **مقيَّدة جدًا، ذرية، مبنية على سياسة واضحة — لا Filament CRUD مباشر.**
7. لا إصلاح تلقائي لتضارب `owner_id` الحالي، لا تخمين نية.

## ⚠️ الاكتشاف الحرج المؤسِّس (من الجولة السابقة، يبقى الأساس التقني لكل قرار هنا)

**Hard Delete لمؤسسة لها ولو سجل `audit_logs` واحد يفشل فعليًا اليوم — ليس اختيارًا معماريًا، بل عطل تقني مؤكَّد تجريبيًا:**
```
DELETE organizations WHERE id=X
        ↓
audit_logs.organization_id مقيَّد بـ nullOnDelete() (Migration من Phase 1)
        ↓
محرك القاعدة يُنفِّذ ضمنيًا: UPDATE audit_logs SET organization_id=NULL WHERE organization_id=X
        ↓
AD-001 Trigger يرفض *أي* UPDATE على audit_logs بلا استثناء — بما فيها هذا الضمني
        ↓
DELETE organizations بأكمله يفشل: QueryException خام
```
**هذا الاكتشاف، مع الاتجاه المعماري أعلاه (بند 1-3، ممنوع تجاوز الحماية)، يعني عمليًا:** Hard Delete لأي مؤسسة لها تاريخ Audit **مستحيل تقنيًا بالبنية الحالية، وممنوع سياسيًا حتى لو أمكن تجاوزه تقنيًا.** الاتجاهان (التقني والسياسي) يتقاطعان على نفس النتيجة — Archive هو المسار الوحيد.

## B. Lifecycle Matrix — الحالات النهائية

### الحالات المعتمَدة: **`Active`** و **`Archived`** فقط — لا حالة `Deactivated` منفصلة

**القرار (مُصمَّم نهائيًا، بند 3 بطلبك):** ❌ **لا نحتاج `Deactivated` كحالة ثالثة منفصلة.** السبب: لا يوجد اليوم أي سلوك عملي مختلف حقيقي بين "معطَّلة مؤقتًا" و"مؤرشَفة" — كلاهما ينتج نفس الأثر بالضبط (تجميد الاشتراكات، سحب الوصول، تجميد إدارة الأعضاء). التمييز بين الاثنين له معنى فقط بوجود سبب تشغيلي حقيقي يستدعي تفرقة (مثال كلاسيكي: "معطَّلة بسبب فشل دفع، ستُستأنف تلقائيًا" — **لا يوجد Billing Engine اليوم**، فلا يوجد هذا السبب أصلًا). **مطابق تمامًا لمبدأ المشروع الثابت:** Future-ready ≠ Future-built — لا نبني حالة ثانية بلا سلوك مميَّز فعلي يبرّرها. لو ظهر مستقبلًا سبب حقيقي (Billing حقيقي مثلًا)، إضافة حالة ثالثة لاحقًا فعل بسيط (لا يكسر التصميم الحالي، `Active`/`Archived` يبقيان كما هما).

**ملاحظة بنيوية مهمة:** `Organization` **لا يملك عمود حالة إطلاقًا اليوم** (لا `status`، لا `archived_at`) — أي تنفيذ لهذا التصميم يتطلب عمودًا جديدًا (تفصيل تنفيذي، Migration لاحقة لو اعتُمد، لا الآن).

### الجدول الشامل — الأسئلة الخمسة عشر

| # | السؤال | الإجابة المُصمَّمة نهائيًا |
|---|---|---|
| 1 | Active | الحالة الافتراضية لكل مؤسسة (تطابق كل البيانات الحالية اليوم — كلها "Active" ضمنيًا بغياب أي عمود حالة) |
| 2 | Archived/Inactive | حالة واحدة، اسمها `Archived` — لا "Inactive" كاسم مستقل (تجنّبًا لازدواج تسمية لنفس المفهوم) |
| 3 | Deactivated منفصلة؟ | ❌ لا، راجع أعلاه |
| 4 | مصير Memberships | **تبقى موجودة بلا حذف.** الأرشفة ليست حذفًا — Membership تبقى السجل التاريخي الصحيح لـ"من كان عضوًا بهذي المؤسسة"، بلا أي أثر عملي فعّال طالما المؤسسة مؤرشَفة (لا Seat جديد يُمنَح، لا صلاحية إدارية تُمارَس عمليًا لأن لا اشتراك نشط يُدار أصلًا) |
| 5 | مصير Subscriptions | **تُلغى صراحة** عبر `OrganizationSubscriptionService::cancel()` الموجود والمُختبَر فعليًا — لكل اشتراك نشط، كجزء من نفس عملية الأرشفة الذرية |
| 6 | مصير Seats | تُحرَّر تلقائيًا كأثر جانبي مباشر لـ`cancel()` (السلوك الموجود فعليًا، مُختبَر) |
| 7 | مصير AccessAssignments | تُبطَل تلقائيًا كأثر جانبي مباشر لـ`cancel()` (نفس أعلاه) |
| 8 | مصير AuditLogs | **لا يتأثر إطلاقًا — هذي بالضبط الميزة الجوهرية لـArchive مقابل Delete.** `organization_id` يبقى صحيحًا للأبد (صف Organization نفسه لم يُحذَف) — تتبّع كامل بلا فقدان، بلا أي صراع مع AD-001 Trigger (لا محاولة UPDATE/DELETE على audit_logs بأي حال بعملية الأرشفة نفسها) |
| 9 | محاولات الوصول بعد Archive | **آمنة تلقائيًا بلا كود إضافي** — بما إن كل Subscription مؤسسي أصبح `cancelled` (خطوة 5)، `EntitlementResolver` (مصدر الحقيقة الوحيد، AD-013) يرفض الوصول بنفس المسار المُختبَر أصلًا لأي اشتراك ملغى — **لا حاجة لفحص "هل المؤسسة مؤرشَفة؟" بمكان منفصل، إعادة استخدام المنطق الموجود بدل بناء فحص مواز (تجنّبًا لتكرار AD-013 حذّر منه Access Control Audit سابقًا)** |
| 10 | إعادة إحياء (Restore) ممكنة؟ | ✅ **نعم — Archive لا يُتلِف أي بيانات (Membership باقية، Subscription ملغى لا محذوف).** لكن **Restore لا يُعيد تفعيل أي Subscription ملغى تلقائيًا** (نفس روح AD-014 حرفيًا، مُطبَّقة هنا بسياق جديد: "أُرشِفت" ≠ "لم تكن نشطة أبدًا"، لكن أيضًا لا إعادة تفعيل ضمنية بلا نية صريحة) — Restore يعيد المؤسسة لحالة `Active` فقط، أي اشتراك يحتاج Owner يعيد تفعيله صراحة بعدها (فعل واعٍ منفصل، ليس جزءًا من Restore نفسه) |
| 11 | من يملك صلاحية Archive/Restore | **مُصمَّم: Owner فقط** — يطابق BR-2B-01 (إنشاء الاشتراك المؤسسي فعل بمسؤولية تعاقدية، Owner حصرًا لا Admin) بنفس المنطق: أرشفة/إحياء مؤسسة قرار بنفس مستوى الجسامة، لا فعل تشغيلي يومي يناسب Admin |
| 12 | Subscription نشطة وقت Archive | **لا تمنع العملية** — تُلغى كجزء منها (بعكس Last Owner Rule اللي *ترفض* الفعل، هنا الفعل يُقبَل ويُسوّي الحالة تلقائيًا) |
| 13 | Seats نشطة وقت Archive | نفس أعلاه — تُحرَّر تلقائيًا، لا ترفض العملية |
| 14 | ضمان عدم وجود Orphan Subscription | **الترتيب الذري نفسه (قسم C أدناه) يضمن هذا بنيويًا** — لا Subscription يبقى `active` بعد Archive بحكم التصميم (كل واحد يُلغى صراحة **قبل** تغيير حالة المؤسسة نفسها، بمعاملة واحدة) + اختبار Data Integrity مستقل (قسم F) للتحقق الدوري |
| 15 | مؤسسة لها Audit History | **هذا بالضبط الحالة العادية المتوقَّعة، لا استثناء يحتاج معالجة خاصة** — الأرشفة لا تلمس `audit_logs` إطلاقًا (بعكس Delete)، فلا يوجد أي تعارض مع AD-001 من الأساس |

## C. Archive كعملية Domain واحدة (تصميم، لا تنفيذ)

```
ArchiveOrganization(actor, organization):
  authorize: actor له Membership.role=Owner بهذي المؤسسة تحديدًا (بند 11)
  BEGIN TRANSACTION
    1. لكل Subscription نشط (subscriber_type=organization, subscriber_id=organization.id):
         OrganizationSubscriptionService::cancel(actor, subscription)
         (يُلغي + يُحرِّر كل Seat + يُبطِل كل AccessAssignment + يسجّل Audit — الموجود فعليًا، بلا تعديل)
    2. organization.status = 'archived' (أو archived_at = now(), حسب القرار التنفيذي المفتوح رقم 1 أدناه)
  COMMIT (فشل أي خطوة → Rollback كامل، لا حالة وسيطة)

RestoreOrganization(actor, organization):
  authorize: actor له Membership.role=Owner بهذي المؤسسة (حتى وهي مؤرشَفة — العضوية باقية، قسم B بند 4)
  organization.status = 'active'
  (لا فعل آخر — لا إعادة تفعيل اشتراكات، بند 10 أعلاه)
```

**لا خطوة تلمس `Membership` أو `AuditLog` بأي عملية من الاثنتين — بعكس تصميم Delete السابق (الذي كان يحذف Membership صراحة)، الأرشفة أبسط وأكثر أمانًا لأنها لا تحذف شيئًا إطلاقًا.**

## Decision Matrix — ملخَّص Delete مقابل Archive

| البُعد | Hard Delete | Archive (المُعتمَد) |
|---|---|---|
| يعمل تقنيًا لمؤسسة لها Audit History؟ | ❌ مستحيل (الاكتشاف الحرج) | ✅ دائمًا |
| يتوافق مع الاتجاه المعماري (بند 1-6)؟ | ❌ يتطلب إما تجاوز الحماية (ممنوع) أو تقييدًا شديدًا | ✅ بلا أي تعارض |
| يحافظ على Audit Trail الكامل؟ | ⚠️ فقط لو نجح أصلًا (نادر) — `organization_id` يُفقَد حتى لو نجح | ✅ دائمًا، `organization_id` صحيح للأبد |
| قابل للتراجع (Restore)؟ | ❌ نهائي بطبيعته | ✅ دائمًا |
| يحتاج Migration Schema جديد؟ | ❌ لا (يستخدم البنية الحالية) | ✅ نعم (عمود حالة جديد) |
| هل هو المسار الطبيعي؟ | ❌ لا (بند 4 من الاتجاه المعتمَد) | ✅ نعم (بند 5) |

## D. Hard Delete — هل نحتاجه أصلًا؟

**التوصية النهائية: ❌ لا حاجة معمارية حقيقية لـHard Delete كعملية Domain — Archive وحدها كافية لكل الحالات الواقعية، بما فيها "مؤسسة أُنشئت بالخطأ بلا أي نشاط".**

**التبرير:** مؤسسة أُنشئت بالخطأ، صفر عضوية حقيقية، صفر نشاط — أرشفتها **بلا أي ضرر أو تكلفة** (لا Audit History تُفقَد لأنه لا يوجد أصلًا، لا Subscription تُلغى لأنه لا يوجد). الفارق العملي الوحيد بين "أرشفة مؤسسة فارغة" و"حذفها" هو **مجرد بقاء صف واحد إضافي بجدول `organizations`** — تكلفة ضئيلة جدًا، مقابل تعقيد حقيقي (Domain Operation ثانية، سياسة شروط منفصلة، مسار اختبار منفصل) لفائدة شبه معدومة. **هذا يطابق حرفيًا مبدأ Future-ready ≠ Future-built مرة أخرى: لا نبني آلية Hard Delete منفصلة لحل مشكلة "نظافة قائمة إدارية" لا تستحق التعقيد.**

**بالإجابة المباشرة على أسئلتك الفرعية (لو اعتُمد لاحقًا خلافًا للتوصية أعلاه):**

| السؤال | الجواب |
|---|---|
| متى يكون مسموحًا؟ | فقط لمؤسسة بصفر `audit_logs` مرتبطة بها إطلاقًا |
| فقط لمؤسسة لم تبدأ أي نشاط؟ | نعم — عمليًا "صفر Audit History" و"صفر نشاط" مترادفان (أي نشاط حقيقي يُنشئ Audit تلقائيًا) |
| وجود AuditLog يمنعه؟ | **نعم، مانع مطلَق، بلا استثناء** — ليس سياسة فقط، بل مُنفَذ تلقائيًا بالفعل عبر AD-001 Trigger (الاكتشاف الحرج) |
| وجود Subscription/Seat/Access يمنعه؟ | **نعم، يجب يمنعه كسياسة صريحة بالـService حتى لو لم يمنعه AuditLog وحده** (نظريًا Subscription بلا أي Audit مرتبط به مستحيل عمليًا بما إن `create()`/`cancel()` كلاهما يسجّلان Audit فورًا — لكن الفحص الصريح خط دفاع مستقل، لا اعتماد فقط على الأثر الجانبي لقيد آخر) |
| شروطه الذرية؟ | فحص (صفر Audit + صفر Subscription + صفر Membership غير المُنشئ نفسه) **قبل** أي فعل، بمعاملة واحدة — رفض فوري وواضح لو أي شرط فشل، لا محاولة فعلية تصل لقاعدة البيانات لتفشل هناك (بعكس اليوم) |
| كيف نضمن عدم تعديل Audit Logs؟ | **بعدم المحاولة أصلًا** — الفحص المسبق (أعلاه) يمنع الوصول لنقطة التعارض مع الـTrigger من الأساس، لا اعتماد على الـTrigger كخط الدفاع الوحيد (هو موجود كضمانة نهائية، لا كآلية تحقق أساسية) |
| غير متاح من Filament أصلًا؟ | **✅ نعم، موصى به بقوة** — إزالة `DeleteAction`/`DeleteBulkAction` القياسيين لـ`OrganizationResource` بالكامل، سواء اعتُمد Hard Delete الضيّق لاحقًا (يصبح حينها Action مخصَّص بشروطه الصريحة، لا Filament القياسي) أو أُلغي المفهوم كليًا (التوصية) |

## F. Security Matrix — السيناريوهات التسعة

| # | السيناريو | التصميم المعتمَد |
|---|---|---|
| 1 | آخر Owner يحاول حذف نفسه | يخص `Membership`, لا `Organization` نفسها — محكوم بـLast Owner Rule (`owner-integrity-hardening-design.md`)، لا علاقة مباشرة بالأرشفة |
| 2 | Owner ينزل إلى Admin بدون بديل | نفس أعلاه — Last Owner Rule |
| 3 | Owner ينقل الملكية لجديد | `TransferOwnership` الذرية (نفس الوثيقة الأخرى) — Membership تبقى بغض النظر عن حالة Organization (Active/Archived) |
| 4 | Admin يحاول تغيير Ownership | ممنوع (Authorization Matrix، Owner فقط) |
| 5 | حذف مؤسسة لديها Subscription | **لا ينطبق بعد التوصية (لا Hard Delete)** — Archive تُلغي الاشتراك صراحة كجزء من نفسها، لا رفض ولا يتم بمعزل |
| 6 | حذف مؤسسة لديها Seats/Access | نفس أعلاه |
| 7 | حذف مؤسسة لديها Audit Logs | **بعد التوصية: غير قابل للحدوث أصلًا** — Archive لا تلمس Audit Logs، Hard Delete (لو طُلب رغم التوصية) يُرفَض بالفحص المسبق (قسم D) |
| 8 | الوصول لبيانات مؤسسة بعد Archive | ✅ مؤمَّن تلقائيًا عبر `EntitlementResolver` (بند 9 بالجدول أعلاه) — لا مسار وصول فعّال يبقى بعد إلغاء كل الاشتراكات |
| 9 | التزامن في Transfer Ownership | مُصمَّم بالكامل بالوثيقة الأخرى (معاملة ذرية) — لا علاقة مباشرة بـArchive نفسها (Archive عملية فردية لا سباق تزامني متوقَّع عليها بنفس الطريقة) |

## G. Testing Strategy

| الفئة | الاختبارات |
|---|---|
| **Unit** | `ArchiveOrganization` تُلغي كل Subscription نشط + تُحرِّر كل Seat + تُبطِل كل Access — بمعاملة واحدة، فشل جزئي = Rollback كامل |
| **Feature** | `RestoreOrganization` تعيد الحالة `Active` بلا إعادة تفعيل أي اشتراك ملغى (اختبار صريح يثبت البقاء `cancelled`) |
| **Security** | Owner فقط يقدر يؤرشف/يُحيي (403 لغيره) — الأربعة الأولى بقسم F محالة للوثيقة الأخرى بلا تكرار هنا |
| **Access** | مستخدم بمقعد فعّال بمؤسسة، تُؤرشَف المؤسسة، `EntitlementResolver` يرفض الوصول فورًا للطلب التالي (لا حاجة انتظار/تحديث جلسة) |
| **Regression** | كامل 141 اختبار حالي + `OrganizationSubscriptionServiceTest`/`SeatServiceTest` تحديدًا (الأرشفة تستهلكهما مباشرة) |
| **Data Integrity** | لا `Subscription(subscriber_type=organization, status=active)` يشير لمؤسسة `Archived` — أداة تحقق دورية (نفس فلسفة L2) |
| **Hard Delete (لو اعتُمد رغم التوصية)** | محاولة حذف مؤسسة بأي Audit History **يجب تُرفَض برسالة واضحة قبل وصول أي استعلام لقاعدة البيانات** — لا `QueryException` خام يصل لأي مستخدم بأي حال |

## D) تحليل الأثر الصناعي بقاعدة التطوير (Synthetic Dev Artifact)

**الصفوف الثلاثة قيد التحليل:**
```
organizations.id=5   ("Cascade Test Org")
users.id=16           (akram41@example.org)
audit_logs.id=36      (event=seat_assigned, subject_type=X, subject_id=1, organization_id=5, actor_user_id=16)
```

**هل توجد طريقة تنظيف آمنة لا تُعطِّل أو تتجاوز AD-001؟**

**فُحِصت كل المسارات المحتملة نظريًا، بلا تجربة جديدة على القاعدة الحية (تجنّبًا لأي أثر إضافي):**

| المسار المحتمَل | آمن؟ | السبب |
|---|---|---|
| حذف `audit_logs.id=36` مباشرة | ❌ | هذا بالضبط ما يمنعه AD-001 Trigger بالتصميم — أي محاولة تعني انتهاك الحماية نفسها |
| حذف `organizations.id=5` (يُشغِّل Cascade على `audit_logs.organization_id`) | ❌ | نفس السبب — Cascade يُنفِّذ UPDATE يرفضه الـTrigger (الاكتشاف الحرج نفسه) |
| تعطيل الـTrigger مؤقتًا، حذف، إعادة تفعيله | ❌ | **ممنوع صراحة بالاتجاه المعماري المعتمَد (بند 1-2)** — لا نقاش بهذا المسار إطلاقًا |
| `PRAGMA foreign_keys=OFF` ثم حذف (تجاوز إنفاذ الـFK بدل الـTrigger) | ❌ | **من نفس فئة "تجاوز الحماية" المحظورة** — يحلّ المشكلة التقنية لكنه يخالف بند 1-2 بالمبدأ، وينتج أثرًا أسوأ (audit_logs.organization_id يبقى يشير لمؤسسة محذوفة بلا حتى استفادة الـnullOnDelete — Orphan فعلي حقيقي) |
| حذف/استبدال ملف `database.sqlite` بالكامل | ❌ | يحذف كل البيانات الأخرى (المؤسسات الثلاث الحقيقية، المستخدمون الثمانية، كل تاريخ الاختبارات) — أثر أفدح بكثير من ثلاثة صفوف صناعية |
| **إعادة تسمية `organizations.name`/`users.name` فقط (بلا حذف، بلا لمس `audit_logs` إطلاقًا) لتوضيح إنها بيانات اختبارية بشكل لا لبس فيه** | ✅ **آمن فعليًا** | لا يلمس `audit_logs` بأي شكل (لا UPDATE، لا DELETE) — `organizations`/`users` جداول عادية بلا أي حماية مماثلة، تعديل اسمي بحت لغرض التوضيح الإداري فقط |

**الخلاصة: لا توجد طريقة آمنة لإزالة الصفوف الثلاثة فعليًا اليوم — يجب تبقى دائمًا، هذا نتيجة مباشرة ومقصودة لتصميم AD-001 نفسه (Append-only حقيقي يعني بالضبط هذا: لا استثناء حتى لبيانات اختبار).** الخيار الوحيد الآمن هو تعديل تجميلي بحت (تسمية توضيحية) لـ`organizations`/`users` فقط — **لم يُنفَّذ هذا التعديل أيضًا بهذي الجولة (تحليل فقط كما طلبت)، مذكور كخيار موثَّق بانتظار قرارك إن رغبت.**

## Open Decisions — القرارات المعمارية الحقيقية المتبقية فقط

بعد التصميم الكامل أعلاه، الأسئلة المعمارية الجوهرية **كلها محسومة** (الحالات، من يملك الصلاحية، مصير كل كيان، Hard Delete غير مطلوب). **تبقى أربعة قرارات تنفيذية/سياسية صغيرة فقط، لا تغيّر التصميم العام لو تغيّرت إجاباتها:**

1. **آلية تخزين الحالة تقنيًا:** عمود `status` (Enum جديد: `active`/`archived`) أم `archived_at` (Timestamp Nullable، نمط Soft-Delete-like)؟ — تفصيل Migration بحت، لا يغيّر السلوك المُصمَّم أعلاه بأي شكل.
2. **حدث Audit تاسع لـ"OrganizationArchived/Restored":** يُضاف (يكسر القائمة المغلقة الحالية بثمانية أحداث AD-001)، أم يُكتفى بأثر `SubscriptionCancelled` الضمني (المُسجَّل فعليًا لكل اشتراك أُلغي أثناء الأرشفة) بلا حدث منفصل للمؤسسة نفسها؟
3. **تأكيدك النهائي على التوصية بإلغاء مفهوم Hard Delete كليًا** (قسم D) — بدل الاحتفاظ به كمسار ضيّق موازٍ. التصميم الحالي يفترض القبول بالتوصية؛ لو رفضتها، الشروط الذرية موثَّقة بقسم D لتنفيذها كخيار موازٍ.
4. **إعادة التسمية التجميلية للأثر الصناعي** (القسم أعلاه) — تنفيذها أم تركها كما هي دون أي تعديل؟

**لا قرار معماري آخر معلَّق — كل ما عدا الأربعة أعلاه محسوم بوضوح ضمن هذا التصميم.**
