# قرار انتقال `/dashboard` — Core Platform vs Marketplace vs Unified Home

**الحالة:** تحليل/تخطيط فقط — **بدون كود، بدون Blade، بدون تعديل Controller**. لا ينفّذ شيئًا، فقط يحسم الاتجاه المعماري ليُبنى لاحقًا حين يُصرَّح به صراحة.
**النطاق:** يجيب حصرًا عن الأسئلة الثلاثة المطلوبة (مستقبل `/dashboard`، تجربة المستخدم الجديد، بوابة معرفة كـFree Auto-Access).
**المرجع:** `phase-l1-legacy-write-cutoff-completion-report.md` (§11 — الاكتشاف الذي ولّد هذي الوثيقة) · `legacy-subscription-closure-plan.md` (قرار Path B السابق) · AD-005 · AD-006 · AD-007 · AD-011 · AD-012 · AD-013 · AD-014.
**قيد حاكم مُضاف بعد اعتماد هذي الوثيقة:** **AD-015 — Marketplace Integrates Into Hukm w Rakam, Not The Reverse** (`marketplace-architecture-blueprint.md`) — كل ما بهذي الوثيقة يحدد **كيف** ستتعايش Marketplace مع حكم ورقم يوم الدمج البصري، **لا يُشكِّل إذنًا** ببدء ذلك الدمج الآن. Header/Navigation/هوية حكم ورقم الحالية لا تتغيّر بسبب هذي الوثيقة — تبقى كما هي حتى تصريح تنفيذ منفصل صريح.

---

## تدقيق الوضع الحالي (مصدره الكود الفعلي، لا الذاكرة)

قبل أي قرار، هذا ما يحدث اليوم فعليًا بعد L1:

| الشاشة | مصدر البيانات | الحالة الفارغة الحالية |
|---|---|---|
| `/dashboard` (`DashboardController`) | `$user->subscriptions()->active()` — **Legacy فقط** (`app_subscriptions`) | "ما عندك أي تطبيق مفعّل بعد. **تصفّح متجر التطبيقات**" |
| `/my/apps` (`MyAppsController`) | `EntitlementResolver` + `marketplaceSubscriptions()` + مقاعد المؤسسة النشطة — **Marketplace الجديد فقط** | "ما عندك أي تطبيق مفعّل بعد. **ابدأ ببوابة معرفة، مجانية بالكامل**" |

**ملاحظة مهمة اكتُشفت أثناء التدقيق (لا افتراض):** الشاشتان مستقلتان تمامًا اليوم، ولكل واحدة حالة فارغة بصياغة مختلفة قليلًا — My Apps صياغتها بالفعل أقرب لدعوة استكشاف حقيقية ("ابدأ ببوابة معرفة، مجانية بالكامل") من Dashboard ("تصفّح متجر التطبيقات" فقط). هذا دليل عملي إضافي (لا نظري) إن My Apps، لا Dashboard، هي الشاشة اللي بُنيت فعليًا بمنطق Marketplace الصحيح — يدعم اتجاهك بالفعل.

**محتوى Core الحقيقي الموجود اليوم فعليًا (لا مُتخيَّل):** `organizations`/`memberships` (مكتبي/مؤسستي)، الملف الشخصي (`profile.edit`)، `bookmarks` (مفضلتي ببوابة معرفة). **لا يوجد "استشارات" أو أي محتوى Core آخر مبني فعليًا اليوم** — هذا محتوى مستقبلي مذكور بالوثيقة التأسيسية فقط (الطبقة الأولى، Core Platform)، وليس موجودًا بالكود. أي تصميم لاحق لـ"قسم Core" بالـDashboard الموحّد يجب يبدأ بالموجود فعليًا (مكتبي + ملفي الشخصي)، لا يخترع محتوى Core وهميًا لملء الشاشة — نفس مبدأ "لا حشو وهمي" المُطبَّق بكل وثائق هذا المشروع.

## 1 — مستقبل `/dashboard`: A أم B أم C؟

### الخيار A — Core Platform Dashboard فقط
`/dashboard` يُقتصَر على محتوى Core الحقيقي (مكتبي/مؤسستي، ملفي الشخصي، لاحقًا أي محتوى Core جديد فعلي) — قسم "تطبيقاتي" يُحذف كليًا، My Apps تصبح الوجهة الوحيدة للتطبيقات بلا أي إشارة لها من Dashboard.

**الإيجابيات:** أبسط تنفيذ (حذف قسم واحد فقط)، فصل Domain كامل بلا أي تعقيد تركيب لاحقًا، يطابق حرفيًا القرار السابق (Path B).
**السلبيات:** مستخدم يفتح `/dashboard` (لا يزال وجهة تسجيل الدخول الافتراضية بـLaravel Breeze) لا يرى أي إشارة لوجود Marketplace إطلاقًا ما لم يعرف مسبقًا رابط `/my/apps` أو `/marketplace` — فجوة اكتشاف (Discoverability) حقيقية لمستخدم جديد بالذات، وهو بالضبط المستخدم اللي اكتشاف L1 يخصّه.

### الخيار B — Marketplace Dashboard فقط
`/dashboard` يصبح فعليًا My Apps (إعادة توجيه أو دمج كامل) — محتوى Core (مكتبي، ملفي) ينتقل لصفحات مستقلة يوصَل لها من الهيدر لا من "اللوحة الرئيسية".

**الإيجابيات:** يحل فجوة الاكتشاف فورًا (أول شيء يراه أي مستخدم بعد الدخول هو تطبيقاته/المتجر).
**السلبيات:** يُناقض مباشرة الرسالة التأسيسية للمنصة ("حساب واحد يدير من خلاله كل احتياجاته... مكتبه، عملاءه، تطبيقاته") — لو أول شاشة بعد الدخول Marketplace-only، هذا يُعيد تأطير حكم ورقم كأنها "متجر تطبيقات له حساب" لا "منصة تشغيل لها متجر تطبيقات"، بالضبط عكس المبدأ الإلزامي رقم 1 بالوثيقة التأسيسية ("حكم ورقم هي المنتج الأساسي، الـMarketplace جزء منها فقط").

### الخيار C — Unified Home (اتجاهك المُعلَن)
`/dashboard` يبقى الوجهة الموحّدة الوحيدة بعد الدخول، لكن بتركيب صريح لمنطقين منفصلين تمامًا داخل شاشة واحدة — لا Domain Logic مُدمَج، فقط تركيب عرض (Composition):

```text
/dashboard
│
├── قسم Core (بيانات حقيقية موجودة اليوم فقط)
│   ├── مكتبي/مؤسستي (organizations/memberships — موجود)
│   └── ملفي الشخصي (رابط سريع — موجود)
│
└── قسم Marketplace (بيانات EntitlementResolver/My Apps حصرًا)
    ├── تطبيقاتي (نفس استعلام My Apps بالحرف — لا استعلام مواز جديد، AD-013)
    └── (مستقبلًا) ملخص اشتراك المؤسسة النشطة، لو صلاحيات الإدارة موجودة
```

**القيد المعماري الحاسم لو اعتُمد C لاحقًا:** القسم الثاني **يستهلك** `MyAppsController`/`EntitlementResolver` كمصدر بيانات وحيد — لا يُعاد بناء استعلام مشابه مستقل بـ`DashboardController` (هذا بالضبط النمط اللي منعه AD-013 صراحة بعد اكتشافه بـAudit سابق). عمليًا هذا يعني `DashboardController::index()` يستدعي نفس منطق `MyAppsController::index()` (استخراج كـMethod مشترك أو Service واحد يُستدعى من الاثنين) بدل تكراره — تفصيل تنفيذي يُحسَم وقت L2/التنفيذ الفعلي، لا الآن.

### التوصية

**أتفق مع ميلك لـC، بشرط واحد لا تفاوض عليه:** التركيب البصري لا يجوز يتحول لتركيب منطقي. القسمان يبقيان بمصدري بيانات مستقلَّين تمامًا (Core queries مقابل `EntitlementResolver` عبر مصدر واحد لا اثنين) — **مثل هذا التوثيق نفسه لا يقرر متى يُبنى**، فقط يثبّت الاتجاه لأي تنفيذ لاحق (L2 أو مرحلة منفصلة تُحدَّد وقتها).

**نقطة يجب حسمها صراحة وقت التنفيذ الفعلي، لا الآن:** هل `DashboardController` يُلغى ويُدمَج بـ`MyAppsController` (Controller واحد لمسارين)، أم يبقى منفصلًا ويستدعي نفس الـService؟ لا أفترض إجابة — هذا قرار تنفيذي يُترك لوثيقة Spec لاحقة لو/حين يُصرَّح بالبناء.

## 2 — ماذا يرى المستخدم الجديد؟ (تصميم مقترح فقط، غير منفَّذ)

**الوضع الحالي (بعد L1، موثَّق):** Dashboard يعرض "ما عندك أي تطبيق مفعّل بعد. تصفّح متجر التطبيقات" — صياغة محايدة لكنها لا تدعو فعليًا، فقط تُخبر.

**المقترح (تصميم نص/UX فقط، لا Blade):**

```text
العنوان: اكتشف التطبيقات والخدمات المتاحة لك
النص الفرعي: بوابة معرفة مجانية بالكامل — فعّلها بضغطة واحدة وابدأ فورًا.
الزر: تصفّح المتجر ←
```

**لماذا هذي الصياغة تحديدًا (لا افتراض عشوائي):**
- تفتح بدعوة إيجابية ("اكتشف") لا بإقرار نقص ("ما عندك") — نفس المبدأ اللي طبّقناه سابقًا بصياغة My Apps الحالية، لكن أوضح.
- تذكر بوابة معرفة تحديدًا كمثال ملموس ("مجانية بالكامل")، لا "تطبيقات" مجردة — لأنها **العنصر الحقيقي الوحيد الجاهز فعليًا اليوم** (نفس مبدأ "لا حشو وهمي" — لا نُلمّح لوجود عدة تطبيقات جاهزة بينما واحد فقط جاهز فعليًا).
- لا تَعِد بأي شيء غير موجود (لا "اكتشف عالمًا من التطبيقات" أو صياغة تسويقية مبالَغ فيها).

**نطاق هذا المقترح:** نص/تصميم مرئي مقترح فقط للاعتماد المستقبلي — **لا يُطبَّق الآن**، ينفَّذ فقط ضمن أي مرحلة تنفيذ لاحقة تُصرَّح بها صراحة (سواء ضمن C أعلاه أو تعديل مستقل أضيق).

## 3 — هل بوابة معرفة يجب أن تكون Free Auto-Access؟

**الجواب الصريح: هذا السؤال محسوم فعليًا من قبل — AD-007، والتطبيق الحالي للكود يطابقه حرفيًا اليوم.** هذا القسم يوثّق الحالة القائمة رسميًا كإجابة نهائية، لا يعيد فتحها.

**الفصل المطلوب موجود بالفعل بالكود، لا يحتاج بناء جديد:**

```text
Public Content (محتوى بوابة معرفة نفسه)
      ≠
Marketplace Access (Subscription/AccessAssignment)
```

**الدليل المباشر من الكود الحالي:**
- `/marefa`, `/laws`, `/updates`, `/calculators/gratuity` — **بلا middleware `auth` إطلاقًا** (`routes/web.php`). أي زائر، مسجَّل أو لا، يفتح المحتوى كاملًا.
- `marketplace-show.blade.php` (صفحة بوابة معرفة بالمتجر): زائر غير مسجَّل يرى نفس زر الدخول المباشر لصفحة التطبيق (`$app['href']`) — **لا Subscription يُنشأ له، ولا يُطلَب منه إنشاء حساب لمجرد التصفح.**
- الاشتراك (`SubscriptionService::subscribeUserToFreeItem`) يحدث **فقط** لمستخدم مسجَّل ضغط زر "فعّل وادخل الآن" صراحة — فعل واعٍ، لا تلقائي، لا مرتبط بزيارة المحتوى العام.

**الحكم الرسمي (تثبيت AD-007 بمثال بوابة معرفة تحديدًا):**
> بوابة معرفة = **Public Content بالكامل** (لا قيد دخول على المحتوى نفسه) + **Marketplace Application مستقلة** (لها Subscription/AccessAssignment حقيقيَّان لمن يفعّلها صراحة، تُستخدَم لأغراض My Apps/Audit/إحصاء لاحقًا، لا للتحكم بالدخول للمحتوى). الاثنان يتعايشان بلا تعارض — Entitlement (هل أنت "مفعّل" بالمتجر) لا يساوي Authorization أو حتى مجرد "الإذن بالمشاهدة" (AD-005 مطبَّق حرفيًا هنا أيضًا: زيارة المحتوى لا تحتاج قرار Entitlement أصلًا، القرار يخص فقط ظهور بادج "مفعّل لديك"/دخول من داخل نظام My Apps).

**لا حاجة لآلية جديدة أو حقل Schema إضافي الآن** (مثل `is_public` على `marketplace_items`) — الفصل قائم عمليًا بالفعل عبر غياب middleware `auth` على مسارات بوابة معرفة نفسها، لا عبر أي منطق Marketplace. لو ظهر تطبيق مستقبلي يحتاج نفس النمط (محتوى عام + Marketplace Application مستقلة)، نفس النمط (بدون middleware على مساراته الخاصة) يُعاد استخدامه بلا حاجة لتصميم جديد.

## خلاصة القرارات

| السؤال | الجواب |
|---|---|
| **1. مستقبل `/dashboard`** | **C — Unified Home**، بشرط فصل مصدر بيانات صارم (AD-013 يُطبَّق على القسمين) — **لا يُبنى الآن**، يحتاج تصريح تنفيذ منفصل لاحقًا |
| **2. تجربة المستخدم الجديد** | نص/CTA مقترح موثَّق أعلاه — **غير منفَّذ**، بانتظار تصريح تنفيذ |
| **3. بوابة معرفة Free Auto-Access؟** | **محسوم مسبقًا بـAD-007** — الفصل (Public Content ≠ Marketplace Access) قائم بالفعل بالكود، لا تعديل مطلوب |

**لا كود تغيّر بهذي الوثيقة — تحليل واتجاه معماري فقط، كما طُلب صراحة.**

## الحالة الرسمية بعد هذي الوثيقة

```
L0 Discovery          ✅
       ↓
L1 Stop Writes         ✅
       ↓
Dashboard Decision      ✅  (هذي الوثيقة — اتجاه فقط، بدون تنفيذ)
       ↓
L2 Safe Migration       🔴  (بانتظار تصريح، مقيَّد بقاعدة AD-014 المُشدَّدة أدناه)
       ↓
L3 Read Elimination     🔴
       ↓
L4 Retirement           🔴
       ↓
Phase 2C                🔴
```

**تذكير مسجَّل صراحة لأي L2 مستقبلي (تشديد AD-014، لا قرار جديد):** أي منطق ترحيل يفحص `active()->exists()` بدل `exists()` الكامل بلا تمييز الحالة، أو يُعيد تفعيل سجل `cancelled` تلقائيًا تحت أي ظرف، **مرفوض بنيويًا قبل حتى المراجعة** — لا استثناء. أي L2 Spec مستقبلي يجب يُظهر صراحة كيف يحقق: (أ) فحص وجود كامل بمعزل عن الحالة، (ب) عدم إعادة تفعيل `cancelled` أبدًا تلقائيًا، (ج) Audit Trail لكل قرار ترحيل فردي.
