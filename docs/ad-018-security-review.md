# AD-018 — مراجعة أمنية مستقلة

**النطاق:** مراجعة عدائية للتنفيذ الفعلي (`OrganizationMarketplaceAccessGuard`، ونقاط استدعائه الثلاث) — **ليست إعادة قراءة لتقرير الإكمال**. تتبّعت الكود من جديد بحثًا عن أي مسار لم يُغلَق، أي Race Condition، وأي أثر جانبي على القرارات الثلاثة المعتمَدة (Membership مسموحة، Guard منفصل عن الـModel، Restore يعيد الإمكانية بلا Reactivation تلقائي). صفر تعديل كود إضافي — الإصلاح الوحيد المطلوب (لو وُجد) يُذكَر كتوصية، لا يُنفَّذ الآن.

## الحكم النهائي

# 🟡 SECURITY REVIEW: PASS WITH ONE NOTED FINDING (غير حاجب)

**الخلاصة المباشرة:** الفجوة المحورية (Finding E1/AD-018) **مُغلَقة فعليًا وبإحكام** — تحققتُ بإعادة تنفيذ Attack Matrix كاملة، وبفحص شامل للـInventory (لا مسار رابع ظهر). القرارات الثلاثة (Membership مسموحة، Guard منفصل، Restore يعيد الإمكانية بلا Reactivation) **مُطبَّقة حرفيًا كما اعتُمدت**. وجدتُ **Finding واحدًا فقط**، درجته **Medium**، **نظري لا مُتحقَّق منه بالتنفيذ** (أول مرة بهذا المشروع أُقر بعدم القدرة على التحقق التجريبي — أوضح السبب أدناه) — **لا يمنع اعتماد AD-018 ولا الانتقال لـPhase OL**، لكن يستحق قرارًا واعيًا منك، لا إغفالًا صامتًا.

## Finding AD018-1 — Race Condition نظري بين `archive()` و`create()` (Medium، غير مُتحقَّق تجريبيًا)

### الفكرة

`OrganizationMarketplaceAccessGuard::assertCanGrantNewAccess()` يقرأ `$organization->isArchived()` على الـinstance المُمرَّر — **بلا `lockForUpdate()`**. بالمقابل، `OrganizationLifecycleService::archive()` **يقفل** صف المؤسسة (`Organization::whereKey(...)->lockForUpdate()`) طوال معاملته الكاملة. هذا يعني نظريًا: لو حدث `archive()` و`create()` **بالتزامن الحقيقي** على نفس المؤسسة (بمحرك قاعدة بيانات يدعم Row-Level Locking حقيقي كـMySQL/Postgres — **لا SQLite المُستخدَمة بيئة التطوير هنا**)، تسلسل زمني نظري ممكن:

1. `create()` يقرأ `$organization->status` = `active` (لحظة القراءة، قبل أي قفل).
2. **بالتزامن**، `archive()` بعملية أخرى يقفل صف المؤسسة، يُلغي كل اشتراك نشط **موجود وقتها**، يُحوِّل الحالة لـ`archived`، يُتمّ معاملته.
3. `create()` يتابع (لم يكن يعلم بـ#2)، يُنشئ اشتراكًا جديدًا `active` **بعد** اكتمال الأرشفة — هذا الاشتراك **لم يكن موجودًا وقت خطوة #2**، فلم يُلغَ.
4. **النتيجة النظرية:** اشتراك نشط على مؤسسة مؤرشَفة — نفس فئة Finding E1 الأصلية، لكن عبر Race لا عبر غياب فحص.

### لماذا "نظري لا مُتحقَّق تجريبيًا" — بصراحة كاملة

كل Finding سابق بهذا المشروع (شاملًا Finding H1، E1 أنفسهم) **تحقَّق منه بتنفيذ حقيقي فعلي** قبل تسجيله. حاولتُ نفس المعيار هنا، **ولم أستطع**: بيئة التطوير الحالية `SQLite` — محرك **Single-Writer** (كل معاملة كتابة تُسلسِل تلقائيًا خلف قفل قاعدة البيانات الكامل، لا قفل صف). يعني: أي محاولة تشغيل `archive()`/`create()` بعمليتي OS حقيقيتين متزامنتين (نفس منهجية L2/Phase OI/OL المُستخدَمة بكل مرة سابقة) **ستُسلسِل تلقائيًا بواسطة SQLite نفسها** — لا يمكن ملاحظة الـRace فعليًا بهذي البيئة مهما حاولتُ، لأن SQLite تمنعه بنيويًا (بصرامة أكبر مما نحتاج فعليًا). **هذا لا يعني الخطر غير حقيقي على محرك إنتاج حقيقي (MySQL/Postgres، القفل بمستوى الصف) — يعني فقط إنه غير قابل للإثبات التجريبي بالبيئة المتاحة لي الآن.** أُفصِح عن هذا القيد صراحة بدل التظاهر بتحقق لم يحدث.

### الخطورة الفعلية

**منخفضة عمليًا رغم تصنيف Medium:**
- يتطلب تزامنًا حقيقيًا بين **فعلين إداريين نادرين** (Archive + Create Subscription على نفس المؤسسة بنفس اللحظة تقريبًا) — ليس مسارًا يقدر مهاجم يستهدفه عمدًا بسهولة (لا يتحكم بتوقيت فعل إداري آخر يقوم به طرف مختلف).
- **ليس Bypass لـAuthorization أو تصعيد صلاحيات** — كلا الفعلين مصرَّح بهما بذاتهما.
- نفس فئة المخاطر المقبولة سابقًا بهذا المشروع لظروف مشابهة (سباقات Phase 2B/OI الموثَّقة، حُلَّت جزئيًا بـ`lockForUpdate` حيث كان السباق قابلًا للإثبات فعليًا، وقُبِلت كـ"نافذة ضيقة" حيث لم يكن).

### التوصية (لا تنفيذ الآن — قرارك)

لو أردتَ إغلاقها احترازيًا (بلا حاجة لإثبات تجريبي، القفل نفسه رخيص ومتّسق مع النمط الموجود):
```php
// داخل OrganizationSubscriptionService::create()، أول سطر بمعاملة الإنشاء:
$locked = Organization::whereKey($organization->id)->lockForUpdate()->firstOrFail();
$this->accessGuard->assertCanGrantNewAccess($locked);
```
يطابق تمامًا نمط `archive()`/`MembershipService` الموجود أصلًا (`Organization::lockForUpdate()` قبل أي قرار حسّاس) — لا تصميم جديد، فقط تطبيق نفس النمط هنا أيضًا.

### Security Test مقترح (يتطلب محرك Row-Level Locking حقيقي، لا SQLite)

## إعادة تأكيد القرارات الثلاثة (فحصتها فعليًا بعد التنفيذ)

1. **Membership مسموحة على مؤسسة مؤرشَفة** — تحققتُ من الكود: `MembershipService::add()`/`changeRole()`/`transferOwnership()` **لا تستدعي `OrganizationMarketplaceAccessGuard` بأي مكان** (`grep` مباشر، صفر نتائج) — القرار مُطبَّق حرفيًا، لا استثناء غير مقصود.
2. **Guard منفصل عن `Organization` Model** — تحققتُ: `app/Models/Organization.php` **لم يُعدَّل إطلاقًا** بهذي الدفعة (لا تابع جديد أُضيف له) — الفحص بالكامل بصف `OrganizationMarketplaceAccessGuard` مستقل بـ`app/Services/`.
3. **Restore يعيد الإمكانية بلا Reactivation تلقائي** — مُثبَت بتنفيذ فعلي: `test_restore_reopens_ability_to_create_new_subscription` (نجح) + `test_restore_does_not_auto_reactivate_previously_cancelled_subscription` (نجح، الاشتراك القديم يبقى `cancelled` حتى بعد Restore).

## تأكيدات إيجابية إضافية (فحصتها فعليًا)

- **Inventory النهائي بعد التنفيذ لم يتغيّر عن التصميم** — `grep` شامل جديد على كل كتابة `status=active` بـ`app/Services` يؤكد: 3 نقاط استدعاء للـGuard بالضبط (`create()`، `changeSeatLimit()` عند الزيادة، `assign()`)، لا نقطة رابعة ظهرت.
- **`reassign()` يرث الحماية تلقائيًا** — تحققتُ بتنفيذ فعلي حقيقي (اختبار مستقل نُفِّذ وحُذف بعد التأكيد): `reassign()` على مؤسسة مؤرشَفة يُرفَض (يستدعي `assign()` داخليًا، فيرث فحصها).
- **`SubscriptionsRelationManager`'s الإصلاح الإضافي (Try/Catch) لا يُخفي أي نوع استثناء آخر بالخطأ** — يلتقط `InvalidArgumentException`/`AuthorizationException` تحديدًا فقط (نفس نمط `MembershipsRelationManager` المُثبَت)، أي استثناء آخر (خطأ برمجي حقيقي) يبقى يظهر بصفحة عطل واضحة، لا يُبتلَع بصمت.
- **232/232 اختبارًا يمرّون** (تحققتُ بتشغيل فعلي)، **صفر تغيير على Dev DB الحقيقية** (`organizations=5, subscriptions=6`، بلا تغيير قبل/بعد).

## الخلاصة

# 🟡 SECURITY REVIEW: PASS WITH ONE NOTED FINDING (غير حاجب)

AD-018 مُنفَّذة بدقة، القرارات الثلاثة محترَمة حرفيًا، الفجوة المحورية مُغلَقة ومُثبَتة بتنفيذ حقيقي عبر كل قناة طُلبت (مباشر/Livewire/Session-manipulation). الـFinding الوحيد (Race نظري) **لا يستدعي حجب الانتقال لـPhase OL** — لكنه يستحق قرارك الواعي: إصلاح احترازي الآن (سطر واحد، منخفض المخاطر) أم تأجيله كملاحظة موثَّقة (نفس نمط Finding E2/H4 السابقين، مقبولة صراحة لا مُهمَلة)؟
